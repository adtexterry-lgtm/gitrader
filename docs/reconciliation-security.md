# Reconciliation security boundary

Reconciliation compares local order and fill records with a venue observation and presents advisory findings. It does not submit, cancel, amend, adopt, or backfill venue activity. A suggested fill is inferred evidence for a person to review; it is not a venue-confirmed event and does not change the economic ledger by itself.

The authenticated `reconcile.status` operation returns the current per-account view and durable review snapshots. Reading it does not change the economic ledger or resume trading. `reconcile.refresh` requests one bounded, read-only observation for one account. The ordinary `gitrader status --json` output also includes reconciliation status. A refresh can be busy while a capture is active or within the per-account interval. A venue request that does not settle remains owned by that account and is not silently repeated; other eligible accounts can continue. Automatic sampling pauses for that account only while its original ready offer remains inside its 30-second review period; other accounts continue to be sampled. A human confirmation still performs fresh venue capture and final safety checks.

The status separates a fresh view from incomplete evidence. A bounded history round may be ready while reporting that older orders remain unchecked. Failed or stale snapshots, missing critical evidence, damaged security state, and unresolved confirmation effects are unavailable and carry no confirmable offer. A successful observation time and the last attempt time describe observation metadata; neither is evidence that a venue fill occurred.

Offers expire after 30 seconds of security wall time. After the existing 10-second minimum interval, a person can confirm the original candidate during its remaining review period. Repeating the same valid observation preserves the current offer. A changed, unavailable, or expired view invalidates it; a later fresh view receives a new offer identity. Confirming an inferred fill is a separate authenticated human action with explicit fill, fee, and PnL details. Agents, services, and engines cannot confirm it.

The normal local flow is `gitrader serve`; in another terminal, run `gitrader session login` and enter the one-time bootstrap token only at its prompt. Inspect `gitrader reconcile status --account <alias-or-id>`, then optionally run `gitrader reconcile refresh --account <alias-or-id>`. Review the original `accountId`, `offerId`, `reportId`, `suggestionId`, and candidate economics. Prepare a local JSON file with exactly those four identifiers plus explicit `fee`, `feeCcy`, `liquidity`, and `realizedPnl` fields, then run `gitrader reconcile confirm '@confirmation.json'` (an explicit JSON argument is also supported). The CLI displays the exact request for review and then prompts separately for the PIN. Keep the bootstrap token and PIN out of command arguments and the JSON file. Fees and PnL must be canonical decimal strings; an unknown amount is not treated as zero.

Confirmation also observes the per-account 10-second minimum interval. It rechecks the originally reviewed candidate against fresh venue evidence and the complete local fill history for that order. An explicit refresh consumes the interval and can be busy; it does not extend the original 30-second lifetime. If the offer expires or the evidence changes, the operator must refresh, review the newly issued offer, and submit that offer explicitly. The client must not replace an accepted candidate silently. A successful response includes `fillId` and `alreadyRecorded`; check `gitrader reconcile status --account <alias-or-id>` for the resulting view. Repeating the exact original accepted request after a fresh login or restart still requires the current PIN and returns the same `fillId` without repeating financial effects.

Durable review snapshots distinguish four kinds of evidence: `inferred_fill`, `known_difference`, `late_real_fill`, and `confirmation_effects`. A pending item remains visible after restart. A valid resolution is also shown on that item; a confirmed inference instead shows its `confirmedFillId`. Resolution stops that item from blocking recovery while preserving the original finding, marker, receipt, fill, and other evidence. New distinct evidence creates a new pending item. Repeated identical late evidence does not create a new blocker.

To handle review items, inspect `gitrader reconcile status --account <alias-or-id>`. For one exact item, save a JSON object containing only `accountId`, `itemId`, `evidenceDigest`, `action`, `reason`, and a unique `requestId`, then run `gitrader reconcile resolve '@decision.json'`. The CLI prints the full captured item and exact decision before prompting for the PIN. Use `reject` only for an unbooked inferred fill; it prevents that candidate from being confirmed. Use `acknowledge` for a known difference, late real fill, or confirmation-effects item. Acknowledgement records that a person reviewed the specified evidence; it does not repair a ledger, reverse a fill, or rerun failed effects. Inspect and manage protection independently before acknowledging incomplete confirmation effects.

After resolving one item, read status again and repeat for each remaining blocking item. Only then separately run `gitrader reconcile resume --account <alias-or-id> --reason <text>` and review the displayed account state before entering the PIN. Resolve and confirm never resume automatically. The same `requestId` with the same six fields is a read-only retry and returns the original receipt after restart; reusing it with changed fields is rejected. Keep request IDs unique for different decisions. Corrupt or mismatched item, receipt, or audit bindings fail closed. The bounded review snapshots are not a complete history; do not edit the local database to clear a blocker.

A real venue fill that arrives after an inferred fill was confirmed is retained as late evidence and halts the account for human review. The confirmed ledger remains append-only. The product does not automatically book the overlapping fill, reverse the inferred record, or rewrite historical economics. A person can acknowledge each exact late-evidence item, then use the separate resume command if the account is otherwise safe to resume. For retained legacy evidence whose raw fill reference does not match the local fill schema, the review may show a derived display reference; the raw identifier and evidence remain retained, and the display reference is not a new financial fill.

Notifications contain only bounded account alias and finding fields. They do not include configuration, credentials, raw transport errors, or full reconciliation views. A notification is advisory and never performs an account action.
