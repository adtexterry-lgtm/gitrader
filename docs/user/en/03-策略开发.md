# Strategy development

## 1. What a strategy is

A strategy is **a pure function**: give it a series of closed candles and a set of parameters, and for each candle it answers one question — "how much position do I want here".

```text
target = +1     full long
target =  0     flat
target = -1     full short
target = 0.5    half long
```

The engine translates **changes** in `target` into order intents, sizes them, runs them through the risk gate and sends them to the venue. The strategy itself **places no orders, computes no order quantity, and never touches venues or secrets**. The split is deliberate: nothing you can edit here can produce a "bypass the limits" outcome.

## 2. Where the file goes

```text
~/.gitrader/engines/<engine-id>/strategies/<your-id>.ts
```

`<engine-id>` is `gitrader-core` for the bundled built-in engine. The folder is watched: within about a second of saving, the engine validates and hot-reloads the file — **no service restart needed**. A validation failure gives a readable error; fix it and save again. To see the current load report, call the engine-side extension method `x-gitrader.strategy.files` (the engine must declare the `x-gitrader.strategy-folder` capability).

Two ways to start:

- from a blank file: `gitrader examples copy template`;
- from a working example: copy any file under `packages/engine-core/examples/strategies/`.

Examples are **teaching material with no performance meaning**; they do not ship with the product and are not loaded by default.

## 3. File shape

```ts
const strategy: StrategyDef = {
  id: 'my-breakout',          // lowercase letters, digits, hyphens; 2–40 chars; unique in the folder
  name: 'Donchian breakout',
  nameZh: '唐奇安突破',        // optional
  version: '0.1.0',           // semver; bump it whenever the logic changes, backtests record it
  desc: '…',                  // plain description of the rules and when they stop working; no performance claims
  tags: ['trend'],

  params: [
    { key: 'period', label: 'Lookback bars', type: 'integer', default: 20, min: 2, max: 400, step: 1 },
  ],

  // optional hook, see section 6
  // anchor(candles, params) { return params },

  evaluate(candles, params) {
    const n = candles.length
    const target = new Array(n).fill(0)
    const reasons = new Array(n).fill('')
    const overlays: Record<string, Array<number | null>> = {}
    const warmup = 0
    return { target, reasons, overlays, warmup }
  },
}
```

### `evaluate` output contract

| Field | Type | Requirement |
|---|---|---|
| `target` | `number[n]` | One target position per candle, within `[-1, 1]`, must be finite; fill 0 during warmup |
| `reasons` | `string[n]` | Every bar where the target changes needs a one-line plain-language reason; `''` where it does not change. It is stored with the signal and the order — this is what you reconstruct incidents from |
| `overlays` | `{ [name]: (number\|null)[n] }` | Lines drawn on the price chart; `{}` is fine; at most 12 |
| `warmup` | integer >= 0 | Index of the first bar with a valid signal; may exceed `n` while still warming up |

The function must survive `n = 0`, `n` smaller than the parameter period, and every numeric parameter at its minimum or maximum — none of these may throw.

## 4. Parameters: two ways to write them, and where each applies

`params` is the single source of truth for parameters. The engine recognises only **form A** when it loads a strategy file; **form B** is a comment form of the same parameters, parsed by tooling (strategy generation, parameter extraction, writing defaults back), and comments alone are never treated as `params`. Both forms run through the same validation: types are only `number` / `integer` / `boolean` / `select`.

**Form A: the `params` array** (what the engine loads; the bundled `packages/engine-core/examples/strategies/grid.ts` uses this)

```ts
params: [
  { key: 'period', label: 'Lookback bars', type: 'integer', default: 20, min: 2, max: 400, step: 1 },
  { key: 'mode', label: 'Gear', type: 'select', default: 'fast', options: ['fast', 'slow'], help: '…' },
  { key: 'allowShort', label: 'Allow shorts', type: 'boolean', default: true },
]
```

`ParamDef` fields: `key` (camelCase, starts with a letter), `label`, `type` (`number` / `integer` / `boolean` / `select`), `default`, `min`, `max`, `step`, `options` (for `select`), `help`, `hidden` (internal parameter, not shown in forms).

**Form B: `@param` comment header** (read by tooling; same type set as form A)

```text
// @param <key> <type> default=<v> [min=<v>] [max=<v>] [step=<v>] [values=a|b|c] [label="…"] [help="…"] [hidden]
```

`<type>` may only be `number` / `integer` / `boolean` / `select`; `values` applies to `select` only and separates options with `|` (not commas); `default` must be one of the options. For example:

```ts
// @param fast_len integer default=12 min=5 max=30 step=1 label="Fast line"
// @param band_pct number default=1.5 min=0.2 max=5 help="Channel width percent"
// @param source select default=close values=close|hl2|hlc3 label="Price source"
```

Writing `int` / `float` / `str`, or `values=close,hl2,hlc3` (comma-separated), is rejected. The comment parser accepts both `//` and `#` prefixes; when writing defaults back it only touches the `default=` token and leaves every other token on the line as-is.

**Rules** (violations are rejected, never silently corrected):

- A key that is not declared in `params` fails with `unknown parameter`; out-of-range values and wrong types fail too — values are **not** clamped for you.
- Parameter names must not look like secrets (`privateKey`, `secret`, `apiSecret`, `mnemonic`, `seed`, `passphrase` and the like).
- `size` is reserved: the per-order size cap is managed by the engine, not decided by a strategy parameter.

## 5. Prohibitions

These are not style advice; the validator enforces them:

1. **No runtime `import`.** Erased type imports (`import type`) are fine; real runtime dependencies are not — copy the helpers you need into the same file.
2. **No I/O and no side effects.** No network, files, `process`, environment variables or `eval`.
3. **Must be deterministic.** The same `(candles, params)` must produce the same output: no `Math.random()`, no `Date.now()`, no hidden state carried across calls.
4. **Do not mutate parameters.** `candles` is frozen during validation.
5. **No look-ahead.** `target[i]` may only use `candles[0..i]`; normalising by the mean or extremes of the whole series counts as a violation. The validator truncates history and re-runs: if any earlier signal changes, the strategy fails.
6. **No model calls at runtime.** A language model can help you write the code once, but it is not on the real-time decision path.
7. **No performance claims in `desc`.** Say what the rules do and when they tend to stop working; that is enough.

## 6. Hooks

| Hook | When it runs | Purpose |
|---|---|---|
| `evaluate(candles, params)` | Required. Every closed candle | Produce `target` / `reasons` / `overlays` / `warmup` |
| `anchor(candles, params)` | Optional. Once when an instance or backtest **starts** | Freeze parameters that depend on "where we start" (a grid's centre price, say). The return value may only contain keys declared in `params` |

## 7. How to re-parameterise the four templates

The examples include four complete bot templates (grid, DCA, martingale, trend). Their parameters live in each file's own `params` array — **open the file and read the `key`s; that is the set of names you can pass**. Do not memorise parameter names from documentation. There are only three ways to change them:

1. **Edit `default` in the file**: bump `version` by one while you are there (backtests record the version, which makes comparison possible).
2. **Leave the file alone and pass parameters at call time**: `strategy.start` / `backtest.run` take `params`; pass only the keys you want to override, the rest use defaults.
3. **Change a running instance**: `strategy.update` (with `instanceId` and `params`); out-of-range values are rejected outright.

The knobs and the real risk of each template:

| Template | Main knobs | Where the risk actually comes from |
|---|---|---|
| Grid (long only) | Centre price and band limits, number of levels, size per level, arithmetic or geometric spacing | It goes full long once price leaves the band; in a one-way decline it keeps buying, and the drawdown comes from the position itself, not from the grid |
| DCA | How many bars between buys, size per buy, maximum number of buys, take-profit line | Long only, no timing; the closer the take-profit line, the more often it trades |
| Martingale (long only) | Size multiplier after a loss, maximum layers, overall take-profit / stop-loss | Position grows with the layer count while losses are consecutive, so the drawdown grows too; this is a **risk example kept for teaching** |
| Trend + ATR | Fast and slow EMA periods, ATR multiple, stop that only moves in the favourable direction | In a range the fast and slow lines cross back and forth and a run of small losses grinds it down; when ATR rises, the loss per trade rises with it |

Workflow after any change: backtest first ([04](04-回测与研究.md)), then paper, and only then talk about live ([05](05-实盘与风控.md)).

## 8. Checklist for one change

- [ ] `id` unique, `version` bumped, `desc` states the conditions where it stops working;
- [ ] every new tunable is declared in `params` with a default and a range;
- [ ] `n = 0`, `n = 1`, and parameters at their minimum / maximum all run;
- [ ] every `target` change has a matching `reasons` entry;
- [ ] no runtime `import`, clock, randomness or hidden state;
- [ ] only `candles[0..i]` is used;
- [ ] after saving, the engine load report shows no error codes.
