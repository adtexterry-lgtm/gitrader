# Testnet account preparation

This page covers **testnet / simulated trading** only: get accounts, keys, import and the journey scripts working first, then talk about real money (the bar for real money is in [05-live-and-risk](05-实盘与风控.md)).

What can be checked in this repository is stated as fact: command-line branches in `packages/cli/src/index.ts`, configuration fields in `packages/kernel/src/config.ts`, and connector behaviour in the relevant package. Anything that depends on the exchange's own website — page names, sign-up steps, how to claim test funds, IP binding, whether a testnet account is derived from a main account — is handled by the exchange, not by Gitrader. For those steps, follow the official Hyperliquid documentation at <https://hyperliquid.gitbook.io/hyperliquid-docs> or the official Binance documentation at <https://developers.binance.com/>. This page does not reproduce exchange-side steps or invent URLs.

## Common prerequisites

- Secrets travel on two paths only: hidden terminal input (`gitrader keys import`) or the **environment variables** present when you start `gitrader serve`. The config file holds only `env:VARIABLE_NAME` handles, never values; the scripts do not read any key file either.
- Testnet and mainnet use two sets of names: testnet variable names all carry `TESTNET` / `DEMO`, and the customary mainnet names (such as `*_API_KEY`) are never read by the testnet scripts.
- The journey scripts live under `tools/testnet/` in the repository; the host allow-list, exit codes and how to read a failure are in [tools/testnet/README.md](../../tools/testnet/README.md).

## Hyperliquid

### 1. Testnet entry point

- The testnet base URL in the connector is `https://api.hyperliquid-testnet.xyz` (`HL_ENDPOINTS.testnet.http` in `packages/connector-hyperliquid/src/rest.ts`); mainnet is a different host, `api.hyperliquid.xyz`.
- `tools/testnet/venues-testnet.json` registers only the testnet host, and `journey-hyperliquid.mjs` accepts only that; a `--base-url` pointing at any other host is rejected before any request is sent.
- The testnet web entry, sign-up and account creation live on Hyperliquid's own site. Follow the official Hyperliquid documentation: <https://hyperliquid.gitbook.io/hyperliquid-docs>.

### 2. What an account needs

- A main account (note the **public address of the main account**, `0x` followed by 20 bytes) plus one **API wallet** (one secp256k1 private key).
- The main account is used only to authorise. Orders are signed by the API wallet: the connector never holds the private key, and signing goes through the `signTypedData` handle the kernel injects (the "Trading" section of `packages/connector-hyperliquid/README.md`).
- Balances / positions / fills are looked up by the **main account address**, so the config must carry the public address of the main account (see `accounts[].owner.address` in step 5).
- How a testnet account is created, and whether it must be derived from a main account, is defined by Hyperliquid. Follow the official Hyperliquid documentation: <https://hyperliquid.gitbook.io/hyperliquid-docs>.

### 3. How to claim test funds

Test funds are claimed on Hyperliquid's testnet site. Gitrader has no implementation for claiming funds. Follow the official Hyperliquid documentation: <https://hyperliquid.gitbook.io/hyperliquid-docs>.

### 4. How to create the API wallet (permissions: read + trade only, never withdrawal)

Two ways, both local, neither puts the private key on a command line:

| Way | Command | Notes |
|---|---|---|
| Generate locally | `gitrader keys new wallet hl-testnet --network testnet --days 180` | The private key never leaves the keystore and only the address is printed; afterwards approve that address once with `approveAgent` from the main wallet |
| Import an existing one | `gitrader keys import hl-testnet --network testnet` | The private key is typed hidden in the terminal, so it is not in argv or shell history |

- After creating it, run `gitrader keys list` to see the address, status and expiry.
- The authorisation window of an API wallet is 180 days at most (`AGENT_MAX_VALID_MS` in `packages/connector-hyperliquid/src/approvals.ts`, with the same cap `WALLET_MAX_VALIDITY_DAYS` in the keystore); rotate it before it expires.
- Grant only "read + trade" and **never withdrawal**: an API wallet has no withdrawal permission itself, and you must not grant one separately when authorising. The `approveAgent` steps in the main wallet are documented by Hyperliquid: <https://hyperliquid.gitbook.io/hyperliquid-docs>.
- The "support the developer" builder fee is off by default (`supportDeveloper` defaults to false); on testnet you can skip this step.

### 5. Import into Gitrader (what to write in the config)

Two places in `gitrader.json` need changing: switch the venue to testnet, and write the account as a live-mode **testnet** account (`mode: "live"` means "connect to the venue", not "touch real money"; the network is decided by `environment`).

```json
{
  "venues": [{ "id": "hyperliquid", "environment": "testnet", "enabled": true }],
  "accounts": [
    { "alias": "hl-testnet", "venue": "hyperliquid", "environment": "testnet", "mode": "live",
      "signerRef": "hl-testnet",
      "owner": { "address": "0x0000000000000000000000000000000000000000" } }
  ]
}
```

- Set `accounts[].signerRef` to the **name** of that API wallet in the keystore (not the private key).
- Set `accounts[].owner.address` to the public address of the main account (public information, not a secret).
- After editing, start `gitrader serve` and use `gitrader status` to check that the venue is connected and the account is ready.

### 6. Run the journey script

```text
export HL_TESTNET_MAIN_ADDRESS=0xMAIN_ACCOUNT_PUBLIC_ADDRESS
export HL_TESTNET_API_WALLET_KEY=0xAPI_WALLET_PRIVATE_KEY
node tools/testnet/journey-hyperliquid.mjs --json
```

- Only these two variables get in; the other parameters are `--instrument` (default `hyperliquid:BTC`), `--account`, `--size` (default `0.001`), `--json` and `--help`.
- The default `--size` is chosen relative to Hyperliquid's minimum notional of `10` USDC (the connector writes that floor into `instrument.minNotional`, and the quantity is truncated to the instrument's step); when the notional falls short the journey doubles the size until it is enough.
- Exit codes: `0` every step passed, `1` any step failed (a redacted Problem is printed), `2` bad usage / non-compliant base URL, `3` missing environment variables (no request is sent).
- The journey uses REST only (no WebSocket); the account snapshot is refreshed by background REST, and the script only reads, never writes.
- Limit / trigger prices are placed from the reference price according to Hyperliquid's price rule (at most 5 significant digits, decimals at most 6 − `szDecimals`); the connector's instrument has no tick field, so the script computes the step from that rule itself.
- Before a real run, confirm the account has **no position and no open order** on that instrument: the journey's pre-check rejects an account that holds a position.

## Binance

### 1. Testnet entry point

- The testnet base URL of this repository's Binance connector is `https://demo-fapi.binance.com` (the USDⓈ-M perpetual testnet) and mainnet is `fapi.binance.com`; `tools/testnet/venues-testnet.json` registers only the testnet host.
- The official Binance Futures testnet site and its documentation are provided by Binance. Follow the official Binance documentation: <https://developers.binance.com/> and the testnet site <https://testnet.binancefuture.com>.

### 2. What an account needs

- A **testnet** account plus one API key / secret pair (testnet keys do not work on mainnet).
- Testnet sign-up steps are defined by Binance. Follow the official Binance documentation: <https://developers.binance.com/>.

### 3. How to claim test funds

Test funds are claimed on Binance's testnet site. Gitrader has no implementation for claiming funds. Follow the official Binance documentation: <https://developers.binance.com/>.

### 4. How to create the API key (permissions: read + trade only, never withdrawal)

- Create a key on the testnet's API management page; tick only "read" and "futures trading", **never withdrawal**, and bind an IP if you can.
- IP binding and any other restrictions are set by Binance. Follow the official Binance documentation: <https://developers.binance.com/>.
- The generated secret is shown only once; copy it into an environment variable (next step) and do not write it into the config file.

### 5. Import into Gitrader (`keys import` cannot store a key/secret)

`gitrader keys import` **currently cannot** store a Binance key/secret pair: it accepts only one 32-byte hex private key, derives the address with secp256k1 and stores it in the keystore (what is stored is an API wallet; see the `keys import` branch of `packages/cli/src/index.ts` and `packages/kernel/src/keystore.ts`). Binance credentials use `env:` handles in the config:

```json
{
  "accounts": [
    { "alias": "bn-testnet", "venue": "binance", "environment": "testnet", "mode": "live",
      "credentials": {
        "apiKey": "env:BINANCE_TESTNET_API_KEY",
        "apiSecret": "env:BINANCE_TESTNET_API_SECRET" } }
  ]
}
```

- The values behind the handles live in the **environment that starts `gitrader serve`**; the kernel accepts only the `env:` form, and when one cannot be resolved that venue falls back to read-only market data (the start-up log prints a warning).
- The config holds only the variable names, never the secrets themselves; the key names of `accounts[].credentials` match the fields the connector needs (`apiKey` / `apiSecret`).

### 6. Run the journey script

```text
export BINANCE_TESTNET_API_KEY=TESTNET_API_KEY
export BINANCE_TESTNET_API_SECRET=TESTNET_SECRET
node tools/testnet/journey-binance.mjs --json
```

- Only these two variables get in; parameters and exit codes follow the Hyperliquid section (default instrument `binance:BTCUSDT`, default `--size 0.002`).
- It talks only to `demo-fapi.binance.com`; a `--base-url` pointing at `fapi.binance.com` exits with `2` before any request is sent.
