# Backtests and research

The purpose of a backtest is not to "prove that it is profitable" but to **put the assumptions on the table before you spend anything**: costs, slippage, fills, leakage, how many attempts you made. This page covers how to run one, what to read, and which evidence to keep.

## 1. Where the data comes from

**The engine ships with no historical data.** That is by design: the data is yours and its provenance must be nameable. `BacktestSpec.data.source` is one of three:

| `source` | Meaning |
|---|---|
| `host` | Market data recorded by the host (kernel) |
| `engine` | Fetched by the engine itself (its own data source) |
| `files` | You supply files: `files[].path` + `files[].sha256` + `format` (`csv` or `json` only) |

When you supply files the **hash is mandatory**: the result records the data digest so someone else — or you, three months later — can check that it was the same data.

**`host` data is local-first and only fills gaps.** The kernel records the closed candles it has fetched on this machine (`<data dir>/data/candles/<environment>/<venue>/<symbol>/<interval>.jsonl`, one candle per line). If every closed interval grid point in the backtest window is already stored, the backtest reads **only the local store and sends no request to the exchange** (the data source is reported as `store`). If there are gaps, only the missing stretch is fetched from the exchange; candles already stored are **never replaced** by exchange data, and only newly fetched candles are recorded (source `<venue>+store`). A series holds each candle once, also after a restart and when two backtests fill the same gap at the same time. The still-forming candle is not part of this path and never appears in a backtest.

Only `csv` and `json` are accepted, and **parquet is not supported**: a spec with `format: "parquet"` is rejected with "only csv and json candle files are supported". If your data is parquet (exported from a market database, say), convert it to csv first with pandas or similar. csv columns are `t,o,h,l,c[,v]` with `t` in Unix milliseconds; a header row is allowed and malformed rows are skipped. json may be a plain array of candles or `{"candles":[...]}`.

The `files` source is available on the TypeScript engine (`@gitrader/engine-core`) only: the Python engine reads the `host` source, and `files` returns `4005 DATA_UNAVAILABLE` there (see [16-python-engine](16-Python策略引擎.md)).

## 2. Entry points

| Entry point | How | Best for |
|---|---|---|
| Agent tool set | `run` / `status` / `result` / `cancel` on `backtest` | Having an agent run it while you read results |
| Engine protocol | `backtest.run` / `backtest.status` / `backtest.result` / `backtest.cancel` | Your own engine or scripts |

There is **no** backtest subcommand on the command line: `gitrader bench` is a built-in placeholder that prints a single line saying M1 does not implement it, and the numbers are written into `docs/perf-baseline.md` by the release process. Do not treat it as a performance measurement tool.

## 3. Which `BacktestSpec` fields matter

```json
{
  "subject": { "strategy": { "id": "my-breakout", "version": "0.1.0", "params": { "period": 20 } } },
  "instruments": ["hyperliquid:BTC"],
  "interval": "1h",
  "from": 1730000000000,
  "to": 1735000000000,
  "data": { "source": "files", "files": [{ "path": "btc-1h.csv", "sha256": "<64 hex chars>", "format": "csv" }] },
  "account": { "initialBalance": "10000", "ccy": "USDC", "leverage": 2 },
  "assumptions": { "fees": { "maker": "0.0002", "taker": "0.0005" }, "slippageBps": 3, "fillModel": "next-bar-open", "funding": false, "liquidation": false },
  "seed": 7
}
```

- `subject` pins the exact strategy `id` + `version` + `params`; out-of-range or undeclared parameters are rejected, not adjusted for you.
- `assumptions` is the **mandatory honesty section**:

  | Field | Meaning |
  |---|---|
  | `fees` | maker / taker rates, or `"venue"` (use the rates the venue declares) |
  | `slippageBps` | Slippage assumption, in basis points |
  | `fillModel` | Fill model, e.g. `next-bar-open` |
  | `funding` | Whether funding is modelled. **Write `false` if it is not**, do not quietly treat it as 0 |
  | `liquidation` | Whether liquidation is modelled. Same rule |

- **Where funding comes from**: with `data.source` = `host` and `funding` set to `true`, the kernel computes funding from the public funding-rate history of Hyperliquid and Binance (read-only, no key needed, at most 2 requests per second). If that venue cannot provide it, the backtest degrades: funding is not applied, `assumptions.funding` comes back `false`, and `warnings` says funding is unavailable; do not read such a result as including funding. With a `files` source you supply a funding file (`kind` = `funding`) in `data.files` yourself.
- `seed` fixes the random source so identical input gives identical output.
- `instruments` holds **one** instrument id: this engine backtests a single instrument per job. Hyperliquid perpetual ids **do not** carry a `-PERP` suffix — write `hyperliquid:BTC` / `hyperliquid:ETH`; appending a `-PERP` suffix yourself does not resolve to an instrument (copy whatever `gitrader agent market search` returns). Instruments on a non-default dex gain one more segment, e.g. `hyperliquid:xyz:TSLA`.

**Window limits**: both the bar count (`(to - from) / interval ms`) and the time span have a cap. Exceeding either fails the job before any data is loaded, with problem code `INVALID_PARAMS` and a message such as `backtest window rejected: bars 30000 exceeds maxBars 26280 for interval 1h`. The caps follow QuantDinger's per-interval day table (1m / 3m: 30 days, 5m: 180 days, 15m / 30m: 365 days, 1h and longer: 1095 days) and are **independent of the 5000-bar per-call protocol limit** (`maxHistoryLimit`): long windows are fetched page by page (at most 5000 bars per page), and bars already in the local recording store are read locally. The engine as a whole also has a 1,000,000-bar ceiling:

| Interval | Max bars |
|---|---|
| `1m` | 43200 |
| `3m` | 14400 |
| `5m` | 51840 |
| `15m` | 35040 |
| `30m` | 17520 |
| `1h` (about 3 years) | 26280 |
| `2h` | 13140 |
| `4h` | 6570 |
| `8h` | 3285 |
| `12h` | 2190 |
| `1d` | 1095 |
| `3d` | 365 |
| `1w` | 156 |
| `1M` | 36 |

(`1M` counts as 30 days.) A window needs at least 30 bars, otherwise it returns `DATA_UNAVAILABLE`. The Python engine's window rules are not covered by this table.

## 4. How to read the result

**An agent fetching a result (`result` on `backtest`) gets a summary by default**: statistics, bias checks, assumptions, warnings and data digest, plus `counts: { equity, trades, funding }` (how many items each series has). Fetch the equity curve, the fills and the funding detail page by page with `part: "equity" | "trades" | "funding"`: each page returns `{ items, total, next? }`, `items` in ascending time order, `limit` 1–1000 (default 500; if a page does not fit the server returns fewer items and still gives `next` instead of truncating); pass the previous page's `next` as `cursor`; the last page has no `next`. The same applies to both engines and to results of any size. On the command line: `gitrader agent backtest result --args '{"jobId":"…","part":"equity","limit":500}'`.

Two blocks in `BacktestResult` must be read separately:

**Statistics** (`stats`): `totalReturnRatio`, `annualizedRatio`, `maxDrawdownRatio`, `sharpe`, `sortino`, `winRatio`, `profitFactor` (`null` when there are no fills), `trades`, `fills`, `avgHoldBars`, `spanDays`, `finalEquity`. Ratios are fractions (0.12 = 12%).

**Bias checks** (`biasChecks`): the results of the `lookahead` and `recursive` checks, plus `trialCount` — how many parameter sets this strategy was tested with during this piece of research. **A large `trialCount` with only one good set is essentially luck**; multiple-comparison problems do not disappear because the metrics look nice.

**Per trade** (`trades`): time, side, price, quantity, PnL, fee, and the `reason` the strategy supplied. When reviewing, read `reason` and the fill price first, the summary second.

## 5. Walk-forward

Rolling windows: sweep parameters over a training window, run the immediately following test window — which **took no part in choosing parameters** — out of sample, shift the whole window forward, and finally stitch the out-of-sample returns of each fold together.

Rules (implemented in `packages/engine-core/src/strategy/walk-forward.ts`, pure functions, callable from scripts):

- training window `[start, start+trainBars)`, test window `[start+trainBars+embargo, ... + testBars)`;
- `embargoBars`: bars left empty between the training and test windows, to handle signal decay and overlap;
- `blindHoldoutBars`: a slice kept at the **end** of the series that no window may touch — the final blind segment;
- the step defaults to `testBars` (non-overlapping windows);
- each fold records the `bestParams` chosen on the training window, training Sharpe, test Sharpe and per-period test returns;
- the summary gives `oosReturns` (folds stitched together) and `oosSharpe`, plus an **efficiency ratio** = mean test Sharpe / mean training Sharpe (`null` when the fold count is 0 or mean training Sharpe <= 0).

How to read it: an efficiency ratio clearly below 1 means the parameters do not survive out of sample; with a single fold (data too short) the number carries no information.

## 6. Holdout and experiment stages

As a strategy moves forward it is recorded as an **experiment**, and the stages form a fixed ladder:

```text
hypothesis → backtest → holdout → shadow → live_small → live
```

- `draft` equals `hypothesis`, and `paper` equals `shadow` (legacy aliases).
- Each stage promotion needs the matching evidence pack, and the rule depends on the stage:
  - To `backtest`: an agent must already have a `backtest` evidence pack (run a backtest first, then generate the pack with the `pack` action on `experiment`); without one the call returns `EXPERIMENT_EVIDENCE_INCOMPLETE` and the stage does not change. Moving it yourself in the workbench is not affected.
  - To `live_small` / `live`: an agent's request is always refused (`EXPERIMENT_TRANSITION_DENIED`, leaving only a request record); you review it in the workbench and enter your PIN (`lab.stage`).
- Experiments carry a `holdoutWindow`: state which period is the holdout segment. Holdout data may only be looked at in the `holdout` stage; if you looked earlier, it is no longer a holdout.
- `live_small` means **trial run**: the evidence pack's `trialCount` is the larger of "number of distinct parameter specifications within the same experiment family" and "number of backtests the same executor ran in the last 30 days" (`TRIAL_WINDOW_DAYS` = 30, that lookback).
- Experiments that involved a language model must be marked `llm` truthfully. The protocol carries `LLM_LEAK_MARGIN_DAYS` (90 days) and a table of known training cut-offs: if the data window sits too close to a model's training cut-off there is a suspicion that "it has seen this market", and the `holdout` stage will ask you to explain.

## 7. Experiment registry

Agent-side `experiment` tool actions: `create` / `get` / `list` / `update` / `attach` / `stage` / `pack` / `export`.

What has to be written down (fill it in completely, or nobody — including you — can review it later):

| Field | What to write |
|---|---|
| `title`, `hypothesis` | A one-sentence hypothesis; not a conclusion |
| `subject` | Strategy `id` + `version` |
| `params` | The parameters tried this time |
| `assumptions` | The same cost assumptions as in the backtest |
| `data` | Data source and range (files need a digest) |
| `lineage` | Which experiment / version this evolved from |
| `holdoutWindow` | The holdout segment |
| `llm` | Whether a model was involved, and at which step |
| `conclusion` | The conclusion. "Under which conditions it stops working" is far more useful than "it works" |

Copying the input below creates an experiment (`create` needs only `patch`). `sha256` comes from `strategySha256` in a backtest result: run one backtest first to get it; when the engine is ready the kernel also checks it against the strategy `id` itself:

```json
{
  "action": "create",
  "patch": {
    "title": "<title>",
    "hypothesis": "<one-sentence hypothesis>",
    "subject": {
      "strategy": { "kind": "strategy", "id": "<strategy id>", "version": "<version>", "sha256": "<sha256>" },
      "params": {}
    }
  }
}
```

When `kind` / `id` / `version` / `sha256` of `subject.strategy` is wrong or missing, the error names the path (for example `/subject/strategy/version`).

Wording that reads like a return claim in a conclusion or description is rejected outright — this is a product red line, not a style check.

## 8. Evidence packs and export

```text
gitrader lab export <experiment-id> --out <file>
gitrader lab verify <file>
```

- `lab export` turns an experiment into a portable pack (evidence plus digest). With `--out <file>` it writes to the file you name (an absolute path, or relative to the current directory; not limited to the data directory) and prints the path written; without `--out` the JSON goes to the screen.
- `lab verify` checks a pack offline (read-only): a file given by absolute path can be anywhere, a relative path is looked up in `<data dir>/lab`; exit code 0 when the content matches; on mismatch it prints the differences and exits 1. **Verify it yourself before sending it to anyone.**

Forward records have their own exit:

```text
gitrader ledger export [--out <name>]        # written to <data dir>/exports/<name>; without a name: gitrader-ledger-YYYYMMDD-HHmmss (local time)
gitrader ledger export --redact              # drop payloads, keep the skeleton
gitrader ledger verify                       # recompute the hash chain of the local database
gitrader ledger verify <export dir>          # check an export
```

An export directory holds four files:

- `账单.csv` ("bill"): **for humans**, opens directly in Excel. Fills only; columns are time, account, instrument, side (buy / sell, in Chinese), quantity, price, fee, realized PnL, and executor (you / agent name / system). Times are **local time on this machine**.
- `trade-log.md`: also a human-readable fill log, also in local time, with the time zone noted in the table header.
- `ledger.jsonl` and `manifest.json`: kept as they are, for audit and for `ledger verify`.

`manifest.json` (`gitrader-ledger-export/2`) carries the chain head at export time, a completeness flag, and a signature made with the install signing key. `ledger verify <export dir>` checks the signature, the entry count, the first and last sequence numbers and the last hash, so it **detects an export whose tail was deleted or that was modified**. When the local database is readable it also uses the install public key from the database as the trusted key and compares against the database, reporting "the database has N newer entries since the export". Older (/1) exports have no signature; verify can only warn that tail deletion cannot be detected.

The limit, stated plainly: the signing identity lives on this machine, so **anyone who can read the local install private key can still re-sign a fully rewritten export**. A valid signature proves "consistent with that install key, unmodified since export", not that the key is yours.

## 9. How to produce a report

Backtest reports have a ready-made exit:

1. **`gitrader research report <backtest job id>`** (`--format md|json`, `--out <file>`); agents use the `backtest_report` action of the `research` tool. It returns `{ jobId, headline, metrics, markdown, truncated, assumptions }`: the Sharpe, total return, max drawdown, final equity, fill count and fees in `metrics` are exactly equal to the fields of the same name in the backtest result's `stats` (not recomputed, not rounded); the Markdown report is cut at 6000 characters with `truncated` set, and the whole reply stays within 8000 bytes. A job that has not finished returns `BUSY`, a job that does not exist returns an error, never an empty report.
2. **Experiment packs** (`lab export`): machine-readable, verifiable, suited to archiving and handover;
3. **Ledger exports** (`ledger export`): the forward fill log; the `账单.csv` and Markdown files are the human-readable ones;
4. **Backtest result JSON** (`result` on `backtest`): render it into tables or charts yourself.

Parameter search, factor reports, portfolio analysis and symbol search use the same `research` tool and `gitrader research` command; see pages 17, 13, 19 and 14.

A report must carry the assumptions verbatim (fees, slippage, fill model, whether funding and liquidation are modelled) and the data digest. Numbers without their assumptions are not numbers.

## 10. Three rules

- **Backtest / replay data never enters the forward ledger.** The forward ledger records only actions that really happened.
- **No forward inference.** A report says what happened inside a historical window; it does not say what will happen next.
- **Say how many attempts you made.** `trialCount` and the experiment record are two sides of one thing: reporting only the best set is lying by omission.
