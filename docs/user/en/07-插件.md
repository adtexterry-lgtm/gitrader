# Plugins

Plugins are how you install "the personal stuff" into Gitrader: indicators, data sources, protectors, panel blocks, notification channels, skill packs. **Dropping a file into the directory is the install** — no install wizard, no marketplace.

## 1. Directory and installation

```text
~/.gitrader/plugins/<dir-name>/gitrader-plugin.json
~/.gitrader/plugins/<plugin-id>/<version>/gitrader-plugin.json
```

Both on-disk shapes are recognised. After installing, run once:

```text
gitrader plugins reload
```

It notifies the service if it is running, otherwise it scans offline. Output is `+added ~updated -removed, rejected n`; any rejection lists its reason line by line, and the exit code is then 2.

## 2. The six commands

| Command | Effect | Needs the service running |
|---|---|---|
| `gitrader plugins check <dir> [--strict] [--json]` | Validate only, do not install. One `code path message` line each, final line `ok <id>@<version>` or `REJECTED n problem(s)`; 0 on pass, 2 on rejection | No |
| `gitrader plugins pin <dir>` | Recompute and write back `source.sha256` (re-pin after changing any file) | No |
| `gitrader plugins reload` | Rescan the plugin directory | Needs a local session when the service is running; not otherwise |
| `gitrader plugins list` | Per plugin: validation result, granted / pending permissions, enabled or not | No |
| `gitrader plugins grant <id> [permission...]` | Enable the plugin and grant permissions one by one (needs PIN, **service must be stopped**) | Must be stopped |
| `gitrader plugins call <id> <tool> [json\|@file\|-]` | Call a tool once | No (starts a temporary kernel; uses the service if it is running) |

The `--strict` flag on `check` validates under "unsigned does not pass" rules — use it before releasing, not the default rules.

## 3. Manifest fields

Main fields: `schema`, `id`, `kind`, `name`, `version`, `vendor`, `source` (including the content hash), `license`, `runtime` (`type`: `node` / `browser` / `builtin` ...), `entry`, `permissions`, `ui.blocks`, `requires`, `signature`, `compat`.

`kind` values: `connector` / `datasource` / `factor` / `decision-model` / `executor` / `protector` / `strategy` / `workflow-template` / `engine` / `block` / `skill` / `layout-preset`.

Field-level specifications are in `docs/plugin-protocol.md` and `packages/protocol/src/plugin/manifest.ts`. The M1 kernel **can only launch plugins with `runtime.type = "node"`** (child process); other runtime types pass manifest validation but return "not supported in M1" at start-up.

### `tools[]`: tools exposed to agents

```json
"tools": [
  { "name": "position_size", "desc": "…", "tags": ["utility", "risk"],
    "input": { "type": "object", "required": ["equity", "stop"], "properties": { "equity": { "type": "string" }, "stop": { "type": "string" } } },
    "output": { "type": "object", "required": ["qty"] },
    "permissions": [] }
]
```

- `input` must be a JSON Schema with `type: "object"`; it is validated before the call and a mismatch is `INVALID_PARAMS` (with the field path in the message).
- When `output` is declared, a non-conforming return value is `PLUGIN_RESULT_INVALID` and the result is not passed to the agent.
- **Tools not listed in `tools[]` are not forwarded by the kernel** (`PLUGIN_TOOL_UNKNOWN`).
- A tool's own `permissions` must be a subset of the manifest permissions, and every one of them must already be granted (otherwise `MANDATE_LIMIT`).
- Tool arguments **must not include secret-like parameters** (`TOOL_SOLICITS_SECRET`, rejected at install).

### `evidence`: performance and backtest numbers

`evidence: { claims: [...], notes? }`, each entry `{ metric, value, basis, window: {from,to}, ref?, assumptions? }`.

- `basis` is only `backtest` / `paper` / `live`;
- backtest claims must state `assumptions` (costs, slippage, data source and range); paper / live claims must carry a `ref`;
- `claims` may be an empty array: **having no numbers is an honest answer**;
- the kernel and the UI display it verbatim, with no second pass.

## 4. Permissions: deny by default

- A capability exists only if it is **declared** in the manifest; and even then it is granted only after you confirm (`plugins grant`). Grants are item by item and each one is written to the ledger.
- Requestable: `market.read`, `account.read`, `ledger.read`, `ledger.append`, `trade.paper`, `trade.propose`, `trade.live` (still bound by mandate and risk gate), `takeover.trigger` (own scope only), `venue.credentials` (connectors only), `net.fetch`, `fs.read.user`, `workspace.control`, `ui.block`, `notify.user`.
- **Never grantable**, and rejected at install if written: `withdraw`, `transfer`, `approval.decide`, `risk.relax`, `policy.write`, `mandate.issue`, `mandate.promote`, `credential.read`, `plugin.install`, `risk.temporaryRelax`.
  In other words: a plugin cannot withdraw, transfer, approve proposals, relax risk limits (temporarily or permanently), issue or promote mandates, read plaintext credentials, or install other plugins.
- Pass conditions (all four must hold): validation passes, the plugin is enabled, the tool is declared in `tools[]`, every permission the tool declares is granted, and the arguments match the schema.

## 5. Version pinning and content hash

- `source.sha256` in the manifest = the hash of every file in the package except the manifest itself, `{path, sha256}` sorted by path.
- The kernel recomputes it on load and **rejects a mismatch**; if the content changes while the plugin is running, it is stopped.
- After changing any file, re-pin with `gitrader plugins pin <dir>`.
- Dependencies (`requires`) must be exact versions plus a hash; there is no `latest`.

## 6. Signatures and developer mode

- Signed plugins: `signature` is an Ed25519 signature over the digest of "manifest (minus the signature) + file list", and the signing public key must be in the trust roots. Trust roots = built-in (empty in M1) + public keys you write into `plugins.trustRoots`.
- Unsigned plugins: loaded only when `plugins.developerMode: true` (local development), and they **cannot** request `trade.live` or `venue.credentials`.
- Bundled plugins (the 6 notification plugins such as `gitrader plugins install notify-webhook`) do **not** need `developerMode`: the product build generates a content-hash list `dist/plugins-bundled/BUNDLED-HASHES.json` for them (each plugin's id, version, content pin and manifest digest), and the kernel reads that list only from the product's own install directory; a file with the same name under `GITRADER_HOME` or in the config is never accepted. An installed bundled plugin is trusted as built-in only if its content matches the list item by item; changing any of its files (even if you re-pin the version with `plugins pin`) or its manifest is rejected (`UNSIGNED_NOT_ALLOWED`), and `gitrader plugins install <name> --force` reinstalls it. This trust introduces no signing private key and does not relax the requirements for other unsigned plugins.
- A wrong signature, or a key not in the trust roots, means the install is rejected.

## 7. Isolation: not a security sandbox

- Node plugins run in a separate child process: they do not inherit your environment, the working directory is the plugin directory, and they talk to the kernel over stdin/stdout only; Node's `--permission` and `--allow-fs-read=<plugin dir>` are added to limit file reads and child processes.
- **This is not a security sandbox.** Permissions are enforced at the kernel API layer (a plugin gets data only through the kernel); process-level restrictions are best effort, and Node 22 does not enforce network restrictions. Trust in a third-party plugin comes mainly from signatures and source review.
- A crash restarts with backoff, and there is a periodic health check.
- Blocks on the browser runtime run in an iframe with `sandbox="allow-scripts"` (no `allow-same-origin`) and can only reach the subscriptions / queries / commands declared in the manifest, through the block bridge.

## 8. Where to copy your first one from

Two examples live under `packages/plugin-template/example/`:

- `ema-reading`: an EMA reading indicator block (with UI);
- `position-size`: a zero-permission tool plugin — **copy this one for your first plugin**; steps are in `docs/plugin-quickstart.md`.

A minimal working loop looks like this:

```text
cp -r <template-dir> ~/.gitrader/plugins/my-plugin     # change id / name / tool name
gitrader plugins check ~/.gitrader/plugins/my-plugin
gitrader plugins pin ~/.gitrader/plugins/my-plugin
gitrader plugins reload
gitrader plugins grant my-plugin                    # service stopped, PIN required
gitrader plugins call my-plugin my_tool @args.json
```

## 9. Common rejection codes

| Code | Meaning | Fix |
|---|---|---|
| `SCHEMA` | Manifest is missing a field or has a wrong type | Fill in against the field table |
| `PERMISSION_UNKNOWN` | Permission name is not in the enum | Use the list in section 4 |
| `PERMISSION_NEVER_GRANTABLE` | A never-grantable permission was requested | Remove it; that capability is not a plugin's to have |
| `HASH_MISMATCH` | Content does not match `source.sha256` | Re-pin with `plugins pin` |
| `SIGNATURE_KEY_UNTRUSTED` | Signing public key is not in the trust roots | Add `plugins.trustRoots`, or use `plugins.developerMode` during development |
| `TOOL_SOLICITS_SECRET` | A tool argument asks for a secret | Read it from an environment variable instead |
| `PROMISE_LANGUAGE` | Copy contains return-claim wording | Restate it as a fact |

## 10. Uninstalling

Move the directory away, then `gitrader plugins reload`. Granted-permission records remain (they are needed for audit); to clear them completely, revoke from the plugin page in the workbench using the id shown by `plugins list`. Install, upgrade and removal are all written to the ledger.

## 11. First-run pitfalls: reload, developerMode, permission kinds, upgrading on Windows

The four things that stop most first-time plugin authors. All of it is current behaviour; following this section saves a round of debugging.

### 11.1 `gitrader plugins reload` needs a local session while the service is running

- **Service not running**: the command scans offline, needs no session, and prints `+added ~updated -removed, rejected n`.
- **Service running**: the command goes through the service write operation (`plugin.reload`), which needs a local write session — exchange the one-time boot token with `gitrader session login` first. If you never logged in, or the session expired, the command fails and tells you to run `gitrader session login`. Scripts hit this on the first call; it is not a plugin problem.

### 11.2 Changing `plugins.developerMode` requires a service restart

`gitrader.json` is read once at startup: there is no file watcher and no SIGHUP reload, and `plugins reload` uses the in-memory copy. So "set `plugins.developerMode` to `true`, then reload" has no effect — run `gitrader stop`, then `gitrader serve`.

### 11.3 Permissions must match the `kind`: a `skill` cannot request `net.fetch`

Declaring a permission is not enough — `packages/protocol/src/plugin/manifest.ts` holds a "permission to allowed `kind`" table. `net.fetch` is limited to `datasource` / `decision-model` / `connector` / `engine`; a `skill` or `block` manifest that lists `net.fetch` fails validation with `PERMISSION_KIND_MISMATCH` (`kind skill cannot request net.fetch`). The same applies elsewhere: `trade.live` only for `executor` / `engine`, `fs.read.user` only for `engine` / `factor` / `datasource`, `venue.credentials` only for `connector`.

The manifest `package` field has exactly two values: `skill` and `block`. `package: "skill"` must be paired with `kind: "skill"` (otherwise `PACKAGE_KIND_MISMATCH`); notification channel plugins use `package: "block"` with `kind: "connector"`, which is not a conflict.

**The runtime layer does not enforce it**: section 7's "this is not a security sandbox" applies to skills too — the manifest rejects `net.fetch`, but inside the child process `require('node:https')` is not blocked by Node (Node 22's `--permission` does not cover network APIs). Trust in a third-party skill therefore rests on signatures and source review; do not read "no `net.fetch` in the manifest" as "it cannot reach the network".

### 11.4 Upgrading a plugin that is in use, on Windows

Windows locks the files an active plugin process has open: overwriting or deleting the plugin directory fails (`EBUSY` / `EPERM`), and `plugins reload` then cannot see the new content. The CLI has no sub-command that stops a single plugin, so the correct order is to stop the service:

```text
gitrader stop                                     # stops the service; plugin child processes exit and the directory unlocks
# replace the contents of ~/.gitrader/plugins/<dirname> (re-pin if any file changed)
gitrader plugins pin ~/.gitrader/plugins/<dirname>
gitrader serve                                    # start the service again
gitrader plugins reload                           # with the service running this needs a session; otherwise run it while stopped
gitrader plugins list                             # confirm the version and hash are the new ones
```

Uninstalling works the same way: moving the directory away before reloading fails on Windows, so run `gitrader stop` first.
