# Parameter search: read the evidence level first

The easiest thing to do with a parameter search is to pick the best-looking parameter set from one stretch of history and then treat it as evidence about the future. The optimizer package (`@gitrader/optimizer`) does not allow that: **overfitting metrics are not optional, and out-of-sample validation is a required argument**.

It runs on top of engine-core backtests and uses only the public entry point `runBacktest` plus the public statistics in `@gitrader/stats`. It does not touch the kernel, does not go online, and has no third-party dependencies.

## 0. Using it in the installed product

The optimizer package is a library (`@gitrader/optimizer`); the installed `gitrader` wires it up as **asynchronous jobs**, the same shape as backtests: start a job, watch progress, fetch the result. Research is read-only: it places no orders and writes no trading ledger entries.

Command line (modelled on Freqtrade's hyperopt subcommand):

```
gitrader research optimize --strategy ema-cross --data btcusdt-1h.csv \
  --space '{"fast":{"type":"integer","min":5,"max":15,"step":5},"slow":{"type":"integer","min":20,"max":60,"step":20}}' \
  --validation holdout:300 --json
gitrader research walk-forward --strategy ema-cross --data btcusdt-1h.csv --space @space.json --validation wf:600:200
```

- `--data` is a `t,o,h,l,c[,v]` candle CSV (millisecond timestamps); without it use `--instrument` / `--from` / `--to` to read venue data. `--search grid|random:<n>|evolution`, `--seed` defaults to 42, `--fee` to 0.0005 (taker), `--slippage` to 3 bp.
- By default the command waits for the job; `--json` prints exactly one JSON (it contains `jobId`). `--no-wait` only starts the job, after which you use `gitrader research status|result|cancel <job id>`; `result <job id> --part trials|folds` pages through the detail.

Agents use the MCP tool `research`: `optimize` / `walk_forward` start a job (returns `{ jobId, kind, state }`), `status` shows progress, `result` returns the summary (at most 8 KB, with `counts`), `result` with `part: "trials" | "folds"` plus `limit` / `cursor` pages the detail, and `cancel` stops it.

Rules in the product (checked synchronously before any job exists; a violation returns `INVALID_PARAMS` and creates nothing):

- `validation` is required (`holdout` or `walk-forward`); the `walk_forward` action only takes a walk-forward plan.
- A grid or random search may not exceed 500 combinations; names in `space` must be parameters the strategy declares; parameters that are not searched go into `subject.strategy.params`.
- The result matches calling `optimize()` directly, point for point; the summary carries `overfit` (PBO / DSR / trial count), `validation` (out-of-sample score) and the first-line banner. Every number is a **hypothetical backtest**, not forward evidence.

What follows describes the library itself (the arguments and result of `optimize()`).

## 1. Three searches and one mandatory validation

| Kind | Behaviour | Reproducibility |
|---|---|---|
| `grid` | Cartesian product of the parameter space, first dimension slowest; if the number of combinations exceeds `maxTrials` it throws `RangeError` instead of **quietly sampling** | Fully deterministic, no random numbers (`seed` is recorded as 0) |
| `random` | Each dimension sampled uniformly over its domain, numeric values snapped to the step grid, `trials` distinct combinations | Same `seed` gives point-for-point identical results |
| `evolution` | Elitism plus tournament selection, uniform crossover, per-gene mutation; `population x generations` evaluations | Same `seed` gives point-for-point identical results |

A given parameter combination is backtested once (results are cached by parameter key inside the search), so **the trial count is the number of backtests actually run**.

## 2. Usage

```ts
import { optimize, renderReport } from '@gitrader/optimizer'

const result = optimize({
  strategy,
  candles,
  space: {
    fast: { type: 'integer', min: 3, max: 20, step: 1 },
    slow: { type: 'integer', min: 10, max: 60, step: 5 },
    mode: { type: 'select', options: ['long', 'both'] },
  },
  search: { kind: 'evolution', population: 12, generations: 4 },
  validation: { kind: 'walk-forward', trainBars: 120, testBars: 40, embargoBars: 1 },
  seed: 7,
  sim: { feeRate: 0.0005, slippageBps: 2 },
})

console.log(renderReport(result))   // the first line of the report is the evidence level
```

- Omitting `validation` throws `TypeError`: **a search with no out-of-sample evidence is not accepted here**.
- `metric` defaults to Sharpe; pass your own `returns => number` for another objective (Calmar, a turnover penalty, and so on).
- `sim` holds fees and slippage; when omitted, the engine-core defaults apply (fee rate 0.00045, slippage 2 bp), which need not be your venue's real rates — **get the fees right first**.

## 3. The four things you must read

| Field | Meaning | How to read it |
|---|---|---|
| `overfit.trials` | Combinations actually backtested inside the search range (excluding the holdout and blind segments) | More trials means the winner is more likely to be luck. Always present |
| `overfit.pbo` | CSCV probability of backtest overfitting (Bailey–Borwein–López de Prado–Zhu 2014) | Nearer 0.5 looks like noise; 8 blocks by default (C(8,4)=70 combinations), reduced to the largest even block that divides the sample, `null` under two periods |
| `overfit.dsr` | Deflated Sharpe of the best trial (Bailey & López de Prado 2014), benchmarked against the expected maximum Sharpe over N trials | DSR is a probability (0..1): the closer to 1, the more clearly the best Sharpe exceeds the expected maximum over N trials; well below 0.95, you cannot rule out that the winner is just luck |
| `validation` | Out-of-sample score of each walk-forward fold or of the holdout period | Only out-of-sample scores count as evidence; an `efficiency` (out-of-sample over in-sample) that collapses means overfitting |

A metric that cannot be computed has a **`null` field and its reason listed in `missing`**; nothing is padded with zero.

When **`inSampleOnly`** is true (walk-forward could not build a window or produced no valid fold, or the holdout sample yielded no usable trial), the first line of the report is the fixed banner: **in-sample only, not forward evidence**. That line is a conclusion, not a disclaimer.

## 4. Validation methods

- `walk-forward`: window rules match engine-core's walk-forward. The test window starts right after the training window, `embargoBars` may sit between them, and `blindHoldoutBars` at the end is untouched by both. Each fold is optimised on its training window only, and the in-sample best parameters are taken to the test window unchanged.
- `holdout`: optimise in-sample, then backtest the in-sample best parameters once on the trailing holdout period.
- The search seed per fold is `seed + fold index`, so folds do not sample the same combinations while the whole run stays reproducible.
- **Search range**: `best`, `trials`, PBO and DSR are computed on the in-sample range only — the first `n - holdoutBars` bars for `holdout`, the first `n - blindHoldoutBars` bars for walk-forward; the holdout period and the blind segment take part in no search or scoring, and `searchRange` in the result states the range. The out-of-sample scores of the walk-forward folds evaluate this search process as a whole; the final `best` is re-chosen over the entire search range and has no separate out-of-sample evidence of its own.
- **Warm-up `warmupBars`**: you can give it explicitly, or let it be inferred from parameter names (lookback-style names such as `period` / `lookback` / `window` / `length` / `bars`); the test window and the hold-out segment borrow `warmupBars` bars of earlier history so the indicators warm up first, and the borrowed part is not scored. When it is neither given nor inferable there is a warning (the first bars before the indicators are ready are scored too). `testBars` should still be a multiple of the longest lookback, otherwise the window may hold no signal and the out-of-sample score drifts towards 0.

## 5. What it does not do

- **No fill simulation**: that belongs to engine-core and sim-book; this runs on candle-level backtest assumptions.
- **No multi-objective search**: the objective is a single `returns => number`. Write your own `metric` for a composite.
- **No judgement about whether a parameter makes economic sense**, and no advice about going live.
- No parameter-sensitivity heat map. `trials` carries every trial's parameters and return series, so plot it yourself.

## 6. What an honest result sheet contains

At minimum: search kind and seed, trial count, `pbo`, `dsr`, validation kind and each fold's out-of-sample score, fee and slippage assumptions, and the full `warnings` list. Without any one of those, the result is "best in-sample" and nothing more.
