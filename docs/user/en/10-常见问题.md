# Troubleshooting

Grouped by "where you are stuck right now". Every entry gives a runnable next step, not a "please check your configuration".

## Install and start-up

**Q: The `gitrader` command does not exist.**
A: You need Node >= 22.13 (`node --version`). While the package is not published to npm, `npx gitrader …` will not work; build and install the tarball from source with `npm install && npm run pack:release -- --skip-portable` (output `dist-release/gitrader-<version>.tgz`, then `npm install -g` that file), or build the portable package with `npm run pack:portable -- --platform win-x64`, as described in the root `README.md`, or use the built `dist/bin.js` inside the repository.

**Q: Start-up says the port is in use.**
A: By default it finds a free port from 47900 upward, skipping a list of common ports. To pin one use `gitrader serve --port 48080`; you can also change `server.port` (`null` = automatic). `--port` wins.

**Q: `a Gitrader service is already running for <home>`.**
A: Only one instance per home directory. Stop the running one first (Ctrl+C in its terminal), or point `--home` at a different home directory for an isolated experiment.

**Q: `status` says the service is not running.**
A: The service is not up, or the pid in `service.json` is gone. Run the suggested next step, `gitrader serve --detach`, and try again. The exit code is 0 in this case (the state was determined); in scripts branch on the `running` field of `--json`.

**Q: Market data never connects, but I want to work on strategies first.**
A: `gitrader serve --offline` (equivalent to `GITRADER_OFFLINE=1`). No market data is connected; accounts, ledger, plugins and strategy files work as usual, and paper matching has no price input so nothing fills.

**Q: I broke the configuration file and the service will not start.**
A: The error lists every offending field and the reason (no silent correction). Fix them as indicated; if all else fails, delete that item from `~/.gitrader/gitrader.json` — re-running `gitrader init` only fills in what is missing and does not overwrite existing content.

**Q: How do I upgrade (for example from 0.1.0 to 0.1.1)?**
A: You do not need to touch your data; the new version uses `~/.gitrader` (or the folder `GITRADER_HOME` points to) as it is. Steps:
1. Run `gitrader stop` first. A service you leave running keeps running the old version.
2. Install the new version the way you installed the old one: for an npm install, `npm install -g <new tgz>` over the top; for the portable package, unzip the new archive into a **different** folder and start it with that folder's `start.cmd` (`./start.sh` on macOS / Linux), then delete the old folder once everything works.
3. Run `gitrader serve` again. `gitrader --version` and `gitrader status` should now show the same version.
4. To confirm the ledger is intact: `gitrader ledger verify`.
Browser sessions that were logged in end when the service restarts; get a fresh link with `gitrader open` (in the portable package, `bin\gitrader.cmd open`).

**Q: How do I uninstall?**
A: Run `gitrader stop` first. Then remove the program the way you installed it: `npm uninstall -g gitrader` for an npm install, or delete the unzipped folder for the portable package. This does not touch your data.
Your data is in `~/.gitrader` (or the folder `GITRADER_HOME` points to): key vault, config and ledger. To remove it as well, delete that folder; it cannot be recovered, so copy it somewhere first if you want a backup. The `gitrader` entries you added to host configs when connecting an agent (`.mcp.json`, `~/.codex/config.toml` and so on) and any token files you saved are yours to remove on the host side.

## Workbench

**Q: The link says it has expired.**
A: The `launch` token in the start-up link is **single-use and valid for 120 seconds**, and reloading the page invalidates it. Press Enter in the `serve` terminal for a fresh link, or run `gitrader open --print` (needs PIN).

**Q: `gitrader open` says no PIN is set.**
A: Run `gitrader init` once in a terminal to set one (non-interactive environments do not ask). Without a PIN no link can be signed; the one printed by `serve` still works.

**Q: Can I embed the workbench in my own system?**
A: Yes, but it is forbidden by default. `gitrader config set embed.allowedOrigins https://app.example`, then **restart the service**. Only `scheme://host[:port]` is accepted, no wildcards or paths; `none` clears it. Only page embedding is loosened — `/api` and WebSocket still require tokens.

## PIN and keys

**Q: I forgot the PIN.**
A: There is no recovery path — the master key is derived from the PIN and cannot be derived backwards. To reset you must delete `~/.gitrader/keys/` and run `gitrader init` again, at the cost of **losing the encrypted API wallet private keys**, which then have to be re-imported with `gitrader keys import` from copies you stored separately.

**Q: How do I make an agent lose its access immediately?**
A: Revoke its agent key, which needs your PIN: in the workbench, Settings → Keys → Agent keys, click "Revoke" on its row (the agent card's tier menu also has "Revoke this agent…"), or run `gitrader keys revoke agent <name>` in your own terminal. After that it can no longer place orders and pending approvals are voided; **existing positions and resting orders are not handled automatically**, so deal with them yourself. Do not let an agent write scripts to revoke itself.

**Q: A wallet in `keys list` is marked `ROTATE SOON`.**
A: Reminders start `keys.walletExpiryWarnDays` before expiry (default 14 days). Generate a new one with `gitrader keys new wallet <new-name> --days 180`, `approveAgent` the new address from the main wallet, repoint `accounts[].signerRef` at it, and finally `gitrader keys revoke wallet <old-name>`.

**Q: Importing a private key fails.**
A: `gitrader keys import <name> --network mainnet` reads hidden terminal input; paste the hexadecimal private key itself (no decoration beyond the `0x` prefix, no quotes). Passing a private key as a command-line argument is never accepted — by design.

## Strategies

**Q: I added a strategy file but `engines list` shows no new strategy.**
A: Three things: (1) is the directory right (`~/.gitrader/engines/<engine-id>/strategies/`, and `gitrader-core` for the built-in engine); (2) is the `id` valid and unique within the folder (lowercase letters, digits, hyphens, 2–40 characters); (3) are there validation errors — a load report appears about a second after saving, with line numbers and reasons.

**Q: Starting the strategy reports `unknown parameter`.**
A: Parameters must be declared in the file's `params` (or in `@param` comments). Passing an undeclared key is rejected; wrong types and out-of-range values are rejected too — **not** clamped for you.

**Q: `engines list` shows `bound:no`.**
A: The engine is not bound to an account. Run `gitrader engines bind gitrader-core` (needs PIN; binds the paper account by default) with the service running.

**Q: The strategy runs but nothing happens.**
A: Check `warmup` first — `target` staying at 0 during warm-up is normal. Then check whether `reasons` ever changes; if `target` is changing but the gate is blocking it, look at denial counts in `gitrader risk stats`.

**Q: My strategies are gone after a restart.**
A: Strategy instances on paper accounts are restored automatically (with their original parameters) once the engine reconnects and every instrument they use is known. While a venue's instrument list is still loading the restore waits and retries by itself (up to about 10 minutes, then the instance is listed in `needsRestart` with `restore timed out`); that wait does not count as a failed restore. Instances on live accounts, or while trading is restricted (`REDUCING` / `HALTED`), are **not** restored: they are listed in the `gitrader status` warnings and in the `needsRestart` field of `engines`, each with a reason. Restart or stop them yourself once you have checked. To restart one, pass its original `instanceId` to `start_strategy`: the same id is reused and the warning is cleared (an id that is already running, or does not exist, is rejected and nothing is started). The system never takes over a live account for you and never places or cancels an order because of this.

**Q: Why can't I open a live position for a while after a restart?**
A: Opening a live position waits for the venue's startup reconciliation: after a restart the kernel first checks its local open orders and fills against the venue, and only then allows new positions (`startupReconciled` in the venue readiness of `gitrader status` turns true). While it is pending, failed or unknown, opening orders are rejected (`TRADING_STATE`, reason `startup reconcile pending`); reducing, closing and cancelling are not affected, and a failed reconciliation is retried automatically after a pause. Paper accounts are not affected.

**Q: What if an engine hangs?**
A: If the engine process is alive but its heartbeat has stopped, `engines status` reports it as `degraded` (`heartbeat lost`) and its bound accounts are first tightened to `REDUCING`. After two heartbeat timeouts without a heartbeat the kernel ends that local engine process and restarts it with the usual backoff. The accounts stay `REDUCING` after the restart until you confirm and run `reconcile resume`, and paper instances are listed in `needsRestart` until you restart them.

## Backtests and research

**Q: The backtest produced no fills at all.**
A: Three common causes: the data range is too short (not enough warm-up), `target` is always 0 (the logic never triggers), or the price series is constant. Also check `biasChecks` and whether the parameters you just changed can ever trigger a signal.

**Q: Walk-forward produced zero folds.**
A: The windows do not fit: you need `trainBars + embargoBars + testBars <= n - blindHoldoutBars`. With too few bars, lower `testBars` or `blindHoldoutBars`, or use a longer data set.

**Q: `data.files[].sha256` does not match.**
A: The kernel refuses to run. Recompute the file's sha256 and fill it in; do not change the hash to something else just to get the backtest running — that gives up the ability to check which data a result belongs to.

**Q: What does a large `trialCount` tell me?**
A: That this strategy was tested with many parameter sets during this research. Reporting only the best set and not how many attempts it took is the most common way research lies to itself. Hand over `trialCount` together with the experiment record.

**Q: `lab verify` reports a mismatch.**
A: The pack changed after export, or it is not the same experiment. Do not send it out; run `lab export` again.

## Plugins and notifications

**Q: `plugins check` reports `REJECTED`.**
A: Read each `code path message` line. The three most common: a permission name that is not in the enum, a request for a never-grantable permission (such as `withdraw`), and `HASH_MISMATCH` (files changed without re-pinning — run `gitrader plugins pin <dir>`).

**Q: `plugins grant` says the service is running.**
A: Deliberate: the grant entry point requires the local PIN and we do not want two writers changing permissions at once. Press Ctrl+C in the `serve` terminal, run `gitrader plugins grant <id> [permission...]`, then start `serve` again.

**Q: A notification test returns `missing secret handle: <NAME>`.**
A: Automatic forwarding and declaration-based secret injection are wired up. Configure a `plugins.secrets` environment handle for `<NAME>`, set the value in the environment of the process that starts the kernel, then start the plugin and run `gitrader notify test <channelId>`. Results and the outlet log report only the name; `notify_send` is callable only by the notification outlet and the human-facing test, a generic `plugins call` and an agent call are refused.

**Q: Why is there no proposal reason, takeover reason or note in the notification?**
A: By design, not a bug. The kernel builds the body from a whitelist of fields, so it carries structured facts only (account, instrument, rule, values, state). Free text is never forwarded, and a string that is not fact-shaped is written as `[text omitted]`. Read the ledger for the record (`gitrader ledger export`), and do not expect a channel plugin to "restore" the body.

**Q: I get several notices for one takeover, or none at all.**
A: Several: the notice key is merged by takeoverId, stage updates share one key, and a channel sends it once per dedupe window; setting `notify.rateLimit.dedupeWindowSec` to 0 disables dedupe (a failed or alert stage still sends its own critical notice, which is expected). None: check whether `notify.channels` is empty, whether a channel `minLevel` is above the event level, and whether a rule routes that topic to another channel; confirm the channel itself with `gitrader notify test <channel id>`.

**Q: Can a channel secret be short, say a 6-character passcode?**
A: No. A secret value shorter than 8 characters is never compared against plugin reply frames; the only trace is a `short secret excluded from frame scan` warning at startup, which means the kernel cannot see that value leaking. Use a random value of at least 8 characters, one per channel.

**Q: Writing `secret` or `password` under `notify.channels[].params` fails validation.**
A: `params` carries non-secret parameters only. A key name that matches `privateKey`, `secret`, `apiSecret`, `mnemonic`, `seed`, `passphrase`, `pin` or `password` (case-insensitive, ignoring `_` and `-`) fails validation and points you at `plugins.secrets`: store only an `env:VARIABLE_NAME` handle in the configuration and keep the value in the environment of the kernel process.

**Q: Passing JSON to `plugins call` always fails on Windows.**
A: The `.cmd` shim swallows inner double quotes. Write the arguments into `args.json` and use `@args.json`.

**Q: The plugin is installed but the agent cannot see the tool.**
A: Four conditions, all required: validation passes, the plugin is enabled (`plugins grant`), the tool is declared in the manifest's `tools[]`, and every permission the tool declares is granted. A missing one returns the matching code (`PLUGIN_TOOL_UNKNOWN` / `MANDATE_LIMIT` / `INVALID_PARAMS`).

## Trading state

**Q: How do I resume from `HALTED`?**
A: Only you, entering your PIN. If it was triggered by a `HALT` file in the home directory, delete the file first and then resume (resuming is refused while the file exists). Do not expect a service restart to fix it — the latch is by design.

**Q: The state is `REDUCING`.**
A: Reduce and cancel only. The usual causes are a protector firing, an agent heartbeat timeout, or a takeover you triggered. `gitrader status` states the reason in parentheses.

**Q: An order was denied and I do not know which rule.**
A: `gitrader risk stats` shows denial counts; once you have a `precheckId`, `gitrader risk replay <precheckId>` replays the verdict field by field and lists the rule codes that differed.

**Q: `ledger verify` reports `LEDGER BROKEN at seq N`.**
A: The chain breaks at that point. Stop writing: export for evidence first (`gitrader ledger export --out <dir>`), then investigate the system state around that entry (disk, clock, whether a second process is writing the same database).

**Q: I made a mess of the paper account, how do I reset it?**
A: `gitrader paper reset --account paper` (needs PIN, service must be running). It resets that paper account explicitly; live accounts are unaffected.

## Other

**Q: Why does `gitrader bench` print only one line?**
A: It is an M1 placeholder. Performance numbers are written into `docs/perf-baseline.md` by the release process, not measured locally.

**Q: Where are the logs?**
A: Kernel logs go to stderr, prefixed with `[gitrader]`. Audit data is in the ledger (`~/.gitrader/data/gitrader.sqlite`); access it with `gitrader ledger verify` and `ledger export`, and do not open the database to edit it directly.

**Q: What if these documents disagree with the code?**
A: The code wins (`packages/cli/src/index.ts` and `packages/kernel/src/config.ts`). Run `node docs/user/en/verify-docs-en.mjs` to see which kind of drift it is: command name, configuration key, or banned word.
