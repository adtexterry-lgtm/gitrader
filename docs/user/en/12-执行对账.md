# Execution reconciliation: what to look at when your ledger and the venue disagree

Sooner or later your ledger and the venue disagree: a fill that never got recorded, a restart that left orders in limbo, an amend that produced a new order id, half a minute of a dead connection. Reconciliation puts both sides next to each other and states **where they differ, what it suggests you do, and which record is the evidence**.

**One rule first: reconciliation only produces a verdict, it never writes.** The package has no write path at all: it does not place or cancel orders, does not touch the ledger, sends no requests and never reads the system clock. Whether and how to correct the ledger is a human decision.

## 1. Input and output

```ts
import { reconcile, renderReport } from '@gitrader/exec-reconcile'

const report = reconcile(
  {
    local: { accountId, orders, fills, positions, asOf },   // what the ledger believes right now
    venue: { openOrders, historyOrders, fills, positions, asOf, truncated, unavailable },
    links,                                                  // optional: amend chain (client id to venue id)
  },
  {
    now,                                    // required: no system clock, so the same input reproduces
    clockSkewMs: 2_000,
    venueLatencyMs: 5_000,
    sizeTolerance: '0',
    positionTolerance: '0.0001',
    priceToleranceBps: 5,
    fillLookbackMs: 24 * 3600_000,
    staleAfterMs: 60_000,
    ownClientOrderIdPrefixes: ['gt-'],
    dedupeFallback: 'accept_with_risk',     // or 'needs_human'
  },
)

report.verdict        // clean | attention | blocked
report.findings       // each: code + suggested action + needs-human flag + evidence
report.inferredFills  // inferred fills, all inferred: true, with basis and price source
report.dedupe         // dedupe keys, repeated arrivals, same-id conflicts
console.log(renderReport(report, { venueLabel: 'venue name' }))
```

| Verdict | Meaning | What to do |
|---|---|---|
| `clean` | No difference inside the views you passed | Nothing; differences may still sit outside the views, see "What it cannot see" |
| `attention` | A difference that is explainable, can wait, and does not poison the ledger | Follow the suggested action, usually re-check after the in-flight window |
| `blocked` | A difference that would poison the ledger (lost fill, position mismatch, fill-id conflict) | **Stop new trading actions**, verify by hand, then decide. Never auto-correct the ledger from a verdict |

## 2. Seven groups of differences (38 codes)

| Group | Typical codes | How it decides |
|---|---|---|
| Local has it, venue does not | `local_open_venue_filled` / `local_open_venue_cancelled` / `local_open_venue_partially_recorded` / `local_open_venue_missing` | Check history orders first, then whether a fill landed on that order id, then whether it is still inside the venue reporting window |
| Venue has it, local does not | `venue_order_unmapped` / `venue_order_external` / `local_terminal_venue_open` | An id that looks like ours but is unclaimed goes to a human; an id with a foreign prefix is external and is never adopted automatically |
| State and size drift | `order_state_drift` / `order_filled_size_drift` / `order_price_drift` / `order_reduce_only_drift` | Field by field; the direction matters (venue ahead means a missed fill, ledger ahead often means the venue reset after an amend) |
| Amend chain | `amend_chain_resolved` / `amend_chain_broken` / `amend_chain_ambiguous` / `order_venue_id_conflict` | Several ids on one chain, a missing link, or one id claimed twice are handled differently |
| Fills | `fill_duplicate` / `fill_conflict` / `fill_orphan` / `fill_missing_inferred` / `fill_missing_unexplained` / `fill_recorded_excess` / `fill_total_exceeds_order` / `fill_time_anomaly` and more | Dedupe, claim to an order, infer the gap, then look for ledger-side duplicates |
| Positions | `position_size_mismatch` / `position_missing_at_venue` / `position_missing_locally` / `position_side_mismatch` / `position_entry_price_drift` and more | Compared per instrument, side and margin mode; net and per-side both checked |
| View quality | `snapshot_stale` / `venue_fills_truncated` / `venue_report_unavailable` | A view that is stale, a backfill that was cut short, a report the venue cannot produce: the verdict is downgraded |

Everything ambiguous becomes a suggestion such as `query_order_status`, `wait_and_recheck` or `review_*`, and `advice.requiresHuman = true`. Every finding carries `advice.why` and `evidence` (which report, which record, which field, which value). Read the evidence, not just the verdict.

## 3. Inferred fills: it tells you when it is guessing

When the venue's cumulative filled size exceeds what the ledger recorded, reconciliation emits an **inferred fill**:

- It always carries `inferred: true`, and `basis` states each step (what the venue report says, what the ledger recorded, the difference, where price and time came from).
- Only two price sources are allowed: the venue order report's average fill price (preferred), or the last fill price on that order in the ledger with `priceSource: 'local_last_fill_price'`, and the basis says it is a stand-in.
- With neither available it does not invent a price: it reports `fill_missing_unexplained` at blocking severity for a human.
- A difference inside `sizeTolerance` is not inferred. A ledger ahead of the venue is not inferred either; that becomes `fill_recorded_excess`.
- Each inferred fill has a deterministic `id` (`inferred:<venueOrderId>:<ledgerTotal>-><venueCumulative>`): re-running reconciliation on the same gap yields the same id, which lets you dedupe against a gap a human already confirmed.

**Inferred is not fact.** Posting it requires a human decision.

## 4. Time and dedupe: why it does not rush to say "lost"

- Every comparison carries tolerance: clock skew plus venue latency form an in-flight window, and "venue has not seen it" inside that window only suggests a re-check.
- A fill timestamped in the future beyond the skew, or older than the lookback window, is reported separately as `fill_time_anomaly`.
- Dedupe key priority: venue fill id, then a fallback composite key (`orderId|time|qty|price`), then a cumulative key. The fallback can misread two identical fills as one duplicate; the report says so (`fill_dedupe_key_fallback`), and `dedupeFallback: 'needs_human'` hands the case straight to a person.

## 5. What it cannot see

Reconciliation only sees the views you pass in. These cases bias the verdict:

- A venue that cannot produce a report type (some brokers do not query completed orders) should declare it in `unavailable`; an undeclared "not found" reads as "does not exist".
- Truncated history (`truncated`): differences outside the window are invisible.
- Amend chains that live only in memory and are lost on restart can make amend-related differences look like external orders.

State these limits in your report. `clean` does not mean the ledger is certainly correct.

## 6. Where it sits

- The kernel's own startup reconciliation (`startupReconcile()`) does three things: pull open orders and recent fills from the venue, look up local open orders the venue does not report and count them as unresolved, and backfill fills by venue fill id. It does **not** compare positions, does **not** compare filled sizes, and does **not** distinguish "venue says no" from "venue cannot say".
- The kernel's `reconcile.status` provides the current reconciliation view of an account, `reconcile.refresh` collects evidence again, `reconcile.confirm` writes into the ledger only inferred fills that a human has confirmed, and `reconcile.resolve` records a human decision on a pending item. The kernel still enforces risk by its own deterministic rules; handling pending items from the CLI never edits the original differences and never resumes trading automatically.

## 7. Viewing and handling the kernel's pending items

```sh
gitrader reconcile status
gitrader reconcile status --account paper
gitrader reconcile status --json
gitrader reconcile resolve --item <ITEM_ID> --action acknowledge --reason "Checked the venue report against the local record"
gitrader reconcile resolve --item <ITEM_ID> --action reject --reason "Do not confirm this inferred fill"
```

The default status output lists, per account, the pending items, the problem name in plain language, the evidence fields and values, the allowed actions and the next command. When nothing is pending it says "no pending reconciliation items"; when evidence is unavailable it also tells you to refresh. `--json` returns the kernel's raw `ReconcileAccountView[]`, with no field or content changed.

`reviews` in the status holds the review records that were kept. `blocking` means the record itself is of a blocking type; the condition that still needs handling is `blocking = true`, no `resolution`, and no `confirmedFillId`. So handled or confirmed historical records may still appear in the JSON but are no longer shown as current to-dos. The `findings` of the current view filter out findings whose review has been handled, and neither the original report nor the historical review records are deleted or rewritten. When there are blocking findings but no review record that can be handled, the CLI tells you to refresh the evidence and never invents a handling action.

The new-style `resolve` takes the account, item ID and `evidenceDigest` from the current local view and generates a unique `requestId`; when the evidence changes, look again before issuing it. The old six-field JSON still works:

| Field | Meaning | Source in the new-style command |
|---|---|---|
| `accountId` | The account the item belongs to | Filled in from the current pending item; `--account` can narrow the account |
| `itemId` | ID of the current review record | `--item` |
| `evidenceDigest` | Digest of that record's current evidence | Filled in from the current local view, so stale evidence is not reused |
| `action` | The human decision | `--action`; `inferred_fill` allows only `reject`, every other pending type allows only `acknowledge` |
| `reason` | A reason of 1 to 500 non-blank characters | `--reason` |
| `requestId` | Idempotency identifier | Generated automatically by each new-style command; the old JSON form must supply its own |

`reject` means the inferred fill is not accepted; `acknowledge` means the other pending differences were looked at and the handling is recorded. Both write only a review receipt: they never change the financial ledger and never resume trading automatically. To resume, you still run `gitrader reconcile resume --account <alias|accountId> --reason <reason>` separately and pass PIN verification.
