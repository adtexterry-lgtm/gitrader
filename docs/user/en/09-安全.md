# Security

This page states plainly what Gitrader does and does not stand behind. Each line maps to code in the kernel; anything not done is written down as not done.

## 1. Three-tier threat model

| Tier | Threat | Commitment |
|---|---|---|
| **T-A** | Agents connected over MCP, including those hit by prompt injection or memory injection | **Enforced.** Approval, limits, keys and resuming trading **are simply not on the tool surface** (there is no entry point, not an entry point that is blocked); every order goes through a mandate and the risk gate; the origin of every record is stamped by the server from the authenticated identity, so an agent cannot self-declare who it is; an agent can only trigger self-protection actions: stop new entries / cancel / close everything / downgrade itself |
| **T-B** | Other processes on this machine calling the local API (including coding agents with a shell) | **Enforced.** Every local endpoint requires a token; the human session token lives only in the UI process's memory and never on disk; loosening actions need a PIN; the risk policy is a kernel-verified document, and if it is missing or modified the state becomes `HALTED`. **If such a process can execute arbitrary code to modify files and read memory, it falls into T-C** |
| **T-C** | Malicious code running as the same system user (modify files, read memory, break user-level encryption, read an unlocked key) | **Not covered.** Mitigations: the API wallet has no withdrawal permission, use a separate sub-account, keep limits small. M1 has no "hardened mode" |

**"The risk gate cannot be bypassed" covers only orders executed through the workbench**: engine mode A (the kernel sends the order), orders you place by hand, orders an agent places over MCP. Orders an external engine places by connecting to the venue itself (mode B) only get advisory risk checks, and the UI marks them as such.

## 2. Local API authentication

- The service binds `127.0.0.1` only.
- **No token, no identity.** Request headers such as `Origin`, `Sec-Fetch-Site` and `Host` are **only ever used to reject** (cross-site browser requests, DNS rebinding) and never to allow — a non-browser process can forge them freely.
- Four kinds of token, each with its own job:

  | Token | Used by | Lifetime | Capability |
  |---|---|---|---|
  | Session `ses_…` | The workbench UI | Memory only, 12 hours, gone on restart | Session-level actions |
  | Bootstrap `boot_…` | The link printed by `serve` | **Single use, 120 seconds** | Exchange for a session token; dead once used |
  | Service `svc_…` | The command line and other local tools | Stored in `service.json` | Read-only plus PIN-present actions; **cannot act as a session** |
  | Agent key `gtk_…` | Connected agents | Until the mandate expires | Inside the mandate only; the plaintext is shown once |

- `service.json`, the keystore and the PIN file are written with tightened permissions: `chmod 600` on POSIX; on Windows `icacls` to remove inheritance and keep only the current user. A failure to tighten does not crash anything, but the state output says so honestly.

## 3. PIN

- 6–12 digits, or a passphrase of 8–64 arbitrary characters (the UI still calls it a PIN). Sequential or all-identical weak PINs (such as `123456`, `000000`) get a "use it anyway?" confirmation in both the web page and the terminal; they are set only after you confirm.
- Derived with scrypt (N=2^17, r=8, p=1, about 128 MB of memory) and **then combined with the device key via HKDF-SHA256** into a 32-byte master key; only the salt and a verifier are stored on disk.
- Failure backoff: no lock for the first 3 attempts, then 1 s, 2 s, 4 s … growing exponentially up to 15 minutes; the backoff state is persisted and survives a restart.
- The PIN never enters logs, the ledger or error messages; the command line **never reads a PIN or private key from arguments** (only from hidden terminal input or stdin).

## 4. Secrets at rest

- API wallet private keys live in `~/.gitrader/keys/keystore.json`, encrypted with **AES-256-GCM**; the master key is derived from the PIN and **never written to disk** — after unlocking it exists only in memory and can be locked again at any time.
- Private keys never leave the kernel: generating a wallet returns only the address; on import the key is read from hidden terminal input.
- The install signing key (which signs ledger checkpoints) is in `keys/install-key.json`.
- The device key is in `keys/device.key.json`: 32 random bytes, generated when the PIN is first set. **On Windows it is wrapped with DPAPI (CurrentUser)**; on macOS / Linux it has file permissions 0600 only, with **no OS keychain wrapping**.

**What this layer defends against**: copying away only `pin.json` + `keystore.json` (a backup, a sync drive, a whole-disk image restored under a different account or machine) without the device key gives no way to brute-force the PIN offline. On Windows the device key file will not decrypt under another machine or user. When all three files are copied together, protection falls back to "PIN strength + scrypt N=2^17" — roughly a fraction of a second per core, so 6 digits do not hold up against anyone with compute, which is why a passphrase is recommended.

**Still not covered** (T-C): malicious code running as the same user can call DPAPI, read memory while the store is unlocked, or install a keylogger.

**Operational requirements**: do not put `~/.gitrader/keys/` on a sync drive. Losing the device key (reinstall, different user) means the keystore cannot be opened, and you must re-import your separately stored API wallet private keys. Keep API wallets to no more than 180 days and rotate them regularly (the reminder window is `keys.walletExpiryWarnDays`, default 14 days).

## 5. Human-only actions

An agent key can call none of the following. "PIN" = must be entered on the spot; "session" = a workbench session is enough.

| Action | Presence required |
|---|---|
| Unlock the keystore, request a new launch link for a running instance, rotate the service token | PIN |
| Resume trading from `REDUCING` / `HALTED` | PIN |
| Relax risk limits (including temporary loosenings, which expire automatically after at most 24 hours) | PIN |
| Turn off "no live entries from a model" | PIN (turning it on needs only a session) |
| Switch risk preset: wider needs PIN, stricter needs only a session | PIN / session |
| Create / rotate agent keys, issue or promote mandates | PIN |
| Bind an engine to an account | PIN |
| Approve a proposal | Session; PIN above `presenceAboveNotional`; PIN first when approving a live order while the keystore is locked |
| Revoke an agent key (UI: Settings → Keys → Agent keys → Revoke; terminal: `gitrader keys revoke agent <name>`) | PIN |
| Tighten risk, reject a proposal, revoke a mandate / API wallet | Session |
| Grant plugin permissions, uninstall a plugin, export the ledger, switch mainnet / testnet, toggle "let agents adjust layout" | Session |
| Change the PIN | Current PIN |

**Takeover** (stop new entries / cancel resting orders / close everything) can be triggered by both humans and agents and **needs no PIN** — self-protection has to be fast.

## 6. Risk and halting

- The risk gate is the **only** order checkpoint: the mandate (limits, account / venue / instrument allowlists, expiry, heartbeat) and the risk policy (limits, protectors) are combined by taking the stricter of the two; stale market data or a missing price means denial.
- Trading state has three values: `ACTIVE` / `REDUCING` / `HALTED`. Entering the latter two includes: you triggered a takeover, a protector fired, an agent heartbeat timed out, startup reconciliation failed, risk-policy signature verification failed.
- What still passes while `HALTED`: cancels and **reduce-only** closes (a halt must not leave you unable to close); every exposure-increasing action, strategy start, mandate issuance and plugin start is denied. Resuming is possible only with your PIN.
- When a mandate requires a heartbeat, missing it automatically drops the agent to read-only and stops new entries.
- Actions of model origin are always labelled with their origin in the ledger and the UI (human / engine / LLM agent / system) and can be banned with one switch. **Gitrader itself calls no language model.**

## 7. Ledger

- An append-only SQLite ledger; each entry carries the hash of the previous one (a hash chain), checkpoints are written periodically and signed with the install signing key. `gitrader ledger verify` recomputes the entire chain.
- **Only the kernel clock counts**: a caller-supplied timestamp more than 60 seconds earlier or 5 seconds later than the kernel clock is rejected (anti-backdating).
- **Start-up chain check**: on every start the kernel recomputes the ledger hash chain (with many entries it verifies from the latest checkpoint, and runs a full pass every 10 minutes while running) and cross-checks the latest 200 fills against the fills table. A broken chain or a mismatch → all trading stops (`HALTED`); the chain is re-verified before trading may resume, and resuming is refused if it still fails; `gitrader doctor` turns red and gives the next step.
- **A missing ledger database never silently starts over**: when `data/gitrader.sqlite` is gone but the machine still holds the signing key / paper state / agent tokens, `gitrader serve` refuses to start. Restore from a backup; add `--accept-new-ledger` only when you really want a fresh ledger (its first entry records that fact).
- **Paper state and ledger check each other**: the digest of `paper-state.json` is recorded in the ledger database; if the file is deleted, truncated, altered or replaced by an old backup, the paper accounts stop trading, and both the original file and `paper-state.json.prev` are left untouched and never overwritten. Ways out: put the original file or `.prev` back and restart, or stop the service and run `gitrader paper rebuild-from-ledger` (rebuilds cash, positions and resting stops with the ledger as the authority). When a disk write fails the kernel retries automatically and the order receipt carries a `state_not_persisted` notice.
- Backtest / replay data may not be written into the forward ledger; payloads containing secret-like or vendor-private fields are refused.
- **Honest limitation**: a local hash chain only proves the export **was not modified after export**; it cannot stop someone who holds the whole ledger file from rewriting the whole thing. An export (`gitrader-ledger-export/2`) additionally carries the chain head at export time and a signature made with the install signing key, so `ledger verify <export dir>` can detect a deleted tail; but anyone who can read the local install private key can still re-sign one. See the export section of [04-backtesting and research](04-回测与研究.md).

## 8. Other boundaries

- **iframe embedding**: forbidden by default (`frame-ancestors 'none'`). To embed in a host page, configure `embed.allowedOrigins` (accepts only `scheme://host[:port]`, no wildcards or paths). What is loosened is only "a cross-site page navigating into an iframe"; `/api` and WebSocket still require tokens.
- **PIN-free link retrieval**: `gitrader open --print --json --unattended --origin <origin>` uses the service token and is allowed **only** when `embed.allowedOrigins` is configured and `--origin` is on the list. With it on, any same-user process that can read `service.json` can obtain a workbench session (session-level actions only; PIN actions still need the PIN). If you do not need embedding, leave it off.
- **Reloading the page needs a new link**: the session token lives only in page memory and the launch token is single-use — by design, not a fault.
- **Order idempotency**: every order-style operation accepts `clientOrderId`. After a timeout **do not resend blindly** — retry with the same id (the kernel returns the original order, the venue sees it once), or look it up with `order.lookup`.
- **Agent call rate**: every key (and every session, service token and engine) has its own token bucket: capacity 200 and 60 refilled per second by default; read-only calls such as quotes / prices / previews go through a smaller separate bucket (capacity 100, 30 per second). A browser workbench session (the human) has its own large bucket (capacity 1000, 300 per second, shared by reads and commands), so a second window of the same session does not crowd the first out. Placing, cancelling, closing, emergency stop and approvals are not counted (self-protection actions must never be throttled). Going over returns `RATE_BUDGET` (HTTP 429, with `retryAfterMs`), throttled calls feed the metric `gitrader_op_rate_limited_total`, and the ledger records at most one `rate.limited` per key per minute. Refused previews are ledgered too, but per key per minute only the first 20 are written one by one and the rest as one summary (count, rule distribution, sample), plus one daily summary. Tune it in `operationRateLimit` of the `server` section (including `readOnly` and `session`).
- **Stops after a restart**: if the stop attached to an opening order was not recorded because the kernel crashed, on restart the kernel adopts the stop that exists on the venue; where the venue has none either, a paper account gets one placed automatically (only once, and a stop a human cancelled later is not put back), while a live account only gets a warning, switches to reduce-only and waits for your confirmation.
- **Plugins**: process isolation **is not a security sandbox**; permissions are enforced at the kernel API layer and network restrictions are not enforced by Node.
- **Engines**: local child processes do not inherit your environment; an engine cannot obtain API wallet private keys (mode A).
- **Data**: stays on this machine by default.
- **Supply chain**: dependencies are version-pinned; build artefacts ship with `THIRD-PARTY-NOTICES.md`.

## 9. In one table

| Covered | Not covered |
|---|---|
| Orders through the workbench pass the mandate and the risk gate | Orders an external engine places by connecting to the venue itself |
| Human-presence actions can only be completed by you, present | Malicious code running as the same system user |
| Secrets are stored encrypted and the PIN is never written to disk | Offline brute force when all three key files are copied away together |
| The ledger is verifiable and exportable | Someone holding the whole ledger file rewriting the entire chain |
| A plugin only gets the permissions you granted | Whether the plugin itself is malicious (that relies on signatures and provenance) |

## 10. Reporting problems

How to report security issues is described in `SECURITY.md` at the repository root. Please do not post exploit details, secrets or raw ledger contents in public issues.
