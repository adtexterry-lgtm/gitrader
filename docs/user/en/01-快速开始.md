# First run

Goal: bring Gitrader up with a single command and run one sample strategy on a **paper account**. Nothing here touches real money; the default network is testnet.

Prerequisites: Node >= 22.13 (check with `node --version`). No Git, Python or Java required, and no database.

## 1. Create the home directory

```text
gitrader init
```

What it does (safe to re-run; existing files and directories are left alone):

- creates `~/.gitrader/` plus six subdirectories: `plugins/` `engines/` `workspaces/` `lab/` `data/` `keys/`;
- writes `~/.gitrader/gitrader.json` with a default configuration: one testnet venue `hyperliquid`, one paper account `paper` (starting balance 10000 USDC) and one bundled built-in engine `gitrader-core`;
- fills in any missing `accountId` per account (do not edit this by hand).

If your terminal is interactive it then asks you to set a PIN:

```text
Choose a PIN (6-12 digits, or a passphrase of 8-64 characters; longer is safer):
Repeat the PIN:
```

Easy-to-guess PINs such as `000000` or `123456` need a second confirmation: the terminal asks "use it anyway? (y/N)", and the web page shows "This PIN is easy to guess" with a "Use it anyway" button. Both paths follow the same rule.

The PIN is the key to every human-presence action on this machine: unlocking the keystore, binding engines, resuming trading, relaxing risk limits, issuing agent keys, requesting a fresh link for a running instance. It never reaches logs or the ledger, and it cannot be passed as a command-line argument. For what happens if you forget it, see [10-troubleshooting](10-常见问题.md).

In non-interactive environments (CI, scripts, the portable package's `start.cmd`) `init` does not ask for a PIN; `--no-pin` skips it explicitly (that flag is not listed in the `gitrader help` text). Afterwards run `gitrader serve` and set the PIN in the browser through the link the terminal prints, or run `gitrader init` again in an interactive terminal.

### Optional: add a watch account first

Want to see the positions of a real address first? Add a **read-only watch account**: it needs only a public address, no key, and it can never trade.

```text
gitrader accounts watch <address> --network testnet
```

After `gitrader serve` is up, an AI you connect (section 9) can read the positions and balances of that address with the `account` tool. `--network` defaults to `mainnet`: a watch account reads public data on its own network, whatever network the hyperliquid venue in `venues` is connected to, so you can keep trading on testnet and still watch a mainnet address (such a cross-network read covers the main dex only, so positions on builder dexes are not shown; with `gitrader serve --offline` there is no data connection, so it cannot be read); details in [02-configuration](02-配置参考.md).

## 2. Start the kernel and the workbench

```text
gitrader serve
```

The terminal prints something like:

```text
Gitrader <version> is running on 127.0.0.1:47900
Open the workbench (link valid for 2 minutes, one use):
  http://127.0.0.1:47900/?launch=...
Press Enter in this terminal for a fresh link. Press Ctrl+C to stop.
```

Key points:

- **The service binds `127.0.0.1` only**; other machines on the LAN cannot reach it. That is by design.
- The port defaults to the first free port from 47900 upward, skipping a list of common ports; pin it with `gitrader serve --port 48080`.
- The `launch` token in the link is **single-use and valid for 120 seconds**. Reloading the page or reopening an old link invalidates it — that is not a fault. Press Enter in the terminal for a new link, or run `gitrader open --print` in another terminal (requires PIN).
- To skip market data (pure offline inspection) use `gitrader serve --offline`, equivalent to the environment variable `GITRADER_OFFLINE=1`. The market panels are then empty; accounts, ledger, plugins and strategy files work as usual.
- Only one instance may run per home directory; starting a second one fails immediately and reports the port and pid of the running instance.
- Session expired (the page says you are logged out, or reloading no longer gets you in): run `gitrader open` in a terminal (requires PIN) for a fresh link.
- Stop the service with `gitrader stop`: it asks the service to shut down cleanly and only force-ends it if that does not work in time, so you never hunt for a process id. Stopping does not cancel orders or close positions: existing positions and resting orders stay where they are on the venue, but while the service is down this machine no longer watches the market or applies risk checks.

## 3. Open the workbench

Click the link above in a browser. The workbench shows three blocks plus a status bar by default: positions and PnL, agent activity and pending approvals, risk state. It is a paper account by default and sends nothing to a venue.

## 4. Check runtime state

In another terminal:

```text
gitrader status
```

It prints: version and pid, trading state (`ACTIVE` / `REDUCING` / `HALTED`), risk-policy version and integrity, ledger sequence and entry count, the account list (with `mode` and network), venue connection state, connector / engine / plugin counts, whether a PIN is set, and whether the keystore is unlocked. Add `--json` for machine-readable output.

When the service is not running or not initialised, it states the current state and the next command (`gitrader serve --detach` / `gitrader init`) and still exits 0; with `--json` read `running` / `state` / `next`. It exits non-zero only when the state cannot be determined (for example the data directory is unreadable).

## 5. Drop in a strategy

A strategy is a single file in a folder. The folder for the built-in engine is fixed:

```text
~/.gitrader/engines/gitrader-core/strategies/
```

The installed package ships examples with it (**not loaded by default**): `gitrader examples list` shows them, and `gitrader examples copy grid` copies one into the folder above; the portable bundle keeps them in `app/cli/examples/` too (copy from there if you prefer no command).

- start from a blank file: `gitrader examples copy template` (interface only, no trading logic);
- to see complete working examples: the ten or so files `gitrader examples list` prints cover grid, DCA, martingale, trend, dual moving average, breakout, momentum, RSI and supertrend;
- running from the source tree (developers): `packages/engine-core/strategy-template/strategy.ts` and `packages/engine-core/examples/strategies/` hold the same files.

After copying, change the file's `id` (lowercase letters, digits and hyphens, 2–40 characters, unique within the folder) and `name`; do not keep the example's `id`. The engine validates and hot-reloads the file within about a second — no service restart needed. Invalid files produce a readable error; fix it, save, and look again.

## 6. Bind the engine to the paper account

Binding is a write action, so you need a local session first. Log in once:

```text
gitrader session login
```

It asks for the "boot token": press Enter in the terminal where `gitrader serve` is running to get a fresh one, and paste it in. If the service was started in the background with `serve --detach` there is no such terminal: run `gitrader open --print` (requires PIN); it prints a link like `http://127.0.0.1:<port>/?launch=<token>`, and you paste only the part after `launch=`. One login per service session is enough; after a service restart you log in again. Then bind:

```text
gitrader engines bind gitrader-core
```

This asks for your PIN. Without `--account` it binds the **paper account**, and the kernel signs a paper-tier mandate for the binding; live accounts do not go through this path (see [05-live-and-risk](05-实盘与风控.md)). Make sure the service is running first — both `engines` subcommands need a live instance:

```text
gitrader engines list
```

Each output line looks like `id  state  transport  gep:<state>  bound:<account>`.

## 7. Run it on paper

Start the strategy from the workbench, or let a connected agent call `start_strategy` from the `engines` tool set (on a paper account this is an L1 action and needs no per-order approval). Use `params` keys declared by the strategy itself; out-of-range values or undeclared keys are rejected rather than silently clamped.

Once it is running, check these three places:

1. "Agent activity and pending approvals" in the workbench — who changed what, when, and why;
2. "Positions and PnL" — paper fills and unrealised PnL;
3. the ledger:

```text
gitrader ledger verify
```

It should print `Ledger OK: <n> entries, seq 0..<m>, ... checkpoints, head <hash>`. Anything that does not match reports the entry number where the chain breaks and exits with code 2.

## 8. Definition of done

After this section you should be able to answer "yes" to all of these:

- `gitrader status` says the service is running, trading state is `ACTIVE`, a PIN is set and the keystore state is normal;
- the workbench shows the three blocks with no red alerts;
- `~/.gitrader/engines/gitrader-core/strategies/` contains your own strategy file, and the engine list shows the paper account after `bound:`;
- the paper account has recorded at least one fill and the ledger entry count is growing;
- `gitrader ledger verify` passes.

## 9. Connect your agent

Let an AI (Cursor, Claude Code, Codex, Hermes and so on) use Gitrader on this machine through MCP. Four steps; keep the order.

**Step 1: create a key for it.** The key decides what it can do; start with the smallest tier. The token goes into a file and is never shown on screen:

```text
gitrader keys new agent <name> --host <host> --preset starter --token-file <token file>
```

It asks for your PIN. `<host>` is only a label (claude-code / codex / hermes / unigit; for Cursor or any other host choose claude-code); `--preset starter` is the confirm tier: every new position needs your approval, and it is limited to small hyperliquid BTC / ETH orders. The paper pass-through tier (`--tier paper`) is different: the agent's orders on the paper account fill immediately without waiting for your approval; use `--preset starter` if you want every order to pass through you. To let it look but not trade, replace `--preset starter` with `--tier read_only`, and you can add `--accounts <watch account alias>` to confine it to the watch account.

**Step 2: generate the host config snippet.**

```text
gitrader mcp snippet cursor --token-file <token file>
```

What it prints is an `mcpServers` block in which the token appears only as a file path, never in plain text. Cursor keeps it as `.cursor/mcp.json` in the project (use `~/.cursor/mcp.json` to share it across projects); any other host that understands `mcpServers` (Cline, Windsurf, Claude Desktop and so on) uses `generic` and merges the output into its `mcpServers`. Claude Code, Codex, Hermes and UNIGIT each have their own format: replace `cursor` with the host name. The end of the snippet says how many tools this key sees; trust the number in the output.

**Step 3: verify.** After restarting the host, look on the host side: in Cursor, Settings → MCP shows a green light on the `gitrader` server; for Claude Code use `claude mcp list`, for Codex `codex mcp list`. You can also run the `--check` command printed at the end of the snippet: it connects to the kernel and prints the key, its tier and the tool count, and being able to list the tools is what counts as connected.

**Step 4: install the onboarding skill.** It teaches the AI how to use these tools:

```text
gitrader skill install claude-code
```

Claude Code gets it in the current project's `.claude/skills/` (add `--global` for your user directory); `gitrader skill install codex` installs to the user-level `$CODEX_HOME/skills` (`~/.codex/skills` when unset) and writes nothing into the current directory.
