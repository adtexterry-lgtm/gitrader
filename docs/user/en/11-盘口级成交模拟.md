# Book-level fill simulation

A candle-level backtest fills at the next bar's open and charges a fixed number of basis points. It cannot answer two questions: **can this order actually get filled at that price**, and **how much size is left in that level after mine**. Book-level simulation takes every level's resting size seriously: size consumed is gone, and two orders in the same millisecond cannot both eat the same size.

This page covers how to prepare the data, how to read the fill report, and which conclusions you must **not** draw from it.

## 1. What it is and what it is not

| It is | It is not |
|---|---|
| A deterministic matching core: same records plus same command sequence gives the same fill report, byte for byte | A stand-in for an exchange: real queueing, hidden orders and exchange-side risk controls are not modelled |
| A standalone library (`@gitrader/sim-book`), no third-party dependencies, no network, never reads the system clock | A built-in path: how the engine wires it in is controlled by the backtest `fillMode` parameter. **If your build has no such parameter, the wiring has not shipped with it** |
| Fill flow plus fees only | Funding, liquidation and margin interest: those belong to position accounting, one layer up |

**Its input is a book, not candles.** Without book or tick data do not force this layer: fall back to candle-level simulation and state the fill assumption in your report.

## 2. Data format: one JSON record per line

Prices and sizes are **decimal text**. JSON numbers and exponent forms such as `1e-8` are rejected. `ts` must be non-decreasing across the stream; `seq` is optional, but once present every record must carry it and it must be non-decreasing.

```jsonl
{"type":"book_snapshot","ts":1000,"seq":1,"instrument":"BTCUSDT","bids":[["100.5","2"],["100","3"]],"asks":[["101","1.5"]]}
{"type":"book_delta","ts":1001,"seq":2,"instrument":"BTCUSDT","side":"ask","action":"add","price":"101.5","size":"0.5"}
{"type":"trade","ts":1002,"seq":3,"instrument":"BTCUSDT","price":"101","size":"0.25","aggressor":"buy","tradeId":"t-1"}
```

| Record | Required | Rules |
|---|---|---|
| `book_snapshot` | `ts`, `instrument`, `bids`, `asks` | Replaces the whole book: bids strictly descending, asks strictly ascending, no duplicate level, best bid below best ask |
| `book_delta` | `ts`, `instrument`, `side`, `action` | `add` / `update` need `price` and `size`; `delete` needs `price` only; `clear` needs neither |
| `trade` | `ts`, `instrument`, `price`, `size` | `aggressor` is `buy` / `sell` / `unknown`; it decides which side's resting size is consumed |

Files ending in `.gz` are compressed and decompressed automatically. **Validate before you match.** The validator replays the whole stream through a book, so it also catches data that is structurally valid but semantically impossible, such as a delta hitting a level that does not exist.

```ts
import { validateJsonl, readJsonlText } from '@gitrader/sim-book'

const result = validateJsonl(readJsonlText('book.jsonl.gz'))
if (!result.ok) console.error(result.errors)   // [{ line, code, message, field? }, ...]
```

Coverage: JSON syntax, record type, field types, decimal syntax, positive sizes, level ordering and duplicates, crossed books, monotonic `ts`, consistent and monotonic `seq`. For structure only, pass `validateJsonl(text, { strictBook: false })`.

## 3. Submitting orders

```ts
import { SimBook } from '@gitrader/sim-book'

const sim = new SimBook({ instrument: 'BTCUSDT' })
sim.apply({ type: 'book_snapshot', ts: 1, instrument: 'BTCUSDT', bids: [['100', '5']], asks: [['101', '5']] })
const r = sim.submit({ id: 'o-1', side: 'buy', type: 'market', qty: '1.5' }, 2)
// r.status === 'filled'; r.fills[0] === { price: '101', qty: '1.5', liquidity: 'taker' }
```

Order types: `market`, `limit`, `stop_market`, `stop_limit`. Time in force: `gtc`, `ioc`, `fok`. Modifiers: `postOnly`, `reduceOnly`.

| Form | Rule |
|---|---|
| Market | Walks the opposite side level by level; any remainder **is not rested** (`reason: insufficient_liquidity`); no fill at all means rejection |
| Limit | Fills only when the level crosses, price taken from the level (never worse than your limit); remainder rests and can be cancelled |
| post-only | Rejected outright if it would take liquidity; only constrains entry, an order already resting still fills |
| IOC / FOK | Fill what is possible / fill only if the whole size is available; remainder is void, and FOK consumes no liquidity |
| Stop / stop-limit | Converts to market / limit once the last trade price crosses the trigger; otherwise rests until triggered |
| Reduce-only | Size is clipped to the position passed in (noted in `notes`); rejected when there is nothing to reduce or the side matches the position |

## 4. Can a resting order fill? Three assumptions

The fill price is always **your own limit** (maker). The modes differ only in whether a given trade counts for your order:

| Mode (`fillModel`) | Trade at your price | Trade through your price | Implied assumption |
|---|---|---|---|
| strictest mode | No fill | Fill, size = min(remaining, trade size) | A print through the price means the level was swept; an at-price print may be absorbed by the queue ahead |
| `queue` | Subtract the displayed size at join time as the queue ahead, fill once it is exhausted | Queue ahead resets, then fill | Displayed size equals the queue ahead, hidden size ignored, queue ahead only shrinks |
| `optimistic` (default) | Fill | Fill | Always first in line, equivalent to fill-on-touch |

The queue position is recorded once, when the order **arrives at the venue**, using the displayed size of that level (re-recorded after a price change). With several of your orders at the same price, each estimates the queue ahead from the displayed size, which is pessimistic. The literal value of the strictest mode is quoted in the package README; the user-docs copy filter rejects that English word, so this page describes the behaviour only.

## 5. Latency: commands match against the book at arrival time

`latency` sets a fixed delay per submit / amend / cancel (milliseconds) plus optional deterministic jitter (fixed seed gives a fixed sequence). One rule: a command reaches the venue at "send time + delay" and is matched **against the book at arrival**, not at send time.

```ts
const sim = new SimBook({ instrument: 'BTCUSDT', latency: { baseMs: 5, insertMs: 20, updateMs: 5, cancelMs: 10, jitterMs: 8, seed: 42 } })
const ack = sim.submit({ id: 'o-1', side: 'buy', type: 'market', qty: '1' }, 1_000)
ack.notes            // states the in-flight delay and the expected arrival time
sim.arrivalOf('o-1') // arrival timestamp
```

- An in-flight order does not take part in matching and consumes no liquidity.
- A cancel in flight does not protect the order: market data can still fill it. That is the point of the delay.
- On an exact tie with a record's `ts`, matching uses the book **after** that record (the later state within the same millisecond, the pessimistic choice).
- The default is zero delay: commands arrive at send time.

## 6. Fees

`fees` sets maker and taker rates as decimal text (negative values are rebates), with per-currency overrides. Fee = fill price times filled size times rate, exact at 18 decimal places.

```ts
const sim = new SimBook({ instrument: 'BTCUSDT', currency: 'USDT',
  fees: { maker: '0.0002', taker: '0.0005', overrides: { USDT: { maker: '0', taker: '0.0004' } } } })
sim.feesOf('o-1')    // fees for one order
sim.feeSummary()     // running totals, maker and taker separately
```

## 7. Three things to remember when reading results

1. **Good fills do not mean a good strategy.** This layer can only be as meaningful as the book you feed it. Record the source, the time range, whether gaps were filled, and whether the stream is complete.
2. **`optimistic` is the default and the most favourable assumption.** Re-run with `queue` or the strictest mode; the difference between the two runs is your queueing cost.
3. **Do not pretend you have a book when you do not.** Conclusions from this layer hold only when tick or book data exists and has passed validation.
