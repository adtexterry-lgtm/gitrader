# Live trading and risk

This page covers what you need to know before **touching real money**. A default install is testnet plus a paper account; going live is a series of actions that require you to be present, not a switch you flip.

## 1. Support boundary

| Item | Current state |
|---|---|
| Trading venue | The only bundled trading connector is Hyperliquid (`venues[].id = "hyperliquid"`); other venues are read-only market data |
| Network | `testnet` by default. Mainnet is off by default; a mainnet API wallet is required before you switch |
| Funds | **Not custodial.** Keys stay on this machine and trading uses an API wallet that can trade but cannot withdraw |
| Risk-gate coverage | Orders sent from the workbench / an agent / an engine in mode A pass through the gate; **orders an external engine places by connecting to the venue itself do not**, and the ledger marks them `engine-reported` with a note in the UI |
| Status | The product itself is M1 work in progress. A connector that has not been verified against the real network must not be used for live trading |

In one sentence: **Gitrader does not trade on your behalf and commits to no particular outcome; what it gives you is a gate of your own design, in front of every order.**

## 2. Three gates to pass

Live trading is not "one" switch but three layers, each needing a human:

### Layer one: the wallet (trade only, no withdrawals)

```text
gitrader keys new wallet main-key --network mainnet --days 180
gitrader keys import my-api-wallet --network mainnet
gitrader keys list
```

- `new wallet` generates on this machine and prints only the address; the private key never leaves the keystore. You then run one `approveAgent` authorisation for that address from your main wallet, **in your own browser wallet**.
- `import` reads from hidden terminal input (a private key is never a command-line argument, because argv ends up in shell history and process listings).
- Rotate before a wallet expires: `keys.walletExpiryWarnDays` (default 14 days) starts reminding you in advance.

### Layer two: the mandate (what an agent may do)

Each connected agent gets one key, in one of four tiers:

| Tier | What it may do |
|---|---|
| `read_only` | Read-only + research (cannot trade): can read markets and accounts, write notes, create experiments and submit backtests; cannot place orders, cannot start or stop strategies (except those it started itself) |
| `paper` | Paper orders / start and stop paper strategies (can only stop its own instances; stopping others' requires confirm tier or higher) |
| `confirm` | Propose, and wait for your approval |
| `auto_limited` | Execute automatically within the mandate's limits; **cannot be the default tier** |

```text
gitrader keys new agent "my-agent" --host claude-code --tier confirm \
  --accounts main-live --max-order 500 --max-daily 2000 --max-daily-loss 200
```

When issuing an L3 / L4 mandate the protocol insists on account / venue / instrument allowlists, limits, daily loss, heartbeat and expiry. A missing item is not "permissive": **the gate treats the mandate as incomplete and turns the action into a proposal** (`MANDATE_INCOMPLETE`). The token is shown once, at creation.

### Layer three: the risk gate (every single order)

The gate lives **in the kernel** and is the only checkpoint. It evaluates all 13 phases in a fixed order without short-circuiting:

```text
SYS system health (strategy signature, stale account view, missing mark price)
KILL kill switch   STATE scope state (REDUCING / HALTED)
MANDATE mandate   LLM model origin   ALLOWLIST allowlist
CONST leverage / order notional / slippage    EXPOSURE per-instrument and total exposure, position count, daily notional
BUYING_POWER buying power    LOSS daily loss    RATE rate and duplicate intents
PROTECTOR protectors    APPROVAL human approval required
```

There are only three verdicts:

| Verdict | Meaning | Consequence |
|---|---|---|
| `ALLOW` | Everything passed | Sent as-is |
| `LIMIT` | Something `limit`-class hit (order notional too large, say) | Sent with the adjusted quantity; the ticket is bound to the adjusted content |
| `BLOCK` | A `deny`, or a `review` (needs human approval) | **Nothing is sent**; `review` becomes a proposal waiting for you |

Hard rules:

- **Risk-reducing actions always get through**: `reduce` (decrease only) and `cancel` are allowed even when `SYS` / `KILL` / `STATE` are abnormal, are logged as `warn`, and are exempt from daily order counts and weight budgets. A halt must never leave you unable to close a position.
- **Stale market data = no order**: older than `risk.failClosed.stalePriceMs` (default 5000 ms), or no price at all, means denial.
- **No live entries from a model**: `denyLlmLiveEntries` defaults to `true`. It can be written in the configuration file, but `false` there is ignored — it can only be turned off in the workbench with your PIN.
- **Dry runs**: a `dryRun` verdict does not tick the ledger, issue a ticket, reserve capacity or count towards circuit breakers. To find out whether something would be blocked, dry-run it.
- **Tickets**: each submission to a venue corresponds to exactly one verdict; without a ticket, or with an expired one, the kernel neither signs nor sends (`GATE_TICKET_INVALID` / `GATE_TICKET_EXPIRED`).

## 3. Pre-launch checklist

Tick every line; if one is missing, do not start:

- [ ] `gitrader keys list` shows a mainnet API wallet with state `active` and an expiry date far enough out;
- [ ] that address has been `approveAgent`-ed from the main wallet and does **not** have withdrawal permission;
- [ ] the live account in `accounts[]` has `mode: "live"`, `environment: "mainnet"`, a `signerRef` pointing at that wallet, and `accounts[].owner.address` set to the main account's public address;
- [ ] the `environment` of `hyperliquid` in `venues[]` is `mainnet` (switching network in the workbench rewrites this line and asks for a restart);
- [ ] `risk.preset` is the tier you want (default `p-lev3-o2000-d3`: <= 3x / per order <= 2,000 / 3% daily loss);
- [ ] `risk.denyLlmLiveEntries` is `true`;
- [ ] `risk.failClosed`'s `stalePriceMs` matches your market-data frequency;
- [ ] `plugins.developerMode` is `false` and no unsigned plugin is running;
- [ ] `embed.allowedOrigins` is empty (unless you deliberately embed the workbench in another page);
- [ ] `gitrader ledger verify` passes;
- [ ] the limits in the output of `gitrader risk policy export` are what you think they are;
- [ ] this strategy has been through the paper (`paper`) and shadow (`shadow`) stages, with `holdoutWindow` and `assumptions` recorded in the experiment.

## 4. Start-up and escalation path

Recommended order; do not skip steps:

1. **Paper** (`mode: "paper"`): simulated matching on real market data, to see whether behaviour matches your expectation;
2. **Shadow** (`mode: "shadow"`): currently the same simulated matching path as paper, used to keep a record of "what would have happened with live parameters";
3. **Live, small** (experiment stage `live_small`, trial-run semantics, 30 days): mandate limits squeezed to the minimum, starting at `--tier confirm`;
4. **Live** (`live`): only after 3 is stable.

Every stage promotion needs an evidence pack; moving to `live_small` / `live` needs you to review it in the workbench and enter your PIN (`lab.stage`), and an agent's request for it is always refused.

## 5. While it is running

- One `gitrader status` line gives you everything: trading state, risk-policy version and integrity, ledger sequence, account and venue connections, engine and plugin counts, PIN and keystore state. Add `--json` for machine reading.
- Trading state has three values:

  | State | Meaning | What still works |
  |---|---|---|
  | `ACTIVE` | Normal | Everything |
  | `REDUCING` | Reduce only | Closing, cancelling; no new exposure |
  | `HALTED` | Halted (latched) | Closing, cancelling; every exposure-increasing action is denied |

- Common reasons for entering `REDUCING` / `HALTED`: you triggered a takeover, a protector fired, an agent heartbeat timed out (dead-man switch), startup reconciliation failed, or risk-policy signature verification failed.
- **Do not leave the `gitrader serve` terminal minimised forever**: it prints warnings about restarts, denials and connection changes. Warnings also appear in the `warnings` section of `status`.

## 6. Takeover and protectors

**Takeover** (a self-protection action; both humans and agents can trigger it, no PIN needed — speed beats ceremony):

- stop opening new positions;
- cancel resting orders (by default reduce-only stop-loss / take-profit protective orders are kept; in the reply, `cancelled` is how many resting orders were cancelled and `keptProtective` how many protective orders were kept, and an agent reports from those fields);
- close everything.

Cancels and closes issued by a takeover go through the gate as `system`, are exempt from cancel rate limits, and are not blocked by rules that the takeover itself just triggered.

**Protectors** (evaluated in the `PROTECTOR` phase of the gate; they can only deny or tighten):

| Kind | Effect |
|---|---|
| `cooldown` | No new entry for some seconds after an entry |
| `stoploss_guard` | Too many stop-outs inside the window -> pause for some minutes |
| `drawdown_pause` | Drawdown beyond the limit inside the window -> pause |
| `low_profit_lock` | Return too low inside the window -> lock |
| `max_consecutive_failures` | N consecutive failures -> pause |
| `plugin` | A verdict supplied by a plugin (treated as `PROTECTOR_UNAVAILABLE` when the plugin is unavailable) |

**Layer-0 kill switch**: if a file named `HALT` appears in the data directory (`GITRADER_HOME`), the kernel latches a halt immediately and attempts to cancel orders. This is the exit for "I need to stop it with no UI at hand".

- Latched: deleting the file does **not** resume trading.
- Resuming only accepts a `resume` from you in person (PIN); while the file is still there the resume is refused with a reminder to delete it first.
- After it fires, an agent's available actions are reduce / cancel / arm protections only. It has no recovery tools.

## 7. Handling incidents

| Symptom | First move | Command / location |
|---|---|---|
| An order was denied and you do not know why | Look at denial counts, then replay that order's verdict | `gitrader risk stats`, `gitrader risk replay <precheckId>` |
| You suspect the strategy file was swapped / the signature is wrong | Verify the signature and replay | `gitrader risk verify`, `gitrader risk verify <precheckId>` |
| You want to confirm what the limits really are | Export the signed policy and locally approved parameters | `gitrader risk policy export` |
| You need a temporary loosening (a stop-out blocked by limits, say) | Human PIN; **default 4 hours** (the UI offers 1 / 4 / 12 / 24 hours), at most 24 hours, reclaimed automatically | Workbench "Temporary relax" with PIN; or `gitrader risk relax @patch.json [--hours N]` (needs PIN) |
| A limit must change permanently | A separate entry that is never reclaimed automatically; in the UI choose "permanent change" in the confirmation step; needs PIN | Workbench confirmation; or `gitrader risk relax @patch.json --permanent` (needs PIN) |
| An agent must lose its access right now | Revoke its agent key: it can no longer place orders and pending approvals are voided; existing positions and resting orders are not handled automatically | Workbench: Settings → Keys → Agent keys → Revoke (needs PIN); or in your own terminal `gitrader keys revoke agent <name>` (needs PIN) |
| The ledger does not check out | Recompute the hash chain and see which entry breaks | `gitrader ledger verify` |
| You want to stop everything | The three-step takeover, or drop a `HALT` file | Workbench / home directory |
| The paper account got into a mess | Reset it explicitly (needs PIN, service must be running) | `gitrader paper reset --account paper` |
| An engine is running wild | Stop the strategy instance first, then bind back to paper | `gitrader engines list` / `engines bind` |

The `risk relax` patch is JSON: a temporary loosening can only change limits inside `{"limits": {...}}`; changing anything else (for example `{"maxDriftBps": 30}`) needs `--permanent`. `--hours N` must be above 0 and at most 24. A loosening requires the PIN throughout and is written to the ledger; the automatic reclaim at expiry is written too.

## 8. What we do not do

- No withdrawals, no transfers, no custody: any action that needs a user signature (transfer, withdrawal, `approveAgent`) is refused by the kernel, except through the human-PIN flow.
- No return claims, no trading advice, no strategies or data supplied.
- We do not claim to stop malicious code running as the same system user — see the T-C tier in [09-security](09-安全.md).
- Orders an external engine places by connecting to the venue itself are not counted as protected traffic.
