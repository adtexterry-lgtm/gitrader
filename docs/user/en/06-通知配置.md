# Notification configuration

Notifications in Gitrader are **not a built-in channel but a plugin**: a plugin that declares a `notify_send` tool is a channel. Adding a channel means installing a plugin; if you do not install one there is none — there is no second notification code path in the kernel.

## 1. The contract: how the kernel calls a plugin

The kernel wraps each notification as a `notice` and, together with the `params` from your configuration, sends it to the plugin's `notify_send` as one `tool.call`:

```json
{
  "notice": {
    "key": "9f2c1a7d… (sha256 hex, 64 characters)",
    "level": "warn",
    "title": "risk.denials",
    "lines": ["ts: 1760000000000", "accountId: acct_fixture", "ruleHits[0].actual: 1200", "ruleHits[0].ruleId: budget"],
    "ts": 1760000000000,
    "topic": "risk.denials"
  },
  "params": { "chatId": "123" }
}
```

- `level` is only `info` / `warn` / `critical`.
- `key` is a sha256 the kernel derives from the content and uses for deduplication; the same channel accepts the same `key` once per window. Do not treat it as a business id. Two exceptions: the `notify test` diagnostic and the rate-limit merge summary use `test:…` / `summary:…` keys and a fixed short title, and their lines carry no `ts` line.
- `title` is the topic name (`risk.denials`, `takeover.failed`, ...); `lines` are `path: value` facts, with `ts` always first.
- The return value is one of two shapes: `{"ok": true, "ref": "<platform message id, optional>"}`, or `{"ok": false, "reason": "<short sentence, no secrets>", "retryable": true|false}`.
- Timeout: 10 seconds by default in the kernel; the plugin's own network timeout is <= 8 seconds, and a timeout returns `retryable: true`.
- **Queues, retries and re-send** (outlet behaviour; plugins need not care):
  - Each channel has its own queue and timeout budget, so a hung channel (for example a webhook whose far end never answers) does not slow the other channels; `critical` notices (takeover, protector triggers, REDUCING / HALTED state changes, ...) go in front of the info / warn notices already queued on the same channel (the one being sent is not interrupted). The dedupe window, the per-minute merge and the 1000-item cap are all counted per channel.
  - One notice makes at most 3 HTTP attempts on one channel across the whole chain: the channel plugin retries by itself (webhook: first retry no earlier than 250 ms, then the gap doubles with jitter, 8-second total budget; Slack / Telegram / Discord / WeCom: 2-3 HTTP attempts each) and only hands the failure back to the kernel once it has used them up, with `exhausted: true`, so the kernel does not stack another retry; the kernel does not re-send after a full call timeout (10 seconds) either.
  - Dedupe key: every request of the webhook plugin carries the header `X-Gitrader-Notice-Key: <notice.key>`; all retries of one notice and the re-send after a restart carry exactly the same value, so the receiver can deduplicate (when a long body is sent in chunks, the key of chunk 2 onwards gets `#<chunk number>` appended).
  - Durable re-send: warn / critical notices that were routed to a channel but not yet confirmed delivered are recorded in `GITRADER_HOME/notify-outbox.jsonl`; after a kernel crash and restart, each channel that did not get them is sent them once more within a 10-minute validity window (same dedupe key), and channels that already got them are not re-sent. `notify test` diagnostics, rate-limit merge summaries and info notices are not written to disk. Notices are still not written to the ledger.
- A plugin **does not rewrite** the content of `title` and `lines`; it only escapes / chunks / formats for the platform.
- If the return value carries a field named `privateKey`, `secret`, `password` or similar, or echoes a declared secret value (raw, JSON-escaped, base64 or URL-encoded), the whole frame is rejected with `SECRET_FIELD_REJECTED`.

## 2. How secrets are supplied

| Layer | Practice |
|---|---|
| Manifest | `secrets: ["TELEGRAM_BOT_TOKEN"]` — **names only, never values** |
| Plugin code | Reads only from `process.env.TELEGRAM_BOT_TOKEN`; never prints, echoes or returns it |
| Tool input | **Must not** carry secrets. The protocol rejects the install at manifest validation: `TOOL_SOLICITS_SECRET` |
| Transport | Secrets never enter JSON-RPC; logs and error messages are redacted |

The handle convention matches remote engine tokens: the configuration file holds only the variable name (`env:VARIABLE_NAME`) and the value lives in the process environment. **Do not paste secrets into `gitrader-plugin.json`** — the manifest enters hashes, signatures and the ledger.

A secret value must be at least 8 characters. Shorter values are not compared against plugin reply frames at all; the only trace is a startup warning, `short secret excluded from frame scan`, which means the kernel cannot see that value being echoed. Use a separate random value per channel.

### 2.1 Only one shape is accepted

A value in `plugins.secrets` must be an `env:<VARIABLE_NAME>` handle, **not** the secret itself — configuration validation accepts nothing else and reports `plugins.secrets requires environment names mapped to env:VAR handles`. The secret itself lives in the environment of **the process that starts the kernel**:

```json
{
  "plugins": {
    "secrets": { "connector.gitrader.notify-webhook": { "WEBHOOK_SECRET": "env:WEBHOOK_SECRET" } }
  }
}
```

```text
export WEBHOOK_SECRET='<random string, at least 8 characters>'   # Windows PowerShell: $env:WEBHOOK_SECRET = '<...>'
gitrader serve                                                    # start it from the same shell so the child process inherits it
```

Three details:

1. **Only names declared by the manifest are injected.** A name in `plugins.secrets` that the manifest does not list under `secrets[]` is ignored with a warning (`ignored undeclared secret name …`) and never handed to the plugin.
2. **Missing handle or unset variable**: the plugin fails to start with `missing secret handle: WEBHOOK_SECRET`; test results and outlet logs show that line only, never the value. Fix `plugins.secrets` and the process environment, then retry.
3. **Do not put secrets in `notify.channels[].params` — not even an `env:` handle.** The kernel treats the field names `privateKey` / `secret` / `apiSecret` / `mnemonic` / `seed` / `passphrase` / `pin` / `password` (case-insensitive, ignoring `_` and `-`) as credentials, so configuration validation fails and tells you to use `plugins.secrets`; `gitrader notify test` fails for the same reason. The webhook plugin README records `params.secret: "env:WEBHOOK_SECRET"` as a handle shape the plugin itself understands, but on a notification channel the configuration layer rejects it first (the README is pending a fix; see the work order). Channel secrets travel only through `plugins.secrets` plus the process environment.


## 3. The `notify` section

The fields follow the `notify` section of `packages/kernel/src/config.ts` (no `notify` section means nothing is sent):

```json
{
  "plugins": {
    "developerMode": false,
    "trustRoots": [],
    "secrets": { "connector.gitrader.notify-webhook": { "WEBHOOK_SECRET": "env:WEBHOOK_SECRET" } }
  },
  "notify": {
    "channels": [
      { "id": "main", "plugin": "connector.gitrader.notify-webhook", "minLevel": "warn", "params": { "url": "https://open.feishu.cn/open-apis/bot/v2/hook/…" } }
    ],
    "rules": [
      { "match": "takeover.*", "level": "critical", "channels": ["main"] }
    ],
    "rateLimit": { "perChannelPerMinute": 20, "dedupeWindowSec": 300 }
  }
}
```

| Field | Rule |
|---|---|
| `notify.channels` | Required array. An empty array sends nothing |
| `notify.channels[].id` | `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`, unique within one configuration; this is the id `notify test` takes |
| `notify.channels[].plugin` | Plugin id (lowercase, dots allowed); the plugin must be installed and enabled |
| `notify.channels[].minLevel` | `info` / `warn` / `critical`; notices below it are not delivered to this channel |
| `notify.channels[].params` | Object passed to the plugin unchanged. It **must not** contain a credential field name (`privateKey`, `secret`, `apiSecret`, `mnemonic`, `seed`, `passphrase`, `pin`, `password`, case-insensitive and ignoring `_` and `-`); validation fails and tells you to use `plugins.secrets` instead |
| `notify.rules[].match` | `*` (everything), an exact topic (`risk.denials`), or a prefix wildcard (`takeover.*`); the first match in order wins |
| `notify.rules[].level` | Level applied to matches; `takeover.failed` and `takeover.alert` stay critical regardless |
| `notify.rules[].channels` | Must name configured channel ids; a typo or an unknown id fails validation |
| `notify.rateLimit.perChannelPerMinute` | Positive integer, default 20; each channel gets a 60-second window starting at its first accepted notice and the overflow is merged into one summary |
| `notify.rateLimit.dedupeWindowSec` | Non-negative integer, default 300; the same channel sends the same `key` once per window. `0` disables dedupe (every takeover stage then sends its own notice) |

With no `rules`, every channel receives whatever passes its own `minLevel`; with `rules`, notices that match no rule take that same default path. Delivery follows the written order of `channels`, one notice at a time, never in parallel.

## 4. Recipes for the three channels

### 4.1 Telegram

| Item | Value |
|---|---|
| Manifest `permissions` | `net.fetch` |
| Manifest `net.hosts` | `api.telegram.org` |
| Manifest `secrets` | `TELEGRAM_BOT_TOKEN` |
| Required `params` | `chatId` (numeric or `@channelusername`) |
| Notes | The body is escaped as MarkdownV2; a single message is capped at 4096 characters, longer content is sent in order as line chunks; each chat has a minimum send interval and 429 responses are retried with backoff |

Get the bot token from @BotFather; it looks like `<digits>:<string>`. If nothing arrives, check in this order: the bot has been added to the target conversation, then the `chatId` has no wrong symbol, then the returned `reason`.

### 4.2 Email (SMTP)

| Item | Value |
|---|---|
| Manifest `permissions` | `net.fetch` |
| Manifest `net.hosts` | the email plugin in the repository declares `localhost` (a local relay); for an external SMTP server your manifest must name that host |
| Manifest `secrets` | `SMTP_PASSWORD` |
| `params` | `host`, `port`, `secure`, `user`, `from`, `to` (string or array, at most 50), `subjectPrefix` (optional) |

```json
{
  "params": {
    "host": "smtp.example.com",
    "port": 587,
    "secure": false,
    "user": "trader@example.com",
    "from": "trader@example.com",
    "to": ["trader@example.com"],
    "subjectPrefix": "[gitrader] "
  }
}
```

- Port 465 pairs with `secure: true` (implicit TLS); 587 pairs with `secure: false` (upgrade in place when the server offers STARTTLS). With no port set, the default is derived from `secure`.
- Session order: `EHLO` -> (optional `STARTTLS` + `EHLO` again) -> authentication if `user` is set -> `MAIL FROM` -> `RCPT TO` x n -> `DATA` -> `QUIT`. If any recipient is refused the whole message is aborted, nothing is delivered.
- With `user` empty and no `SMTP_PASSWORD` you can use an unauthenticated local relay; if the server demands authentication and none is configured, the result is `retryable: false`.

### 4.3 Webhook

| Item | Value |
|---|---|
| Manifest `permissions` | `net.fetch` |
| Manifest `net.hosts` | the webhook plugin in the repository declares: `open.feishu.cn`, `oapi.dingtalk.com`, `qyapi.weixin.qq.com`, `hooks.slack.com`, `discord.com` |
| Manifest `secrets` | `WEBHOOK_SECRET` |
| `params` | `url` (required), `markdown` (optional; send Markdown or plain text); the signing key arrives through the declared environment handle and is **not** put in `params` |

- The dialect is detected from the URL: Feishu / DingTalk / WeCom / Slack / Discord / generic.
- Feishu and DingTalk signatures are HMAC-SHA256 + base64 (with the timestamp included); the plugin computes them, you do not.
- Vendor errors are translated into `retryable`: 429 / 5xx are retryable, 4xx parameter errors are not.
- For a generic webhook the host comes from your `url`, which the manifest's `net.hosts` cannot cover — add the host yourself when writing a manifest.

## 5. Install and enable

Taking a channel plugin directory `notify-demo/` as the example, run these in order (all of them are real subcommands):

```text
gitrader plugins check notify-demo            # validate manifest and hash; 0 = pass, 2 = rejected
gitrader plugins pin notify-demo              # re-pin after any file change (writes source.sha256)
gitrader plugins reload                       # notify the service if running, otherwise scan offline
gitrader plugins list                         # per plugin: ok / REJECTED, granted, pending, enabled
```

Enabling and granting (**stop the service first**; this entry point needs the local PIN):

```text
gitrader plugins grant connector.gitrader.notify-webhook net.fetch
```

For a zero-permission plugin, giving no permission names simply enables it. Grants take effect item by item and each one is written to the ledger.

## 6. Send a test message

First configure `notify.channels` and `plugins.secrets` as in section 3, and put the channel's target parameters in `params`. Secret values live only in the environment of the process that starts the kernel; the configuration stores an `env:VARIABLE_NAME` handle.

```text
gitrader notify test main
```

`main` is a channel id from the configuration. The command sends a fixed info test notice through the human-facing action `notify.test({ channelId })` and prints the result per channel: exit code 0 on success, 1 on failure. It bypasses dedupe, rate limits and `minLevel`, so "the test works but real events never arrive" is usually a routing or level problem, not a channel problem (see section 10). It works with an offline local kernel or a running service; an enabled but not yet started plugin is launched on first call.

Only the notification outlet and this test entry point may call `notify_send`. A generic `plugins call` and an agent call are both refused, so neither can send a custom body.

## 7. Three hard rules

These are implemented inside the kernel and cannot be changed by configuration. Know them before writing a channel plugin or routing rules:

1. **Free text never enters the body.** The template reads only whitelisted fields (`accountId`, `instrumentId`, `orderId`, `takeoverId`, `ruleId`, `code`, `state`, `price`, `quantity`, `notional`, `limit`, `actual`, and so on) and descends only into groups such as `scope`, `ruleHits`, `precheck`, `intent`, `error`. A string that is not fact-shaped (1–64 characters of `A-Za-z0-9_.:/-`) is written as `[text omitted]`, and every other key is skipped. Proposal reasons, takeover reasons, notes and strategy descriptions never reach a notification — read the ledger for the record.
2. **One notice per takeover.** The notice key is merged by takeoverId: requested / applied / completed and the following `trading_state.changed` for the same scope share one key, so a channel sends a single notice per dedupe window; failed and alert get their own key and are always critical. The window is 300 seconds by default (`notify.rateLimit.dedupeWindowSec`), and a failed delivery inside the window still consumes the slot.
3. **Short secret values are not scanned.** A declared value shorter than 8 characters is never compared against plugin reply frames; you only get a startup warning. That gives up the "echo means reject" protection, so use random values of at least 8 characters instead of something like `123456` or `ok`.

The full contract, rate limits and metrics are in [the notification outlet](../notifications.md).

## 8. Current state (October 2026, this repository)

1. **Automatic forwarding is wired up.** The kernel subscribes to risk, takeover, protector, proposal, plugin-state and engine-health events, routes and deduplicates them through the notification outlet, applies rate limits, then calls the channel plugin. With no `notify` section, or with an empty `notify.channels`, nothing is sent. Takeovers are correlated by takeoverId: stage updates inside the dedupe window are not re-sent, and a failed stage sends one separate critical notice.
2. **Declared secrets are injected automatically.** When a plugin starts, only the names declared in the manifest's `secrets[]` are resolved, and their values are injected into that plugin process. A missing or unresolvable handle shows `missing secret handle: <NAME>` in the test result and the outlet log, never the value. Undeclared names are ignored with a warning.
3. **Failures are observable.** A single channel failure is retried at most once when `retryable` is set; `/api/metrics` exposes `notify_sent_total`, `notify_failed_total`, `notify_dropped_total`, `notify_deduplicated_total`, `notify_merged_total`, `notify_redacted_total` and `notify_retried_total`. Notifications themselves are not written to the ledger.

Notification bodies carry structured facts only; proposal reasons, takeover reasons, notes and strategy descriptions are not forwarded. The fake-connection mode used by test fixtures is for local verification only and needs no real credentials.

## 9. Three new channels: Discord, Slack, WeCom

Each channel is a pair of "library plus plugin", written the same way as the Telegram pair: the library lives in `packages/notify-<channel>` and the plugin in `packages/plugin-notify-<channel>` (a plugin cannot import workspace packages, so the plugin is an `.mjs` copy of the same logic).

| Channel | Library / plugin | Secret environment variable (the `secrets[]` name) | Outbound host | Per-message limit | Retry policy |
|---|---|---|---|---|---|
| Discord | `@gitrader/notify-discord` / `plugin-notify-discord` | `DISCORD_WEBHOOK_URL` | `discord.com` (also `discordapp.com` / `canary` / `ptb`) | 2000 characters, chunked by line | On 429 wait the official `retry_after` and retry once; if the wait exceeds 5 s or would break the budget, do not wait and return `retryable: true` |
| Slack | `@gitrader/notify-slack` / `plugin-notify-slack` | `SLACK_WEBHOOK_URL` | `hooks.slack.com` | 40000 characters, **over the limit is an error, not an extra message** | 408 / 429 / 5xx retryable (429 prefers `Retry-After`); other 4xx are not |
| WeCom | `@gitrader/notify-wecom` / `plugin-notify-wecom` | `WECOM_WEBHOOK_URL` | `qyapi.weixin.qq.com` | markdown 4096 **bytes** / text 2048 bytes (UTF-8; one Chinese character is 3 bytes) | `errcode 45009` (over 20 messages per minute) is retryable; `93000` (invalid key) is not |

Four rules:

1. **The webhook URL itself is the credential.** Slack and Discord put a token in the path; WeCom puts `key` in the query string. All three read it from the environment only (the configuration stores an `env:VARIABLE_NAME` handle), never print it, never write it to disk, and redact errors first, so neither the full URL nor the key ever appears in `reason`.
2. **Mentions cannot be forged.** Discord always sends `allowed_mentions.parse: []`, so `@everyone` in a body triggers nothing, and `wait=true` is what makes a message id available as `ref`. Slack escapes `&`, `<` and `>` into entities, so `<@U123>` or `<!channel>` cannot form. Escaping only; the body is never rewritten.
3. **One notice means one send action.** Slack returns an error above 40000 characters instead of splitting into two messages; Discord, bound by the platform's 2000-character limit, chunks by line **inside the same call**; WeCom chunks by bytes without cutting a code point.
4. **Levels and dedupe are unchanged**: `minLevel`, `dedupeWindowSec` and routing rules are configured as in section 3; a new channel does not alter kernel-side merging or rate limiting.

After installing, follow sections 5 and 6: inspect the manifest with `gitrader plugins list`, grant `net.fetch` with `plugins grant`, and send a test notice with `gitrader notify test <channel id>`.

**Verified versus unverified**: request shapes, status-code handling, chunking, escaping and redaction all have tests, and the reference is each package's own fake server (written independently from the official rules, importing no client code). None of the three has **ever sent a request to the real endpoint** (all tests are offline). The Discord README lists its unverified items one by one (the Markdown escape table, error-code to HTTP-status mapping, and so on); read it as written.

## 10. Troubleshooting table

| Return / symptom | Cause | What to do |
|---|---|---|
| `params.chatId` missing | No target parameter for the channel | Fill it in under `notify.channels[].params` |
| `missing secret handle: <NAME>` | The declared name has no handle, or the handle does not resolve | Add `plugins.secrets` and the matching process environment variable, then start the plugin |
| `unknown channel` | The id given to `notify test` is not in `notify.channels` | Compare `gitrader plugins list` with the configured `notify.channels[].id` |
| Configured, yet nothing arrives | `notify.channels` is empty, a channel `minLevel` is above the event level, or a rule points the event at another channel | Confirm the channel itself works with `gitrader notify test <id>`, then check the levels and routing in section 3 |
| No reason or note in the notice | Free text never enters the body (rule 1 in section 7) | Read the ledger; do not ask a plugin to "fill in" the body |
| Several notices for one takeover | `dedupeWindowSec` is 0, or the same event was routed to several channels | Restore a positive window; configure more channels when you really want several alerts, do not disable dedupe |
| `retryable: true` | Platform rate limit / 5xx / timeout | Retry; if it keeps failing look at the platform side |
| `retryable: false` + 4xx | Wrong parameter or target (chatId, recipient, webhook key) | Fix the configuration; do not retry |
| `insecure_url` | The webhook address is plaintext `http:` and the host is not loopback (`127.0.0.1` / `localhost` / `[::1]`) | Use `https:`; keep plaintext loopback addresses for local testing only |
| `SECRET_FIELD_REJECTED` | The plugin return value has a credential field name, or echoed a declared value | Fix the plugin: return only `{ ok, ref }` |
| `REJECTED n problem(s)` | Manifest non-compliant (permission enum, host, hash mismatch) | Fix line by line; then `plugins pin` |
| `MANDATE_LIMIT` | The plugin is not enabled, or the tool permission was not granted | `plugins grant <id> [perm]` |
| `PLUGIN_RESULT_INVALID` | The return value does not match the declared `output` | Fix the plugin's return value |

Titles and bodies come from kernel templates and a plugin only formats and sends them. Because notices quote structured facts only, they never reproduce free text from the ledger.
