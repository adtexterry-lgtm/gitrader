# Indicators: the ta-plus inventory and how it differs from engine-core

engine-core ships its own indicator set (`packages/engine-core/src/strategy/ta/`). ta-plus (`@gitrader/ta-plus`) adds the ones it does not have: fundamental ratios, risk and volatility measures, moving-average distance, window extremes, and several classic TA-Lib functions. The two packages **coexist**; ta-plus is not merged into engine-core.

This page answers three questions: what is in the package, where the overlapping names differ from engine-core, and when you can get a wrong number.

## 0. Using it in the installed product

ta-plus is a function library (`@gitrader/ta-plus`); it has **no command or tool action of its own**. In an installed `gitrader` the research tool is where indicators show up:

- Agent: the `factor_report` action of the MCP tool `research`; command line: `gitrader research factors --instrument hyperliquid:BTC --interval 1h --from <ms|ISO> --to <ms|ISO> --json` (or `--data <csv>` for a local candle file). It scores 157 rolling factors by IC / IR / quantile returns with a Newey-West (HAC) t value; the method is named in the summary (`tMethod`, `tLags`). The factor catalog is the bundled one, not ta-plus.
- To use an indicator from this page in your own strategy: strategy files must be self-contained (no `import`), so copy the function body from the ta-plus source into the file. The npm package does not ship the ta-plus source; take it from `packages/ta-plus/src/` in the repository.

## 1. Conventions (identical in both packages)

- Output is **the same length as the input**; positions that cannot be computed yet are `null`, never `0` and never `NaN`.
- **Causal**: item i uses data up to i only. Truncating the tail does not change historical values.
- Periods must be integers >= 1. Undefined cases — `period <= ddof`, a zero denominator in a fundamental ratio, previous-period revenue <= 0 — throw `RangeError` rather than returning `Infinity`; where the variance inside the rolling window is zero (as in `correl` / `beta`), that position is `null`.
- **An illegal period always throws** (0, negative, fractional, `NaN`, `Infinity`), including the five indicators that forward to engine-core: engine-core silently returns all `null` for an illegal period, while this package validates in its wrapper and throws. Regression-style indicators additionally require `period >= 2`: `linRegSlope` / `linRegIntercept` / `linRegAngle` / `tsf` and, like them, `correl` / `beta` throw `RangeError` for `period = 1` (or 0); `period = 2` computes normally (see section 6, point 1).
- **Non-finite input is not handled uniformly**: `NaN` / `±Infinity` make only some functions throw; the rest carry `NaN` into the output, and a few treat `NaN` as "no movement" and swallow it silently. Clean your input before calling — do not expect the library to catch it (per-function results are in section 6).
- Input arrays and bar objects are never mutated.
- Doubles throughout (no decimal type). **Ratio-style indicators return fractions, not percentages** — the exceptions are `atrPercent` (a ratio by design), `pricePosition` (0..100) and `natr` (a percentage).

## 3. Overlap with engine-core

**Nine places overlap semantically**, in two kinds:

| ta-plus | engine-core counterpart | Relationship |
|---|---|---|
| `plusDI`, `minusDI` | the +DI / −DI inside `adx()` (not exported separately) | Same definition, same values: they **forward** engine-core's implementation (Wilder 1978, seed is the sum of DM / TR over bars 1..period, first value at index period) and this package no longer keeps a second copy |
| `aroonOsc` | the `osc` field of `aroon()` | Same definition, same values: **forwarded** |
| `linRegSlope`, `linRegIntercept` | `linearRegression()` | Same definition, same values: **forwarded** (x axis is the index inside the window) |
| `adOsc` | `chaikinOscillator()` | **Different definition**, see below |
| `stochF` | `stochastic()` | **Different definition**, see below |
| `correl` | `rollingCorr()` | **Different definition**, see below |
| `variance` | `rollingStd()` | **Different definition**, see below |

Forwarding means a read-only relative-path reference to engine-core's sources (engine-core's `package.json` exports `.` only, and its root entry does not re-export `ta/`), with equality asserted item by item in `test/engine-core-parity.test.ts`; `dx`, `linRegAngle` and `tsf` are composed from the forwarded results.

The four differences, one by one:

1. **`adOsc` versus `chaikinOscillator`**: the formula is the same (`EMA(A/D, fast) - EMA(A/D, slow)`); the seed and warm-up differ. `adOsc` follows TA-Lib `ta_ADOSC.c`: both EMAs are seeded with the first A/D value, and the first non-null index is `max(fast, slow) - 1`. `chaikinOscillator` uses engine-core's own `emaSeries` seeding and warm-up. The call shape differs too (`fastPeriod` default 3, `slowPeriod` default 10 as positional arguments versus a `{ fast, slow }` options object). Values differ during warm-up and converge afterwards.
2. **`stochF` versus `stochastic`**: `stochF` is the fast stochastic, so K is not smoothed after the fact (`dPeriod` only smooths D), default `kPeriod = 5`; `stochastic` defaults to `kPeriod = 14`. **A zero range is handled differently**: `stochF` gives `K = 0`, `stochastic` gives `K = 50`. In a flat market that difference changes the signal.
3. **`correl` versus `rollingCorr`**: the windowed Pearson value is the same (zero denominator gives `null`); the input shape and gap handling differ. `correl` takes `number[]` with `period` defaulting to 20; `rollingCorr` takes `(number | null)[]` and returns `null` whenever the window contains a null, with `period` required.
4. **`variance` versus `rollingStd`**: same windowed sum of squares, but `variance` returns the variance (TA-Lib `TA_VAR`, `ddof` default 0) while `rollingStd` returns the standard deviation. Both accept `ddof` (`ddof = 1` matches the sample form used by pandas `.var()` / `.std()`).

## 4. Known differences from TA-Lib (what bites when you cross-check)

| Indicator | Difference |
|---|---|
| `cmo` | Uses the TA-Lib definition (Wilder smoothing), not the original Chande definition. Input `[10,11,10,12,12,13]` with period 3: the original gives 50 / 33.33 / 100, this package gives 50 / 50 / 68 |
| `plusDM` / `minusDM` / `plusDI` / `minusDI` | Wilder seed is the sum over bars 1..period with the first value at index period; TA-Lib seeds with the sum of the first period−1 bars and smooths one step (first value at index period−1), so warm-up values differ |
| `natr` | ATR uses TR = h−l on bar 0 with the first value at index period−1; TA-Lib starts TR at bar 1 with the first value at index period |
| `beta` | No return conversion. TA-Lib `BETA` converts both price series to single-bar returns internally; for a conventional beta, convert with `simpleReturns` first |
| `correl` | TA-Lib returns 0.0 when the denominator is zero; this package returns `null` (a missing value, not a fake zero) |
| `skewness` / `kurtosis` | Sample form by default (the corrected formulas behind pandas `.skew()` / `.kurt()` and Excel SKEW / KURT, needing n >= 3 / n >= 4); `{ sample: false }` switches to population moments |
| `volumeRatio` | The baseline **excludes the current bar**: `volume[i] / mean(volume[i−period .. i−1])`. Including it systematically understates the ratio |

## 5. Where the numbers come from (do not self-certify)

Reference values do **not** come from this package's implementation, and not from the output of any ported code:

- **TA-Lib** (BSD, downloaded read-only, not vendored) C sources, used to check formula definitions (CMO smoothing, BOP, the AVGDEV divisor, VAR as a population variance, the ADXR delay term).
- **QuantDinger** (Apache-2.0) factor registry and market technical-indicator modules: only the definition and field semantics were borrowed.
- **Hand-worked examples**: every indicator has at least one case built from small integers that divide exactly, with the fraction worked out in a comment (for example CMO `[10,11,10,12,12,13]` -> 68).

When you verify numbers yourself, keep this rule: **the reference must live outside your own code**. Checking your output against your own output only ever returns "consistent".

## 6. Input conventions: non-finite values, overflow, and the period table

This section answers one question only: what happens when the input is wrong. Nothing here is quoted — each indicator was called on a fixed series and the returned values were inspected for `NaN`, `Infinity`, `null`, or a thrown error. **Three behaviours coexist today**, so clean the input yourself before calling.

### 6.1 Input containing `NaN` / `Infinity`

1. **Throws `RangeError`**: the five functions in `packages/ta-plus/src/risk.ts` validate each element first, and the message names the offending index (`realizedVolatility: index 5 is not finite`) — `realizedVolatility`, `downsideVolatility`, `skewness`, `kurtosis`, `maxDrawdown`. This is the easy group: a bad value is an error.
2. **Carries `NaN` into the output**: the other 30 period-taking exports (last column of the table in 6.3). The output holds `NaN`, **not** `null` — `null` means "not computable yet", `NaN` means "computed from dirty data". Do not conflate them.
3. **Swallowed silently** (the dangerous group: no error and no `NaN` in the output): `cmo`, `maxIndex`, `minIndex`, `plusDM`, `minusDM`, `aroonOsc`. These implementations branch on comparisons (`if (x > 0)` style); a comparison against `NaN` is always false, so dirty data is treated as "no movement on this bar". Filter it yourself.

Functions without a period argument do not validate either: `avgPrice` / `medPrice` / `typPrice` / `wclPrice` / `bop` / `simpleReturns` pass a `NaN` bar straight through (`avgPrice([{ c: NaN … }])[0]` is `NaN`); the fundamental ratios are scalar entry points and throw `RangeError` on a zero or non-finite denominator.

Holes coming from a data source (halts, missing bars, split gaps) should be dropped or filled first — do not let `NaN` reach `cmo` / `maxIndex`, which swallow it.

### 6.2 Overflow (1e300 magnitude)

Windowed variance is computed from sums of squares: at an input magnitude of 1e299 the term `d²` is already 1e598, past the double range, and becomes `Infinity`.

- engine-core `rollingStd` returns `Infinity`; `bollinger` is built on top of it, so `upper` / `lower` / `bandwidth` are all `Infinity` and `percentB` is `NaN` (`upper - lower` becomes `Infinity - Infinity`). **This is `Infinity`, not `null`**, and it propagates into charts and comparisons.
- The three ta-plus indicators with the same formula overflow too: `variance`, `realizedVolatility`, `downsideVolatility`.
- `kurtosis`: the series is scaled by its largest absolute value before the moments are taken (kurtosis does not depend on scale or shift), so at 1e299 / 1e300 it returns the same value as at a small magnitude: no overflow and no constant any more.
- `amihudIlliquidity`: when the traded value (close x volume) or the ratio is outside the double range, that window is `null` (not representable) instead of `0`.
- The remaining functions stay finite at this magnitude (linear arithmetic, ratios, extremes).

In practice this magnitude shows up when index-like levels or very small unit prices are fed in raw. Rescale first (divide by the mean of the series, or convert to returns with `simpleReturns`); these functions will not preserve precision for you.

Three things to take from the table:

1. **`correl` / `beta` now agree with `linRegSlope`**: with `period = 1` (a one-point window has zero sum of squares) all of them throw `RangeError`, because a regression needs two points; before this change `correl` / `beta` quietly returned all `null` here. From `period = 2` on they compute normally, with the first `period - 1` entries `null`.
2. **Minimum 2 comes from `ddof`**: `zScore` (default `ddof` 1) and `realizedVolatility` (default `ddof` 1) require `period > ddof`, hence 2; pass `ddof: 0` explicitly and `period = 1` works. `skewness` needs at least 3 points and `kurtosis` at least 4, so `period < 3` / `< 4` gives all `null` instead of throwing.
3. **Most "valid numbers" at `period = 1` are degenerate**: `variance` / `avgDev` are always 0, `cmo` is always 100 or 0. Running without an error is not the same as producing a meaningful value.
