# 通知配置

通知在 Gitrader 里**不是内置通道，是插件**：一个声明了 `notify_send` 工具的插件，就是一条通道。加通道 = 装一个插件；不加就不装，内核里没有第二套通知代码。

## 1. 契约：内核怎么叫插件

内核把每条通知包成一个 `notice`，连同你在配置里的 `params`，作为一次 `tool.call` 发给插件的 `notify_send`：

```json
{
  "notice": {
    "key": "9f2c1a7d…（sha256 十六进制，64 位）",
    "level": "warn",
    "title": "risk.denials",
    "lines": ["ts: 1760000000000", "accountId: acct_fixture", "ruleHits[0].actual: 1200", "ruleHits[0].ruleId: budget"],
    "ts": 1760000000000,
    "topic": "risk.denials"
  },
  "params": { "chatId": "123" }
}
```

- `level` 只有 `info` / `warn` / `critical`。
- `key` 是内核按内容算出的 sha256，用来去重；同一通道同一 `key` 在窗口内只发一次。别把它当业务 ID。`notify test` 的测试通知与限流合并摘要例外：key 是 `test:…` / `summary:…`，title 是固定短句，lines 不带 `ts` 行。
- `title` 是主题名（如 `risk.denials`、`takeover.failed`），`lines` 是「路径: 值」形式的逐行事实，首行固定 `ts`。
- 返回两形状之一：`{"ok": true, "ref": "<平台消息 id，可选>"}`，或 `{"ok": false, "reason": "<短句，不含密钥>", "retryable": true|false}`。
- 超时：内核默认 10 秒；插件内部网络超时 ≤ 8 秒，超时按 `retryable: true` 返回。
- **队列、重试与补发**（出口行为，插件不用管）：
  - 每个通道有自己独立的队列和超时预算，一个通道挂死（比如对端 Webhook 不回）不会拖慢别的通道；`critical` 级通知（接管、保护器触发、REDUCING / HALTED 状态变化等）排在本通道已排队的 info / warn 前面（正在发的那条不打断）。去重窗口、每分钟合并和 1000 条上限都按通道算。
  - 一条通知在一个通道上，全链路最多 3 次 HTTP 尝试：通道插件自己重试（Webhook：首次重试不早于 250 ms，之后间隔翻倍并带抖动，总预算 8 秒；Slack / Telegram / Discord / 企业微信：各自最多 2–3 次 HTTP 尝试），重试到头才把失败结果交回内核，并带 `exhausted: true`，内核不会再叠一层重试；内核等满一次调用超时（10 秒）也不再重发。
  - 去重键：Webhook 插件的每次请求都带请求头 `X-Gitrader-Notice-Key: <notice.key>`；同一条通知的所有重试以及重启后的补发值完全相同，接收端可据此去重（长正文分块发送时，第 2 块起键后面加 `#<块号>`）。
  - 落盘补发：已经路由到某个通道、还没确认送达的 warn / critical 通知会记在 `GITRADER_HOME/notify-outbox.jsonl`；内核崩溃后重启，在 10 分钟有效期内对没送达的通道各补发一次（原去重键），已送达的通道不重发。`notify test` 的测试通知、限流合并摘要和 info 级通知不落盘。通知仍不写账本。
- 插件**不改写** `title` 与 `lines` 的内容，只做平台需要的转义 / 分块 / 排版。
- 返回值里出现 `privateKey`、`secret`、`password` 这类字段名，或回显了声明密钥的值（原文 / JSON 转义 / base64 / URL 编码），整帧被拒收，错误码 `SECRET_FIELD_REJECTED`。

## 2. 密钥怎么给

| 层 | 做法 |
|---|---|
| 清单 | `secrets: ["TELEGRAM_BOT_TOKEN"]` —— **只写名字，不写值** |
| 插件代码 | 只从 `process.env.TELEGRAM_BOT_TOKEN` 读；不打印、不回传、不写进返回值 |
| 工具入参 | **不许**携带密钥。协议在清单校验阶段就会拒装：`TOOL_SOLICITS_SECRET` |
| 传输 | 密钥不进 JSON-RPC；日志与错误消息经脱敏 |

句柄约定与引擎的远程令牌一致：配置文件里只有变量名（`env:<变量名>`），值放在进程环境里。**别把密钥粘进 `gitrader-plugin.json`**——清单会进哈希、进签名、进账本。

密钥值至少 8 个字符：短于 8 位的值不参与插件帧回显比对，启动时只有一条告警 `short secret excluded from frame scan`，等于内核看不见它被回显。每个通道用各自独立的随机值。

### 2.1 只有一种写法会被接受

`plugins.secrets` 的值必须是 `env:<变量名>` 句柄，**不是**密钥原文——配置校验只认 `env:` 这一种形状，写别的会报 `plugins.secrets requires environment names mapped to env:VAR handles`。密钥本体放在**启动内核的那个进程**的环境里：

```json
{
  "plugins": {
    "secrets": { "connector.gitrader.notify-webhook": { "WEBHOOK_SECRET": "env:WEBHOOK_SECRET" } }
  }
}
```

```text
export WEBHOOK_SECRET='<至少 8 位的随机串>'      # Windows PowerShell: $env:WEBHOOK_SECRET = '<...>'
gitrader serve                                  # 同一个 shell 里启动，子进程才拿得到
```

三条细节：

1. **只注入清单声明过的名字**。`plugins.secrets` 里多写了清单 `secrets[]` 没声明的变量名，内核忽略并告警（`ignored undeclared secret name …`），不会传给插件。
2. **缺句柄或环境变量没设**：插件起不来，报 `missing secret handle: WEBHOOK_SECRET`；测试结果与出口日志里只显示这一行，不显示值。补 `plugins.secrets` 与进程环境变量后重试。
3. **`notify.channels[].params` 里不要放密钥——连 `env:` 句柄也不要**。内核把 `privateKey` / `secret` / `apiSecret` / `mnemonic` / `seed` / `passphrase` / `pin` / `password` 这些字段名（不分大小写、忽略 `_` 与 `-`）一律当密钥字段，配置校验直接失败并提示改用 `plugins.secrets`；`gitrader notify test` 也会因此发不出去。仓库里 Webhook 插件 README 记的 `params.secret: "env:WEBHOOK_SECRET"` 是插件自身能认的句柄形状，但走通知通道这条路会在配置层先被拦下（README 待改，见工单）。通道密钥只走 `plugins.secrets` + 进程环境变量这一条路。


## 3. 配置 `notify` 段

字段以 `packages/kernel/src/config.ts` 的 `notify` 段为准（不写 `notify` = 不发送）：

```json
{
  "plugins": {
    "developerMode": false,
    "trustRoots": [],
    "secrets": { "connector.gitrader.notify-webhook": { "WEBHOOK_SECRET": "env:WEBHOOK_SECRET" } }
  },
  "notify": {
    "channels": [
      { "id": "main", "plugin": "connector.gitrader.notify-webhook", "minLevel": "warn", "params": { "url": "https://open.feishu.cn/open-apis/bot/v2/hook/…" } }
    ],
    "rules": [
      { "match": "takeover.*", "level": "critical", "channels": ["main"] }
    ],
    "rateLimit": { "perChannelPerMinute": 20, "dedupeWindowSec": 300 }
  }
}
```

| 字段 | 规则 |
|---|---|
| `notify.channels` | 必填数组。空数组 = 不发送 |
| `notify.channels[].id` | `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`，同一份配置内不许重名；`notify test` 用的就是它 |
| `notify.channels[].plugin` | 插件 ID（小写、可用点），必须已安装、已启用 |
| `notify.channels[].minLevel` | `info` / `warn` / `critical`；级别低于它的通知不投给这条通道 |
| `notify.channels[].params` | 对象，原样传给插件。**不能**出现密钥字段名（`privateKey`、`secret`、`apiSecret`、`mnemonic`、`seed`、`passphrase`、`pin`、`password`，不分大小写、忽略 `_` 与 `-`），否则配置校验直接报错并让你改用 `plugins.secrets` |
| `notify.rules[].match` | `*`（全部）、精确主题（`risk.denials`）、或前缀通配（`takeover.*`）；按顺序取首个匹配 |
| `notify.rules[].level` | 命中后的通知级别；`takeover.failed` 与 `takeover.alert` 固定 critical，不受它影响 |
| `notify.rules[].channels` | 必须是已配置的通道 ID；写错或引用不存在的通道，校验失败 |
| `notify.rateLimit.perChannelPerMinute` | 正整数，默认 20；每通道从首条受理通知起 60 秒窗口，超额合并为一条摘要 |
| `notify.rateLimit.dedupeWindowSec` | 非负整数，默认 300；同一通道同一 `key` 在这个窗口内只发一次。`0` = 关闭去重（等于同一接管每阶段各发一条） |

没配 `rules` 时，所有通道按各自的 `minLevel` 过滤后接收；配了 `rules`，未命中任何规则的通知也走这条默认路径。发送顺序照 `channels` 的书写顺序，单条串行，不并发。

## 4. 三条通道的配方

### 4.1 Telegram

| 项 | 值 |
|---|---|
| 清单 `permissions` | `net.fetch` |
| 清单 `net.hosts` | `api.telegram.org` |
| 清单 `secrets` | `TELEGRAM_BOT_TOKEN` |
| 必要 `params` | `chatId`（数字或 `@channelusername`） |
| 注意 | 正文按 MarkdownV2 转义；单条上限 4096 字符，超了按行分块顺序发；同一 chat 有最小发送间隔，429 会退避重试 |

Bot Token 从 @BotFather 拿，形如 `<数字>:<字符串>`。收不到的排查顺序：先确认 bot 被拉进目标会话、再确认 `chatId` 没写错符号，再看返回的 `reason`。

### 4.2 邮件（SMTP）

| 项 | 值 |
|---|---|
| 清单 `permissions` | `net.fetch` |
| 清单 `net.hosts` | 仓库里的邮件插件声明的是 `localhost`（本地 relay）；用外部 SMTP 时你的清单要写对应主机 |
| 清单 `secrets` | `SMTP_PASSWORD` |
| `params` | `host`、`port`、`secure`、`user`、`from`、`to`（字符串或数组，最多 50 个）、`subjectPrefix`（可选） |

```json
{
  "params": {
    "host": "smtp.example.com",
    "port": 587,
    "secure": false,
    "user": "trader@example.com",
    "from": "trader@example.com",
    "to": ["trader@example.com"],
    "subjectPrefix": "[gitrader] "
  }
}
```

- 端口 465 配 `secure: true`（隐式 TLS）；587 配 `secure: false`（服务端报 STARTTLS 就地升级）。不写端口时按 `secure` 取默认。
- 会话顺序：`EHLO` →（可选 `STARTTLS` + 再 `EHLO`）→ 有 `user` 时认证 → `MAIL FROM` → `RCPT TO`×n → `DATA` → `QUIT`。任一收件人被拒就整体中止，不投递。
- `user` 留空且没有 `SMTP_PASSWORD` 时，可以走不认证的本地 relay；两者都不给认证信息又要求认证，会返回 `retryable: false`。

### 4.3 Webhook

| 项 | 值 |
|---|---|
| 清单 `permissions` | `net.fetch` |
| 清单 `net.hosts` | 仓库里的 Webhook 插件声明：`open.feishu.cn`、`oapi.dingtalk.com`、`qyapi.weixin.qq.com`、`hooks.slack.com`、`discord.com` |
| 清单 `secrets` | `WEBHOOK_SECRET` |
| `params` | `url`（必填）、`markdown`（可选，发 Markdown 还是纯文本）；签名密钥通过声明的环境句柄注入，**不写进 `params`** |

- 方言按 URL 自动识别：飞书 / 钉钉 / 企业微信 / Slack / Discord / 通用。
- 飞书与钉钉的签名是 HMAC-SHA256 + base64（时间戳参与），插件自己算，不需要你处理。
- 厂商返回的错误会翻译成 `retryable`：429 / 5xx 可重试，4xx 参数类错误不重试。
- 通用（generic）webhook 的主机来自你的 `url`，清单里的 `net.hosts` 覆盖不到它——自己写清单时把主机写进去。

## 5. 装上并启用

以一个通道插件目录 `notify-demo/` 为例，按顺序执行（都是真实存在的子命令）：

```text
gitrader plugins check notify-demo            # 校验清单与哈希；0 = 通过，2 = 被拒
gitrader plugins pin notify-demo              # 改了文件就重新钉版本（写 source.sha256）
gitrader plugins reload                       # 服务在跑就通知服务，不在跑就离线扫一遍
gitrader plugins list                         # 看每个插件：ok / REJECTED、已授予、待授予、启用否
```

启用与授权（**先停服务**，这个入口要本地 PIN）：

```text
gitrader plugins grant connector.gitrader.notify-webhook net.fetch
```

零权限插件不带权限名就是「只启用」。授权逐项生效、每次都入账。

## 6. 试发一条

先按第 3 节配好 `notify.channels` 和 `plugins.secrets`，把通道需要的目标参数放在 `params`。密钥值只放在启动内核的进程环境中，配置保存 `env:<变量名>` 句柄。

```text
gitrader notify test main
```

`main` 是配置中的通道 ID。命令通过人面动作 `notify.test({ channelId })` 发送固定的 info 测试消息，输出各通道结果：成功退出 0，失败退出 1。它绕过去重、限流和 `minLevel`，所以「测试能发、真事件不发」通常不是通道问题，而是路由或级别问题（见第 10 节）。支持离线本地内核和已运行服务；已启用但未启动的插件会在首次调用时拉起。

`notify_send` 只允许通知出口与这个测试入口调用。通用 `plugins call` 和 Agent 调用都会被拒绝，不能用它们发送自定义正文。

## 7. 三条硬规则

这三条在内核里实现，改配置改不掉；写通道插件和配路由之前先知道：

1. **自由文本不进正文。** 模板只取白名单字段（`accountId`、`instrumentId`、`orderId`、`takeoverId`、`ruleId`、`code`、`state`、`price`、`quantity`、`notional`、`limit`、`actual` 等）并只下钻 `scope`、`ruleHits`、`precheck`、`intent`、`error` 这类分组。字符串值不符合事实词形（1–64 个 `A-Za-z0-9_.:/-`）时写成 `[text omitted]`，其它键不序列化。提案理由、接管理由、备注、策略说明不会出现在通知里——要留档去账本。
2. **同一接管只发一条。** 通知 key 按 takeoverId 归并：requested / applied / completed 与随后同 scope 的 `trading_state.changed` 共用同一个 key，同一通道在去重窗口内只发一条；failed 与 alert 另算一条、固定 critical。窗口默认 300 秒（`notify.rateLimit.dedupeWindowSec`），窗口内投递失败也占位。
3. **短密钥值不参与回显扫描。** 声明值短于 8 个字符时内核不拿它比对插件返回帧，只在启动时告警；等于放弃了「回显即拒收」这层保护。密钥用 ≥8 字符的随机串，别用 `123456`、`ok` 这类短值。

完整契约、限流与指标见 [通知出口](../notifications.md)。

## 8. 现状（2026 年 10 月，本仓库）

1. **自动转发已接线。** 内核订阅风控、接管、保护器、提案、插件状态与引擎健康事件，经通知出口按配置路由、去重、限流，再调用通道插件。未配置 `notify` 或 `channels` 为空时一条都不发。接管以 takeoverId 关联：去重窗口内阶段更新不重复发送，失败阶段另发一条 critical。
2. **声明的密钥已自动注入。** 启动插件时，只解析清单 `secrets[]` 声明的名字，并将值注入该插件进程。缺句柄或无法解析时，测试结果与出口日志显示 `missing secret handle: <NAME>`，不显示值。未声明的名字被忽略并告警。
3. **失败可观测。** 单通道失败按 `retryable` 最多再试一次；`/api/metrics` 暴露 `notify_sent_total`、`notify_failed_total`、`notify_dropped_total`、`notify_deduplicated_total`、`notify_merged_total`、`notify_redacted_total`、`notify_retried_total`。通知本身不写账本。

通知正文只含结构化事实；提案理由、接管理由、备注、策略说明等自由文本不转发。测试夹具的假连接模式只用于本地验证，不需要真实凭据。

## 9. 新增三个通道：Discord / Slack / 企业微信

三个通道各是一对「库 + 插件」，写法与 Telegram 那对一致：库在 `packages/notify-<通道>`，插件在 `packages/plugin-notify-<通道>`（插件不能 import 工作区包，所以是同一套逻辑的 `.mjs` 版）。

| 通道 | 库 / 插件 | 密钥环境变量（清单 `secrets[]` 名） | 出网主机 | 单条上限 | 重试口径 |
|---|---|---|---|---|---|
| Discord | `@gitrader/notify-discord` / `plugin-notify-discord` | `DISCORD_WEBHOOK_URL` | `discord.com`（以及 `discordapp.com` / `canary` / `ptb`） | 正文 2000 字符，按行分块 | 429 按官方 `retry_after` 等一次；等待超过 5 s 或会破预算就不等，直接 `retryable: true` |
| Slack | `@gitrader/notify-slack` / `plugin-notify-slack` | `SLACK_WEBHOOK_URL` | `hooks.slack.com` | 正文 40000 字符，**超限报错，不拆条** | 408 / 429 / 5xx 可重试（429 优先看 `Retry-After`）；其它 4xx 不重试 |
| 企业微信 | `@gitrader/notify-wecom` / `plugin-notify-wecom` | `WECOM_WEBHOOK_URL` | `qyapi.weixin.qq.com` | markdown 4096 **字节** / text 2048 字节（按 UTF-8 算，一个汉字 3 字节） | `errcode 45009`（超 20 条/分钟）可重试；`93000`（key 无效）不重试 |

四条要点：

1. **webhook URL 本身就是凭据。** Slack 与 Discord 的地址里带 token，企业微信的地址里带 `key` 查询参数。三个通道一律只从环境变量读（配置里只写 `env:<变量名>` 句柄），库不打印、不落盘；错误消息先脱敏，整条 URL 与 key 都不会出现在 `reason` 里。
2. **提及造不出来。** Discord 请求固定带 `allowed_mentions.parse: []`，正文里写 `@everyone` 也不会触发提及，`wait=true` 才拿得到 message id 当 `ref`；Slack 把 `&` `<` `>` 转义成实体，`<@U123>` / `<!channel>` 无法成立。只转义，不改写正文。
3. **一条通知只发一次发送动作。** Slack 超过 40000 字符直接报错，不拆成两条；Discord 受平台 2000 字符硬限，在**同一次调用内**按行分块；企业微信按字节分块，切点不落在码位中间。
4. **分级与去重照旧**：通道的 `minLevel`、`dedupeWindowSec`、路由规则仍按第 3 节配，新通道不改变内核侧的合并与限流。

装上之后照第 5、6 节走：`gitrader plugins list` 看清单、`plugins grant` 给 `net.fetch` 权限、`gitrader notify test <通道 ID>` 试发一条。

**已验证与未验证的边界**：三条通道的请求形状、状态码判定、分块、转义与脱敏都有测试，判定依据是各包自带假服务器（按官方规则独立实现、不 import 客户端代码）；但**都没有对真实端点发过请求**（测试全离线）。Discord 那篇 README 逐条列了未验项（Markdown 转义字符表、错误码到 HTTP 状态的对应关系等），照实读。

## 10. 排错表

| 返回 / 现象 | 原因 | 怎么办 |
|---|---|---|
| `params.chatId` 缺失 | 通道目标参数未配置 | 在 `notify.channels[].params` 中补齐 |
| `missing secret handle: <NAME>` | 声明名缺句柄或句柄无法解析 | 补齐 `plugins.secrets` 与对应进程环境变量，再启动插件 |
| `unknown channel` | `notify test` 的 ID 不在 `notify.channels` 里 | 用 `gitrader plugins list` 与配置里 `notify.channels[].id` 对齐 |
| 配好了却一条不发 | `channels` 为空、通道 `minLevel` 高于事件级别、或规则把事件指到了别的通道 | 先用 `gitrader notify test <id>` 确认通道本身通，再查第 3 节的级别与路由 |
| 通知里没有理由 / 备注 | 自由文本不进正文（第 7 节第 1 条） | 去账本查；不要让插件去「补」正文 |
| 同一接管收到多条 | `dedupeWindowSec` 被设成 0，或同一个事件被配到多个通道 | 改回正窗口；一个事件确实要多处提醒就多配通道，别关去重 |
| `retryable: true` | 平台限流 / 5xx / 超时 | 可以重试；连续重试仍失败看平台侧 |
| `retryable: false` + 4xx | 参数或目标错（chatId、收件人、webhook key） | 改配置，不要重试 |
| `insecure_url` | Webhook 地址是明文 `http:`，且主机不是本机回环（`127.0.0.1` / `localhost` / `[::1]`） | 改用 `https:`；明文回环只留给本机自测 |
| `SECRET_FIELD_REJECTED` | 插件返回值带密钥字段名，或回显了声明值 | 改插件：只回 `{ ok, ref }` |
| `REJECTED n problem(s)` | 清单不合规（权限枚举、主机、哈希对不上） | 按行修；改完 `plugins pin` |
| `MANDATE_LIMIT` | 插件没启用或工具权限没授予 | `plugins grant <id> [perm]` |
| `PLUGIN_RESULT_INVALID` | 返回值不合清单里声明的 `output` | 修插件返回值 |

通知标题与正文由内核模板生成，插件只负责排版与发送。通知仅摘取结构化事实，因此不会复刻账本里的自由文本。
