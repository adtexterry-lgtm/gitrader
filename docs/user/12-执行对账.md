# 执行对账：账本与场所对不上时看什么

「我这边的账」和「场所那边的账」迟早会不一致：漏记的成交、卡住的重启、改单换了单号、网络断了半分钟。对账做的就是**把两边摆在一起，指出差在哪、建议怎么办、证据是哪条记录**。

**这条规矩先记住：对账只出结论，不改账。** 对账包没有任何写入口：不下单、不撤单、不改账本、不发请求、不读系统时钟。要不要改、怎么改，由人定。

## 1. 输入与输出

```ts
import { reconcile, renderReport } from '@gitrader/exec-reconcile'

const report = reconcile(
  {
    local: { accountId, orders, fills, positions, asOf },   // 账本此刻相信的东西
    venue: { openOrders, historyOrders, fills, positions, asOf, truncated, unavailable },
    links,                                                  // 可选：改单链（客户端单号 ↔ 场所单号）
  },
  {
    now,                                    // 必填：不读系统时钟，保证同一输入可复现
    clockSkewMs: 2_000,
    venueLatencyMs: 5_000,
    sizeTolerance: '0',
    positionTolerance: '0.0001',
    priceToleranceBps: 5,
    fillLookbackMs: 24 * 3600_000,
    staleAfterMs: 60_000,
    ownClientOrderIdPrefixes: ['gt-'],
    dedupeFallback: 'accept_with_risk',     // 或 'needs_human'
  },
)

report.verdict        // clean | attention | blocked
report.findings       // 每条：差异码 + 建议动作 + 是否需人工 + 证据
report.inferredFills  // 推断成交（全部 inferred: true，带依据与定价来源）
report.dedupe         // 去重键、重复到达、同号冲突
console.log(renderReport(report, { venueLabel: '交易所名' }))
```

| 结论 | 意思 | 你该做什么 |
|---|---|---|
| `clean` | 视图之内没有差异 | 不用动；差异可能在视图之外，看下一节「看不见的部分」 |
| `attention` | 有差异，但可解释、可等待、不影响账 | 按建议动作处理，多为等窗口过去后重查 |
| `blocked` | 有差异且会污染账（漏记成交、持仓对不上、成交号冲突） | **停止新增交易动作**，人工核对后再决定；不要用对账结果自动改账 |

## 2. 差异分七组（38 个差异码）

| 组 | 典型差异码 | 判定要点 |
|---|---|---|
| 本地有、场所无 | `local_open_venue_filled` / `local_open_venue_cancelled` / `local_open_venue_partially_recorded` / `local_open_venue_missing` | 先看历史订单，再看有没有成交落在这个单号上，都没有再看是否还在场所回报延迟窗口内 |
| 场所有、本地无 | `venue_order_unmapped` / `venue_order_external` / `local_terminal_venue_open` | 单号像我们的但账本没认领 → 交给人；前缀不是我们的 → 外部单，不自动接管 |
| 状态 / 数量漂移 | `order_state_drift` / `order_filled_size_drift` / `order_price_drift` / `order_reduce_only_drift` | 逐字段比；成交量方向不同结论不同（场所多 = 漏记；账本多 = 改单后场所重置） |
| 改单链 | `amend_chain_resolved` / `amend_chain_broken` / `amend_chain_ambiguous` / `order_venue_id_conflict` | 链上多单号、缺一段、一号多认领分别处理 |
| 成交 | `fill_duplicate` / `fill_conflict` / `fill_orphan` / `fill_missing_inferred` / `fill_missing_unexplained` / `fill_recorded_excess` / `fill_total_exceeds_order` / `fill_time_anomaly` 等 | 先去重 → 认领订单 → 推断缺口 → 查账本侧重复 |
| 持仓 | `position_size_mismatch` / `position_missing_at_venue` / `position_missing_locally` / `position_side_mismatch` / `position_entry_price_drift` 等 | 按标的 × 方向 × 保证金模式比，净额与分方向都比 |
| 视图质量 | `snapshot_stale` / `venue_fills_truncated` / `venue_report_unavailable` | 视图不新鲜、回补被截断、场所给不出某类报告：结论一律降级 |

「难以判断」的全部落到 `query_order_status` / `wait_and_recheck` / `review_*` 这类建议，并且 `advice.requiresHuman = true`。每条差异都带 `advice.why`（为什么这么建议）和 `evidence`（哪份报告、哪条记录、哪个字段、什么值）——看证据，不要只看结论。

## 3. 推断成交：它会告诉你「我是猜的」

场所累计成交量比账本已记的多出来的那部分，对账会给出一条**推断成交**：

- 一定带 `inferred: true`，`basis` 逐条写依据（场所哪份报告说多少、账本记了多少、差额多少、价格与时间从哪来）；
- 定价来源只有两种：场所订单报告的成交均价（首选），或账本该单最后一笔成交价（`priceSource: 'local_last_fill_price'`，依据里写明是替代价）；
- 两者都没有 → 不猜价格，报 `fill_missing_unexplained`（阻断级，需人工）；
- 差额在 `sizeTolerance` 内不推断；账本多于场所不推断，改报 `fill_recorded_excess`；
- 每条推断成交带确定性 `id`（`inferred:<场所单号>:<账本已记合计>-><场所累计成交量>`）：同一个缺口重复对账得到同一个 id，可以据此对「人已确认入账」的那条去重。

**推断不等于事实。** 要入账必须人工确认。

## 4. 时间与去重：为什么它不急着说「丢了」

- 所有比较都带容差：时钟偏差 + 场所延迟合成「在途窗口」，窗口内「场所没看到」只提示等待重查，不判丢失。
- 成交时间落在未来超出偏差、或早于回补窗口，单独报 `fill_time_anomaly`。
- 去重键优先级：场所成交号 > 回退合成键（`单号|时间|数量|价格`）> 累计量键。回退键有误判风险，报告里会写明（`fill_dedupe_key_fallback`）；把 `dedupeFallback` 设成 `'needs_human'` 可以让它直接交给人。

## 5. 它看不见的部分

对账只能看见你喂给它的视图。以下情况结论会偏：

- 场所给不出某类报告（例如某些券商不查已完成订单），连接器应在 `unavailable` 里声明；没声明的「查不到」会被读成「没有」。
- 历史成交被截断（`truncated`）：窗口外的差异看不见。
- 改单链只在内存里、重启就丢：涉及改单的差异可能被判成「外部单」。

这几项都要写在报告的局限性里，别把 `clean` 读成「账一定对」。

## 6. 它的位置

- 内核自己的启动对账（`startupReconcile()`）现在做三件事：拉场所未结订单与最近成交、把本地挂单在场所查不到的先查一次再算作未解决、按场所成交号回补成交。它**不比持仓、不比成交量、也不区分「场所没有」和「场所给不出」**。
- 内核的 `reconcile.status` 提供账户当前对账视图，`reconcile.refresh` 重新采集证据，`reconcile.confirm` 仅将人工确认的推断成交写入账本，`reconcile.resolve` 记录对待审项目的人工决定。内核仍按自己的确定性规则执行风控；CLI 处理待审项不会修改原始差异或自动恢复交易。

## 7. 查看与处理内核待审项

```sh
gitrader reconcile status
gitrader reconcile status --account paper
gitrader reconcile status --json
gitrader reconcile resolve --item <项目ID> --action acknowledge --reason "已核对场所报告与本地记录"
gitrader reconcile resolve --item <项目ID> --action reject --reason "不确认这条推断成交"
```

默认状态输出按账户显示当前待处理项目、中文问题名称、证据字段和值、允许动作和下一条命令。没有待审项时会显示「无待处理对账项」；证据不可用时还会提示刷新。`--json` 返回内核原始 `ReconcileAccountView[]`，不改字段或内容。

状态中的 `reviews` 是已留存的审查记录。`blocking` 表示该记录本身属于阻断类型；当前仍需处理的条件是 `blocking = true`、没有 `resolution`，且没有 `confirmedFillId`。因此已处理或已确认的历史记录可能仍在 JSON 中，但不再作为当前待办显示。当前视图的 `findings` 会过滤已处理审查对应的发现，原始报告与历史审查记录不被删除或改写。仅有阻断发现而没有可处理审查记录时，CLI 会提示刷新证据，不会凭空生成处理动作。

新式 `resolve` 从本机当前视图自动取得账户、项目 ID 和 `evidenceDigest`，并生成唯一 `requestId`；证据变化时应重新查看后再发起。旧式六字段 JSON 仍可用：

| 字段 | 含义 | 新式命令中的来源 |
|---|---|---|
| `accountId` | 项目所属账户 | 从当前待审项目自动带出；可用 `--account` 限定账户 |
| `itemId` | 当前审查记录 ID | `--item` |
| `evidenceDigest` | 该记录当前证据的摘要 | 从本机当前视图自动带出，避免沿用过期证据 |
| `action` | 人工决定 | `--action`；`inferred_fill` 只允许 `reject`，其他待审类型只允许 `acknowledge` |
| `reason` | 1 至 500 个非空白字符的处理理由 | `--reason` |
| `requestId` | 幂等请求标识 | 每次新式命令自动生成；旧式 JSON 需自行提供 |

`reject` 表示不接受这条推断成交；`acknowledge` 表示已查看并记录对其他待审差异的处理。两种操作都只写入审查回执，不会改动财务账本，也不会自动恢复交易。需要恢复时，仍须另行执行 `gitrader reconcile resume --account <别名|账户ID> --reason <理由>` 并完成 PIN 验证。
