# 回测与研究

回测的目的不是「证明它能赚」，而是**在花钱之前把假设摆到桌面上**：成本、滑点、成交、泄漏、试了多少次。这一节讲怎么跑、看什么、留什么证据。

## 1. 数据从哪来

**引擎不带任何历史数据。** 这是设计：数据是你的，来源要能被指认。`BacktestSpec.data.source` 三选一：

| `source` | 意思 |
|---|---|
| `host` | 用宿主（内核）录制的行情 |
| `engine` | 引擎自己取（它自己的数据源） |
| `files` | 你给文件：`files[].path` + `files[].sha256` + `format`（只有 `csv` 与 `json` 两种） |

给文件时**哈希是必填**的：回测结果里会记下数据摘要，别人（或三个月后的你）能核对是不是同一份数据。

**`host` 数据本地优先、只补缺口。** 内核把取过的已收盘 K 线录在本机（`<数据目录>/data/candles/<环境>/<场所>/<标的>/<周期>.jsonl`，一行一根）。回测请求的窗口里每个已收盘的周期格点本机都有，就**只读本机、不向交易所发请求**（行情来源记作 `store`）；有缺口，只向交易所拉缺的那一段，本机已有的根**不会被交易所的数据替换**，只把新拉到的根录进去（来源记作 `<场所>+store`）。同一序列里同一根 K 线只存一行，重启后、两个回测同时补同一个缺口也一样。还在形成中的那一根不属于这条路径，回测里不会有它。

文件格式目前只收 `csv` 与 `json`，**不支持 parquet**：spec 里写 `format: "parquet"` 会被直接拒掉，报「only csv and json candle files are supported」。手上有 parquet（比如从行情库导出的），先用 pandas 之类的工具转成 csv 再给。csv 的列是 `t,o,h,l,c[,v]`，`t` 是 Unix 毫秒，可以有表头行，坏行会被跳过；json 可以是一个 K 线数组，也可以是 `{"candles":[...]}`。

`files` 源目前只有 TypeScript 引擎（`@gitrader/engine-core`）支持；Python 引擎只吃 `host` 源，写 `files` 会回 `4005 DATA_UNAVAILABLE`（见 [16-Python策略引擎](16-Python策略引擎.md)）。

## 2. 回测入口

| 入口 | 用法 | 适合 |
|---|---|---|
| Agent 工具集 | `backtest` 的 `run` / `status` / `result` / `cancel` | 让 Agent 跑、你看结果 |
| 引擎协议 | `backtest.run` / `backtest.status` / `backtest.result` / `backtest.cancel` | 自己写的引擎或脚本 |

命令行**没有**回测子命令：`gitrader bench` 是内置的一个占位，只打印一行「M1 未实现」，数字由发布流程写进 `docs/perf-baseline.md`。这条别当成性能测量工具。

## 3. `BacktestSpec` 要看哪几项

```json
{
  "subject": { "strategy": { "id": "my-breakout", "version": "0.1.0", "params": { "period": 20 } } },
  "instruments": ["hyperliquid:BTC"],
  "interval": "1h",
  "from": 1730000000000,
  "to": 1735000000000,
  "data": { "source": "files", "files": [{ "path": "btc-1h.csv", "sha256": "<64 位十六进制>", "format": "csv" }] },
  "account": { "initialBalance": "10000", "ccy": "USDC", "leverage": 2 },
  "assumptions": { "fees": { "maker": "0.0002", "taker": "0.0005" }, "slippageBps": 3, "fillModel": "next-bar-open", "funding": false, "liquidation": false },
  "seed": 7
}
```

- `subject` 指到具体的策略 `id` + `version` + `params`；参数出界或没声明会被拒，不会替你改。
- `assumptions` 是**必填的诚实项**：

  | 字段 | 说明 |
  |---|---|
  | `fees` | maker / taker 费率，或 `"venue"`（用场所声明的费率） |
  | `slippageBps` | 滑点假设，基点 |
  | `fillModel` | 成交模型，如 `next-bar-open` |
  | `funding` | 是否计资金费。**不建模就写 `false`**，别默默当成 0 |
  | `liquidation` | 是否建模强平。同上 |

- **资金费从哪来**：`data.source` 是 `host` 且 `funding` 写 `true` 时，内核用 Hyperliquid 和币安（Binance）的公开资金费历史来计资金费（只读，不需要钥匙，每秒不超过 2 次请求）；这个场所拿不到时会降级：本次回测不计资金费，结果里的 `assumptions.funding` 回 `false`，并在 `warnings` 里写明资金费不可用，别把这样的结果当成含资金费。`files` 源则要在 `data.files` 里自己给 `kind` 为 `funding` 的文件。
- `seed` 固定随机源，保证同输入同结果。
- `instruments` 只放**一个**标的 id：这个引擎一次回测只跑单标的。Hyperliquid 的永续合约 id **不带** `-PERP` 后缀——填 `hyperliquid:BTC` / `hyperliquid:ETH`；自己拼上 `-PERP` 那种写法找不到标的（`gitrader agent market search` 返回什么就照抄什么）。非默认 dex 的标的会多一段前缀，形如 `hyperliquid:xyz:TSLA`。

**窗口上限**：`from` → `to` 的根数（`(to - from) / 周期毫秒`）和跨越时长都有上限，超限在装载数据之前就判失败，问题码 `INVALID_PARAMS`，消息形如 `backtest window rejected: bars 30000 exceeds maxBars 26280 for interval 1h`。上限取自 QuantDinger 的按天窗口表（1 / 3 分钟 30 天，5 分钟 180 天，15 / 30 分钟 365 天，1 小时及以上 1095 天），**与单次行情拉取的 5000 根协议上限（`maxHistoryLimit`）无关**：长窗口由引擎分页拉取，每页 ≤ 5000 根，录制库里已有的部分直接读本地。整个引擎另有 100 万根的总上限：

| 周期 | 最多根数 |
|---|---|
| `1m` | 43200 |
| `3m` | 14400 |
| `5m` | 51840 |
| `15m` | 35040 |
| `30m` | 17520 |
| `1h`（约 3 年） | 26280 |
| `2h` | 13140 |
| `4h` | 6570 |
| `8h` | 3285 |
| `12h` | 2190 |
| `1d` | 1095 |
| `3d` | 365 |
| `1w` | 156 |
| `1M` | 36 |

（`1M` 按 30 天算。）窗口内至少要有 30 根 K 线，不够会回 `DATA_UNAVAILABLE`。Python 引擎的窗口规则不在此表内。

## 4. 结果怎么读

**Agent 取结果（`backtest` 的 `result`）默认只回摘要**：统计量、偏差检查、假设、警告、数据摘要，外加 `counts: { equity, trades, funding }`（三条序列各有多少项）。权益曲线、逐笔成交、资金费明细用 `part: "equity" | "trades" | "funding"` 分页取：每页回 `{ items, total, next? }`，`items` 按时间升序，`limit` 取 1–1000（缺省 500；一页放不下时服务端少给几条并照样给 `next`，不截断），下一页把上一页的 `next` 填进 `cursor`，最后一页没有 `next`。两种引擎、结果多大都是这个用法。命令行同理：`gitrader agent backtest result --args '{"jobId":"…","part":"equity","limit":500}'`。

`BacktestResult` 里两块要分开看：

**统计量**（`stats`）：`totalReturnRatio`、`annualizedRatio`、`maxDrawdownRatio`、`sharpe`、`sortino`、`winRatio`、`profitFactor`（无成交时为 `null`）、`trades`、`fills`、`avgHoldBars`、`spanDays`、`finalEquity`。比例都是分数（0.12 = 12%）。

**偏差检查**（`biasChecks`）：`lookahead` 与 `recursive` 两项检查结果，加 `trialCount`——这条策略在这次研究里被试了多少组参数。**`trialCount` 大而只有一组好看，基本等于运气**；多重比较的问题不会因为指标漂亮而消失。

**逐笔**（`trades`）：时间、方向、价格、数量、盈亏、手续费、以及策略给出的 `reason`。复盘时先看 `reason` 与成交价，再看汇总。

## 5. Walk-forward

滚动窗口：拿一段训练窗扫参数，紧接一段**没参与选参**的测试窗跑样本外，窗口整体前移，最后把各折样本外收益拼起来。

规则（实现在 `packages/engine-core/src/strategy/walk-forward.ts`，纯函数，可在脚本里直接调）：

- 训练窗 `[start, start+trainBars)`，测试窗 `[start+trainBars+embargo, ... + testBars)`；
- `embargoBars`：训练窗与测试窗之间空出的根数，处理信号衰减与重叠；
- `blindHoldoutBars`：序列**末尾**保留一段，任何窗口都不许碰——这是最后的盲测段；
- 步长缺省等于 `testBars`（窗口不重叠）；
- 每折记录训练窗选出的 `bestParams`、训练窗 Sharpe、测试窗 Sharpe、测试窗逐期收益；
- 汇总给 `oosReturns`（各折拼接）与 `oosSharpe`，外加**效率比** = 平均测试 Sharpe / 平均训练 Sharpe（折数为 0 或平均训练 Sharpe ≤ 0 时是 `null`）。

读法：效率比明显低于 1，说明参数在样本外站不住；只有一折（数据太短）时这个数字没有信息量。

## 6. 留出与实验阶段

一条策略往下走要被记录成**实验**（experiment），阶段是固定的梯子：

```text
hypothesis → backtest → holdout → shadow → live_small → live
```

- `draft` 等同 `hypothesis`，`paper` 等同 `shadow`（历史别名）。
- 阶段上升要有对应的证据包，规则按阶段分：
  - 推到 `backtest`：Agent 要先有一份 `backtest` 证据包（先跑回测，再用 `experiment` 的 `pack` 动作生成）；没有就回 `EXPERIMENT_EVIDENCE_INCOMPLETE`，阶段不变。你自己在工作台里推进不受这条影响。
  - 推到 `live_small` / `live`：Agent 的请求一律被拒（`EXPERIMENT_TRANSITION_DENIED`，只留一条申请记录），要你本人在工作台里审，并输 PIN（`lab.stage`）。
- 实验对象里有 `holdoutWindow`：写清哪段时间是留出段。留出段的数据在 `holdout` 阶段才允许看；提前看过，这段就不算留出了。
- `live_small` 是**试运行**语义：证据包里的 `trialCount` 取「同族实验内不同参数规格数」与「同一执行器最近 30 天内跑过的回测数」两者的较大值（`TRIAL_WINDOW_DAYS` = 30，就是这个回看窗）。
- 大模型参与过的实验要如实标 `llm`。协议带 `LLM_LEAK_MARGIN_DAYS`（90 天）与已知训练截止时间表：数据区间离模型训练截止太近，就有「它见过这段行情」的嫌疑，`holdout` 阶段会因此要你解释。

## 7. 实验注册表

Agent 侧工具集 `experiment` 的动作：`create` / `get` / `list` / `update` / `attach` / `stage` / `pack` / `export`。

要写进去的东西（写不全，后面的人（包括你）就没法复核）：

| 字段 | 写什么 |
|---|---|
| `title`、`hypothesis` | 一句话假设，别写结论 |
| `subject` | 策略 `id` + `version` |
| `params` | 这次试的参数 |
| `assumptions` | 与回测里一致的成本假设 |
| `data` | 数据来源与区间（文件要给摘要） |
| `lineage` | 从哪条实验 / 哪个版本演化来的 |
| `holdoutWindow` | 留出段 |
| `llm` | 模型是否参与、参与了哪一步 |
| `conclusion` | 结论。写「在什么条件下失效」比写「有效」有用得多 |

照抄下面这个入参就能建成一条实验（`create` 只需要 `patch`）。`sha256` 取自回测结果里的 `strategySha256`：先跑一次回测拿到它；引擎已就绪时内核也会按策略 `id` 自己核对：

```json
{
  "action": "create",
  "patch": {
    "title": "<标题>",
    "hypothesis": "<一句话假设>",
    "subject": {
      "strategy": { "kind": "strategy", "id": "<策略 id>", "version": "<版本>", "sha256": "<sha256>" },
      "params": {}
    }
  }
}
```

`subject.strategy` 的 `kind` / `id` / `version` / `sha256` 写错或缺了哪项，错误里就点名哪条路径（例如 `/subject/strategy/version`）。

结论与描述里出现收益承诺类措辞会被直接拒收——这不是文风检查，是产品红线。

## 8. 证据包与导出

```text
gitrader lab export <实验 id> --out <文件>
gitrader lab verify <文件>
```

- `lab export` 把一个实验导成一份可带走的包（含证据与摘要）。加 `--out <文件>` 就写到你指定的文件（绝对路径，或相对当前目录，不限于数据目录）并打印写出的路径；不加 `--out`，JSON 直接打在屏幕上。
- `lab verify` 离线核验一份包（只读）：绝对路径的文件可以放在任何位置，相对路径从 `<数据目录>/lab` 里找；内容一致时退出码 0；不一致时打印差异并以 1 结束。**发给别人之前先自己 verify 一次。**

前向记录另有出口：

```text
gitrader ledger export [--out 名字]          # 写到 <数据目录>/exports/<名字>；不给名字用 gitrader-ledger-年月日-时分秒（本机时间）
gitrader ledger export --redact              # 去掉载荷，只留骨架
gitrader ledger verify                       # 重算本机库的哈希链
gitrader ledger verify <导出目录>             # 核对一份导出件
```

导出目录里有四个文件：

- `账单.csv`：**给人看的**，Excel 直接能开。只含成交，列是时间、账户、标的、方向（买入 / 卖出）、数量、价格、手续费、已实现盈亏、执行方（你本人 / Agent 名字 / 系统）。时间是**本机本地时间**。
- `trade-log.md`：同样是给人看的成交记录，时间也是本地时间，表头注明时区。
- `ledger.jsonl`、`manifest.json`：原样保留，给审计和 `ledger verify` 用。

`manifest.json`（`gitrader-ledger-export/2`）带导出时的链头、是否完整，以及用安装签名钥打的签名。`ledger verify <导出目录>` 会核对签名、条数、首尾序号和末条哈希，**能发现被删掉尾部或被改动的导出件**；本机库读得到时，还会用库里的安装公钥当受信公钥，并与本机库逐点比对，报告「库里在导出之后又新增 N 条」。旧版（/1）导出件没有签名，只能提示「无法发现尾部被删」。

上限要说清楚：签名身份存放在本机，**能读到本机安装私钥的人仍然可以重新签出一份整条重写的导出件**。验签只能证明「与那把安装签名钥一致、导出后没被改」，不能证明那把钥匙是你的。

## 9. 报告怎么出

回测报告有现成的出口：

1. **`gitrader research report <回测作业 id>`**（`--format md|json`，`--out <文件>`）；Agent 用 `research` 工具的 `backtest_report` 动作。回 `{ jobId, headline, metrics, markdown, truncated, assumptions }`：`metrics` 的夏普、总收益、最大回撤、期末权益、成交数、手续费与回测结果 `stats` 里的同名字段逐项相等（不重算、不四舍五入），Markdown 报告超过 6000 字符截断并标 `truncated`，整个回包不超过 8000 字节。作业没跑完回 `BUSY`，作业不存在回错误，不回空报告。
2. **实验包**（`lab export`）：机器可读、可核验，适合存档与交接；
3. **账本导出**（`ledger export`）：前向的成交日志，`账单.csv` 与 Markdown 那两份是给人看的；
4. **回测结果 JSON**（`backtest` 的 `result`）：自己渲染成表或图。

参数寻优、因子报告、组合分析、标的搜索走同一个 `research` 工具与 `gitrader research` 命令，用法见 17、13、19、14 号文档。

报告里必须原样带上假设（费率、滑点、成交模型、资金费与强平是否建模）与数据摘要。缺了假设的数字，等于没有数字。

## 10. 三条纪律

- **回测 / 回放数据不进前向账本。** 前向账本只记真实发生过的动作。
- **不做未来推断。** 报告写历史区间内发生了什么，不写「以后会怎样」。
- **试过多少次要写。** `trialCount` 与实验记录是同一件事的两面：只报最好那一组，等于撒谎。
