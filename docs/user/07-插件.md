# 插件

插件是把「个性化的东西」装进 Gitrader 的方式：指标、数据源、保护器、面板块、通知通道、技能包。**文件丢进目录就是安装**——没有安装向导，没有市场。

## 1. 目录与安装

```text
~/.gitrader/plugins/<目录名>/gitrader-plugin.json
~/.gitrader/plugins/<插件id>/<版本>/gitrader-plugin.json
```

两种落盘形态都认。装完跑一次：

```text
gitrader plugins reload
```

服务在跑就通知服务，不在跑就离线扫一遍。输出是 `+added ~updated -removed, rejected n`；有被拒的会逐条给出原因，此时退出码是 2。

## 2. 六个命令

| 命令 | 作用 | 要不要服务在跑 |
|---|---|---|
| `gitrader plugins check <目录> [--strict] [--json]` | 只校验，不装。每行 `码 路径 说明`，末行 `ok <id>@<版本>` 或 `REJECTED n problem(s)`；通过 0，被拒 2 | 不用 |
| `gitrader plugins pin <目录>` | 重算并写回 `source.sha256`（改了任何文件都要重钉） | 不用 |
| `gitrader plugins reload` | 重新扫描插件目录 | 服务在跑要本地会话；没跑不用 |
| `gitrader plugins list` | 每个插件的校验结果、已授予 / 待授予权限、是否启用 | 不用 |
| `gitrader plugins grant <id> [权限…]` | 启用插件并逐项授予权限（要 PIN，**先停服务**） | 要停 |
| `gitrader plugins call <id> <工具> [json\|@文件\|-]` | 调一次工具 | 不用（会临时起内核；服务在跑就走服务） |

`check` 的 `--strict` 按「未签名不放行」的口径检查——发布前用它，别用默认口径。

## 3. 清单字段

主要字段：`schema`、`id`、`kind`、`name`、`version`、`vendor`、`source`（含内容哈希）、`license`、`runtime`（`type`：`node` / `browser` / `builtin` …）、`entry`、`permissions`、`ui.blocks`、`requires`、`signature`、`compat`。

`kind` 的取值：`connector` / `datasource` / `factor` / `decision-model` / `executor` / `protector` / `strategy` / `workflow-template` / `engine` / `block` / `skill` / `layout-preset`。

字段级规范以 `docs/plugin-protocol.md` 与 `packages/protocol/src/plugin/manifest.ts` 为准。M1 内核**只能拉起 `runtime.type = "node"` 的插件**（子进程）；其他运行时类型能通过清单校验，但启动时会返回「M1 不支持」。

### `tools[]`：暴露给 Agent 的工具

```json
"tools": [
  { "name": "position_size", "desc": "…", "tags": ["utility", "risk"],
    "input": { "type": "object", "required": ["equity", "stop"], "properties": { "equity": { "type": "string" }, "stop": { "type": "string" } } },
    "output": { "type": "object", "required": ["qty"] },
    "permissions": [] }
]
```

- `input` 必须是 `type: "object"` 的 JSON Schema；调用时先过它，不合是 `INVALID_PARAMS`（说明带字段路径）。
- 声明了 `output` 的，返回值不合是 `PLUGIN_RESULT_INVALID`，结果不会给到 Agent。
- **没写进 `tools[]` 的工具，内核不转发**（`PLUGIN_TOOL_UNKNOWN`）。
- 工具自己声明的 `permissions` 必须是清单权限的子集，且每一项都要已授予（否则 `MANDATE_LIMIT`）。
- 工具参数里**不许出现密钥类参数**（`TOOL_SOLICITS_SECRET`，直接拒装）。

### `evidence`：业绩与回测数字

`evidence: { claims: [...], notes? }`，每条是 `{ metric, value, basis, window: {from,to}, ref?, assumptions? }`。

- `basis` 只有 `backtest` / `paper` / `live`；
- 回测类声明必须写 `assumptions`（成本、滑点、数据来源与区间）；纸面 / 实盘类必须带 `ref`；
- `claims` 可以是空数组：**没有数字是诚实的答案**；
- 内核与界面原样展示，不做二次加工。

## 4. 权限：默认拒绝

- 清单里**声明**了才可能有；声明了还要你本人确认（`plugins grant`）才授予。逐项授予，每次入账。
- 可申请：`market.read`、`account.read`、`ledger.read`、`ledger.append`、`trade.paper`、`trade.propose`、`trade.live`（仍受授权书与风控闸约束）、`takeover.trigger`（只在自身作用域）、`venue.credentials`（仅连接器）、`net.fetch`、`fs.read.user`、`workspace.control`、`ui.block`、`notify.user`。
- **永远不可授予**，写了就拒装：`withdraw`、`transfer`、`approval.decide`、`risk.relax`、`policy.write`、`mandate.issue`、`mandate.promote`、`credential.read`、`plugin.install`、`risk.temporaryRelax`。
  也就是说：插件不能提现、不能转账、不能批准提案、不能放宽风控（含临时放宽）、不能签发或升级授权书、不能读明文凭据、不能装别的插件。
- 放行条件（四个都要满足）：校验通过、已启用、工具已在 `tools[]` 声明、工具声明的权限全部已授予，并且入参合 schema。

## 5. 钉版本与内容哈希

- 清单里的 `source.sha256` = 包内除清单外每个文件 `{路径, sha256}` 按路径排序后的哈希。
- 内核加载时重算一遍，**对不上就拒绝**；插件跑起来之后内容变了会被停掉。
- 改任何文件都要 `gitrader plugins pin <目录>` 重钉。
- 依赖（`requires`）必须是精确版本加哈希，没有 `latest`。

## 6. 签名与开发者模式

- 已签名插件：`signature` 是对「清单（去掉签名）+ 文件清单」摘要的 Ed25519 签名，签名公钥必须在信任根里。信任根 = 内置（M1 为空）+ 你在 `plugins.trustRoots` 里手写的公钥。
- 未签名插件：只有 `plugins.developerMode: true` 才加载（本地开发用），且**不能**申请 `trade.live` 与 `venue.credentials`。
- 随包插件（`gitrader plugins install notify-webhook` 等 6 个通知插件）**不需要**打开 `developerMode`：产品构建时为它们生成内容哈希清单 `dist/plugins-bundled/BUNDLED-HASHES.json`（每个插件的 id、版本、内容 pin 与清单摘要），内核只从产品自己的安装目录读这份清单——放在 `GITRADER_HOME` 或配置里的同名文件一概不认。装好的随包插件内容必须和清单逐项对得上才按内置信任放行；改了其中任何文件（哪怕用 `plugins pin` 重新钉过版本）或改了它的清单，都会被拒（`UNSIGNED_NOT_ALLOWED`），用 `gitrader plugins install <名> --force` 重装即可。这套信任没有引入任何签名私钥，也不会放宽对其他未签名插件的要求。
- 签名不对、密钥不在信任根里，直接拒装。

## 7. 隔离：不是安全沙箱

- Node 插件跑在独立子进程里：不继承你的环境变量、工作目录是插件目录、只经标准输入输出与内核通信；另加 Node 的 `--permission` 与 `--allow-fs-read=<插件目录>`，限制文件读取与子进程。
- **这不是安全沙箱。** 权限在内核 API 层强制（插件要拿数据只能经内核）；进程层的限制是尽力而为，Node 22 不强制网络限制。第三方插件的信任主要来自签名与来源审查。
- 崩溃会退避重启，另有定时健康检查。
- 浏览器运行时的块跑在 `sandbox="allow-scripts"`（不给 `allow-same-origin`）的 iframe 里，只能经块桥拿清单里声明过的订阅 / 查询 / 命令。

## 8. 从哪抄第一个

`packages/plugin-template/example/` 下两份：

- `ema-reading`：一个 EMA 读数指标块（带 UI）；
- `position-size`：一个零权限的工具插件——**第一次写插件从它抄**，步骤见 `docs/plugin-quickstart.md`。

一个最小可用循环长这样：

```text
cp -r <模板目录> ~/.gitrader/plugins/my-plugin     # 改 id / name / 工具名
gitrader plugins check ~/.gitrader/plugins/my-plugin
gitrader plugins pin ~/.gitrader/plugins/my-plugin
gitrader plugins reload
gitrader plugins grant my-plugin                    # 要停服务，要 PIN
gitrader plugins call my-plugin my_tool @args.json
```

## 9. 常见拒绝码

| 码 | 意思 | 修法 |
|---|---|---|
| `SCHEMA` | 清单缺字段或类型不对 | 对照字段表补 |
| `PERMISSION_UNKNOWN` | 权限名不在枚举里 | 用第 4 节的名单 |
| `PERMISSION_NEVER_GRANTABLE` | 申请了永远不可授予的权限 | 删掉；这类能力不属于插件 |
| `HASH_MISMATCH` | 内容与 `source.sha256` 不符 | `plugins pin` 重钉 |
| `SIGNATURE_KEY_UNTRUSTED` | 签名公钥不在信任根 | 加 `plugins.trustRoots`，或开发期用 `plugins.developerMode` |
| `TOOL_SOLICITS_SECRET` | 工具参数里要密钥 | 改成从环境变量读 |
| `PROMISE_LANGUAGE` | 文案里有收益承诺类措辞 | 改成事实陈述 |

## 10. 卸载

把目录移走，然后 `gitrader plugins reload`。已授予的权限记录留着（审计要用）；要彻底清掉，按 `plugins list` 里的 id 走工作台的插件页撤销。安装、升级、移除都会写进账本。

## 11. 上手卡点：reload、developerMode、权限 kind、Windows 升级

第一次写插件最容易卡住的四件事，都是当前实现的真实行为，照这一节做能省掉一轮排查。

### 11.1 服务在跑时 `gitrader plugins reload` 要本地会话

- **服务没跑**：命令走离线扫描，不需要会话，输出 `+added ~updated -removed, rejected n`。
- **服务在跑**：命令改走服务的写操作（`plugin.reload`），要本地写会话——先用 `gitrader session login` 把服务启动时给的一次性启动令牌换成会话。没登录过、或会话过期，命令直接失败并提示去跑 `gitrader session login`。脚本里第一次调用最容易撞上这条，不是插件写错了。

### 11.2 改 `plugins.developerMode` 要重启服务

`gitrader.json` 在启动时读一次，没有文件监听、也没有 SIGHUP 重载，`plugins reload` 用的是内存里那份配置。所以「把 `plugins.developerMode` 改成 `true`，再 reload」不会生效：先 `gitrader stop`，再 `gitrader serve`。

### 11.3 权限要和 `kind` 对得上：`skill` 申请不了 `net.fetch`

权限不是「写了就能申请」——`packages/protocol/src/plugin/manifest.ts` 里有一张「权限 → 允许的 `kind`」表。`net.fetch` 只给 `datasource` / `decision-model` / `connector` / `engine`；`skill` 或 `block` 的清单写 `net.fetch`，校验直接给 `PERMISSION_KIND_MISMATCH`（`kind skill cannot request net.fetch`）。同理：`trade.live` 只给 `executor` / `engine`，`fs.read.user` 只给 `engine` / `factor` / `datasource`，`venue.credentials` 只给 `connector`。

清单里的 `package` 字段只有两个值：`skill` 与 `block`。`package: "skill"` 必须配 `kind: "skill"`（否则 `PACKAGE_KIND_MISMATCH`）；通知通道插件是 `package: "block"` + `kind: "connector"`，两者不冲突。

**但运行时那层不强制**：第 7 节说的「不是安全沙箱」对 skill 同样成立——清单拒了 `net.fetch`，子进程里直接 `require('node:https')` 不会被 Node 拦（Node 22 的 `--permission` 不覆盖网络 API）。所以第三方 skill 的信任只来自签名与来源审查，别把「清单里没申请 `net.fetch`」当成「它连不上网」。

### 11.4 Windows 上怎么升级一个正在用的插件

Windows 会锁住运行中的插件进程打开的文件：直接覆盖或删除插件目录会失败（`EBUSY` / `EPERM`），`plugins reload` 也就读不到新内容。CLI 里没有「只停某一个插件」的子命令，正确顺序是停服务：

```text
gitrader stop                                     # 停服务，插件子进程随之退出，目录解锁
# 替换 ~/.gitrader/plugins/<目录名> 里的内容（改过文件就要重钉）
gitrader plugins pin ~/.gitrader/plugins/<目录名>
gitrader serve                                    # 重新起服务
gitrader plugins reload                           # 服务在跑时走它，要会话；不方便就停服务后单独跑一次
gitrader plugins list                             # 确认版本号与哈希已是新的
```

卸载同理：Windows 上先把目录移走再 reload 会失败，同样先 `gitrader stop`。
