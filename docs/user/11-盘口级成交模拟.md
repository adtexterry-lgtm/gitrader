# 盘口级成交模拟

K 线级回测只按「下一根开盘价」成交，成本按固定基点算。它回答不了两个问题：**这一单按这个价到底吃不吃得到**，**吃完这一档还剩多少量**。盘口级模拟把每一档的挂单量当真：被吃掉就少一份，两张单在同一毫秒不能吃同一份量。

这一页讲怎么准备数据、怎么读回报、以及哪些结论**不能**从这份模拟里得出。

## 1. 它是什么、不是什么

| 是 | 不是 |
|---|---|
| 确定性的撮合核心：同样的记录 + 同样的命令序列 → 同样的成交回报，逐位一致 | 交易所的替代品：真实排队、隐藏单、交易所侧风控都不在里面 |
| 独立库（`@gitrader/sim-book`），零第三方依赖，不联网、不读系统时钟 | 内置通道：引擎侧的接入看回测里的 `fillMode` 参数；**你手里的版本若没有这个参数，说明接入尚未随包发布** |
| 只算成交流水与手续费 | 资金费、强平、借贷利息：那是持仓记账的事，不在这层 |

**它需要的输入不是 K 线，是盘口。** 没有盘口 / 逐笔数据时，别用这层硬凑：退回去用 K 线级模拟，并在报告里写明成交假设。

## 2. 数据格式：一行一条 JSON

价格与数量一律写**十进制文本**，不收 JSON 数字，也不收 `1e-8` 这类指数写法。整串记录上 `ts` 必须非递减；`seq` 可选，一旦出现就得每条都带且非递减。

```jsonl
{"type":"book_snapshot","ts":1000,"seq":1,"instrument":"BTCUSDT","bids":[["100.5","2"],["100","3"]],"asks":[["101","1.5"]]}
{"type":"book_delta","ts":1001,"seq":2,"instrument":"BTCUSDT","side":"ask","action":"add","price":"101.5","size":"0.5"}
{"type":"trade","ts":1002,"seq":3,"instrument":"BTCUSDT","price":"101","size":"0.25","aggressor":"buy","tradeId":"t-1"}
```

| 记录 | 必填 | 规矩 |
|---|---|---|
| `book_snapshot` | `ts`、`instrument`、`bids`、`asks` | 整簿替换：买档严格递减、卖档严格递增、档位不许重复、买一必须低于卖一 |
| `book_delta` | `ts`、`instrument`、`side`、`action` | `add` / `update` 必带 `price` 与 `size`；`delete` 只带 `price`；`clear` 都不带 |
| `trade` | `ts`、`instrument`、`price`、`size` | `aggressor` 取 `buy` / `sell` / `unknown`，主动方向决定吃哪一侧的挂单量 |

`.gz` 后缀的文件在读写时自动压缩 / 解压。**先校验再撮合**：校验器会把整串记录真跑一遍盘口，抓「增量命中不存在的档位」这种结构上合法、语义上不成立的数据。

```ts
import { validateJsonl, readJsonlText } from '@gitrader/sim-book'

const result = validateJsonl(readJsonlText('book.jsonl.gz'))
if (!result.ok) console.error(result.errors)   // [{ line, code, message, field? }, …]
```

校验覆盖：JSON 语法、记录类型、字段类型、十进制语法、数量为正、档位排序与去重、盘口不许交叉、`ts` 单调、`seq` 一致且单调。只想看结构时传 `validateJsonl(text, { strictBook: false })`。

## 3. 下单与成交

```ts
import { SimBook } from '@gitrader/sim-book'

const sim = new SimBook({ instrument: 'BTCUSDT' })
sim.apply({ type: 'book_snapshot', ts: 1, instrument: 'BTCUSDT', bids: [['100', '5']], asks: [['101', '5']] })
const r = sim.submit({ id: 'o-1', side: 'buy', type: 'market', qty: '1.5' }, 2)
// r.status === 'filled'；r.fills[0] === { price: '101', qty: '1.5', liquidity: 'taker' }
```

订单类型 `market` / `limit` / `stop_market` / `stop_limit`，有效期 `gtc` / `ioc` / `fok`，修饰 `postOnly` / `reduceOnly`。

| 形态 | 约定 |
|---|---|
| 市价 | 从对手方最优档逐档吃到吃完；吃不完的剩余**不挂簿**（`reason: insufficient_liquidity`）；一口都吃不到则拒单 |
| 限价 | 价格穿越才吃，成交价取档位价（不会比限价差）；剩余挂簿，可撤 |
| post-only | 下单即会吃单则整单拒绝；只约束入场，挂上之后照常成交 |
| IOC / FOK | 能成交多少算多少 / 试算整单吃下才落账；剩余作废，FOK 不消耗任何流动性 |
| 止损 / 止损限价 | 触发价被最新成交价穿过时转成市价 / 限价；未触发时挂簿等触发 |
| 减仓 | 数量按传入持仓截断（`notes` 写明）；无仓可平或与持仓同向则拒单 |

## 4. 挂单能不能成交：三档假设

成交价永远是**自己的限价**（maker）。三档只在「这一笔逐笔成交算不算我的」上有差别：

| 档位（`fillModel`） | 同价成交 | 穿价成交 | 隐含假设 |
|---|---|---|---|
| 严格档 | 不成交 | 成交，量 = min(剩余量, 本笔额度) | 穿价说明整档被扫过；同价可能是前方队列吃掉 |
| `queue` | 先扣「挂单时该档显示量」当前方量，扣完才成交 | 前方量清零后成交 | 显示量 = 前方量，不考虑隐藏单，前方量只减不增 |
| `optimistic`（缺省） | 成交 | 成交 | 永远排在队首，等于触价即成交 |

队列位置在订单**到达场所**那一刻按该档显示量记一次（改价后重记）；同一价有多张我方挂单时每张各按显示量估前方量，偏悲观。严格档的取值字面量见包内 README（用户文档的文案过滤会拦掉那个英文词，这里只按行为描述）。

## 5. 延迟：命令按到达时刻的盘口撮合

`latency` 给下单 / 改单 / 撤单各自的固定延迟（毫秒）+ 可选确定性抖动（固定种子 → 固定序列）。语义只有一条：命令在「发出时刻 + 延迟」才到场，**按到达时刻的盘口撮合**，不是发出时刻。

```ts
const sim = new SimBook({ instrument: 'BTCUSDT', latency: { baseMs: 5, insertMs: 20, updateMs: 5, cancelMs: 10, jitterMs: 8, seed: 42 } })
const ack = sim.submit({ id: 'o-1', side: 'buy', type: 'market', qty: '1' }, 1_000)
ack.notes            // 写明「在途：下单延迟 N ms，预计 T 到达场所」
sim.arrivalOf('o-1') // 到达时刻
```

- 在途的单不参与撮合、不吃流动性。
- 撤单在途期间订单仍可能被行情成交——这正是延迟的意义。
- 到达时刻恰好等于某条记录的 `ts` 时按**该记录之后**的盘口撮合（同一毫秒取较晚那版，偏悲观）。
- 缺省零延迟 = 命令在发出时刻就到场。

## 6. 手续费

`fees` 给 maker / taker 两档费率（分数文本，负数 = 返佣），可按币种覆盖。佣金 = 成交价 × 成交量 × 费率，18 位定点精确。

```ts
const sim = new SimBook({ instrument: 'BTCUSDT', currency: 'USDT',
  fees: { maker: '0.0002', taker: '0.0005', overrides: { USDT: { maker: '0', taker: '0.0004' } } } })
sim.feesOf('o-1')    // 这一单的费用
sim.feeSummary()     // maker / taker 分开的累计
```

## 7. 读结果时的三条硬话

1. **成交好看不代表策略好**：这一层的输入是你给的盘口，盘口质量决定了结论的上限。来源、时间范围、是否补齐、有没有断层，都要写进报告。
2. **`optimistic` 是缺省，也是最乐观的假设**：触价即成交。要论证「这条策略在排队上能不能活」，用 `queue` 或严格档再跑一遍，两次数值的差就是排队成本。
3. **拿不到盘口就别假装有**：这层的结论只在「有逐笔 / 盘口数据、且数据经过校验」的前提下成立。
